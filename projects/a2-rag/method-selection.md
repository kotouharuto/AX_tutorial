## 4. 「無料」の条件

| 方式 | 無料で使える範囲 | 納品で有料になる理由 |
|---|---|---|
| NotebookLM | 個人利用 | 組織利用は Workspace 契約 |

| Dify | セルフホストは無料・商用可 | Cloud の権限管理は有料。マルチテナント提供は商用ライセンス |
| Gemini API（自作・Dify の生成） | 無料枠 | **無料枠は送信内容が学習・人間レビュー対象**（→ [記録](../../docs/pitfalls/a1-gemini-free-tier-data-use.md)） |

## Q1. 顧客から「社内文書を検索できる AI を作りたい」と言われたとき、方式を決めるために何を聞くか

```
1. 外部サービスの利用可否
   - 社内文書を外部の AI サービスに送ってよいか（規定はあるか）
   - 情シスの申請手続きはあるか。通るまでの期間は
   - 「送る」の範囲：保存が NG か、API 経由の一時送信も NG か

2. 利用者
   - 誰が使うか、何人か
   - 部署や役職で「見せる文書」を分ける必要があるか

3. 文書
   - 何件あるか、今後増えるか
   - 形式：スキャン PDF（画像）や表はあるか   ← 今回の失点要因の大半
   - 同じ規程の新旧版が混在しているか

4. 運用
   - 新しい文書を誰が追加するか
   - 担当者が異動・退職したとき、誰が引き継ぐか

5. 予算の中身
   - 構築費か、月額か、ライセンス費込みか
```

## Q2. 具体ケースへの適用

各ケースについて「どの方式を選ぶか」と「決め手」を書く。
判断材料が足りないなら「何を追加で聞くか」でもよい。

### ケース1：今回の題材そのまま

社内規程・手順書が60件程度。Google Workspace を使っている。
情シスがあり、外部サービスの利用には申請が要る。
「ベテランしか知らないことを新人も調べられるようにしたい」。

```
選ぶ方式：NotebookLMかClaudeのEnterpriseのプロジェクト
決め手：利用に申請がいる点から、外部サービスの利用が不可能ではない上に、構築も早い。またGoogle Workspaceを使用していることから、NotebookLMやClaude(コネクタ)はGoogleとの互換性が高いので選びます。
```

### ケース2：データの置き場所に制約がある

同じ題材。ただし「社内文書を外部の AI サービスにアップロードするのは禁止」と
情シスから言われている。予算は限られている。

```
選ぶ方式：Dify セルフホスト。ただし生成・埋め込みをローカルモデルに置き換える

決め手：
  - 既製2方式は文書を外部に送るので即除外
  - Dify も自作も、今回の構成のままでは Gemini に文書を送っている。
    埋め込みを multilingual-e5（自作で実証済み、ローカル動作）、
    生成を Ollama 経由の日本語対応モデルに置き換えれば完全ローカルになる
  - Dify と自作の分岐は「運用を誰がするか」。予算が限られる＝保守に人を割けないなら、
    GUI で文書追加ができる Dify の方が運用コストが低い。
    ただし構築は技術者が必要（実測 3.5h。ローカル LLM の導入でさらに増える）

先に確認すること：
  「禁止」の範囲。保存が NG なだけなら、Gemini 有料枠（学習に使われない）で
  API 送信は許容される可能性がある。そうなら今回の構成のまま使え、工数が大きく減る。
  要件を厳しく解釈して工数を積む前に、緩められるかを聞く。
```

### ケース3：部署ごとに見せる文書を分けたい

人事規程は人事部と管理職のみ、IT 手順書は全員、経理規程は経理部のみ。
利用者は200人。文書は今後も増える。

```
選ぶ方式：要件を緩められるかで分岐する

  A. 「人事規程は社内ポータルで別管理にして、AI 検索は全員向け文書だけ」に緩められる
     → NotebookLM / Claude（Team 以上）1つで済む。ケース1と同じ

  B. 部署別の出し分けは必須だが、「部署ごとに別のノートブックを使う」運用を受け入れられる
     → 既製方式を部署別に3つ作る。人事部の人は「全員向け」と「人事向け」を行き来する。
       横断検索はできない。新文書の振り分けは運用者の手作業

  C. 「1つの窓口で、所属に応じて自動で出し分け」が必須
     → 自作。文書にアクセスレベルのメタデータを付け、利用者の所属でフィルタする。
       認証との連携まで含めて全部作る。工数は最大

決め手：
  精度表は判断に使わない。4構成で 24.5〜30 の差より、権限モデルの差の方が大きい。
  Dify を選ばない理由：Dify のナレッジ権限はワークスペースメンバー（構築側）向けで、
  チャットアプリのエンドユーザー200人の出し分けには使えない。
  アプリを3つ作れば B と同じになり、既製方式に対する優位がない

「利用者200人」「文書は増える」の扱い：
  方式選択の理由ではなく、A〜C どれを選んでも発生する運用コストの規模。
  200人なら個人契約は不可（Workspace / Team 契約が前提）。
  文書が増えるなら「誰が権限を付けるか」を決めないと、どの方式でも半年で崩れる
```

## Q3. 「作らない」を提案する条件

あなたの当初の仮説「既製で十分」は数値で支持された。
では顧客に対して、**どういう条件が揃ったら「作らなくていい」と言うか。**
逆に、どういう条件があったら作るか。

```
作らない条件：
  - 外部AIサービスの利用規制がない場合
  - 利用者数が多い
  - 部署ごとに文書が異なる場合(ユーザーの部署によってベースにする情報が異なるため、外部サービスの方が容易)
  - 予算に余裕がない

作る条件：
  - 外部AIサービスの利用規制が存在する
  - 構築工数がかかっても構わないので、difyや自作で安全に情報を管理したい
  - 予算に余裕がある
```

## Q4. 各方式を選んで失敗するケース

```
NotebookLM / Claude Projects を選んで失敗する場合：外部企業サービス利用禁止の会社に提案してしまうこと

Dify を選んで失敗する場合：業務委託で構築したものが止まってしまうことで、誰も直せないと言うリスク

自作を選んで失敗する場合：保守契約を行わないと、保守をできる人がいない場合に困る。また、精度が出る保証が外部サービスよりも少ないので、過剰に期待をされると落差でクレーム等を入れられる可能性がある。
```

## Q5. 顧客への説明

第1部の比較表を見せながら、3分で説明するとしたら何を言うか。
技術用語は使ってよい。**顧客が選べる説明**にすること。

```
まず結論から言います。60件程度の社内文書なら、AI を新しく作る必要はありません。

こちらの表を見てください。同じ文書・同じ30問で4つの方式を比べました。
Google の NotebookLM と Anthropic の Claude は、構築ゼロで 30点満点中 29.5 と 30 です。
私が手で作った方式は 28、GUI ツールで作った方式は 24.5 でした。
作った方が精度が低い。これが実測です。

「分からないことを分からないと言えるか」も測りました。
存在しない情報を聞いたときに、それらしい嘘を返した方式はゼロでした。
どの方式でも、この点は安心してください。

では何で選ぶかというと、精度ではなく3つの条件です。

1つ目、社内文書を外部サービスに送ってよいか。
  送ってよければ、NotebookLM か Claude で今日から始められます。
  ダメなら、自社のサーバに置く方式になり、構築に数日かかります。

2つ目、部署ごとに見せる文書を分ける必要があるか。
  なければ1つで済みます。あれば部署ごとに分けて作るか、
  出し分けの仕組みを作るかで、工数が大きく変わります。

3つ目、文書にスキャンした PDF や表が多いか。
  多いなら、既製の方式の方が有利です。
  作る方式は、画像の PDF を読めずに2問落としました。

この3つを教えていただければ、方式は今日決められます。
多くの場合、答えは「作らない」です。
その方が早く、安く、精度も高い。私の役割は、作らなくていいと判断できる根拠を持っていることです。
```
