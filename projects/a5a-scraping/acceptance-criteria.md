# スクレイピング案件の受注判断基準

A-5a で実際に踏んだ内容をもとにした、**着手前に確認すること**の一覧。

対象は「技術的に可能か」と「やってよいか」と「継続運用できるか」の3点。
価格・契約条件はこの文書の範囲外。

> **法的判断はしない。** 以下は確認すべき項目と、確認した結果をどう扱うかの整理。
> 利用規約違反の可否や著作権の解釈が争点になる案件は、**判断せず持ち帰る。**

---

## 0. 最初の3分で判定できること

この3つを先に見る。ここで断る案件に時間を使わない。

| 確認 | 方法 | 結果の扱い |
|---|---|---|
| ログインが必要か | 対象ページをログアウト状態で開く | **必要なら原則断る**（後述） |
| 個人情報を含むか | 取得対象の項目を列挙してもらう | 含むなら条件付き（後述） |
| JS 描画か | **「ページのソースを表示」**で目的のデータを探す | 工数と依存関係が変わる |

### JS 描画の判定を間違えると作り直しになる

**開発者ツールの Elements は判定に使えない。** あれは JavaScript 実行後の DOM なので、
静的に取得できないデータも表示される。見るのは「ページのソースを表示」。

```bash
# データの一部が HTML に含まれるかを直接見る
curl -s <URL> | grep -o "<探している文字列>"
```

A-5a では、JS 描画ページを静的手法で取ると
**10ページ巡回して0件・例外なし・終了コード0**になった。
ページ送りのリンクだけがサーバ側で出力されるため、
「巡回は成功したが1件も無かった」という結果になり、
**サイトが本当に空の場合と区別できない。**

`<script>` の中に JSON が埋まっている場合は、ブラウザを起動せず直接読める。
A-5a の実測では **inline 2.2秒 vs ブラウザ 8.7秒**（待ち時間を除く）で4倍速く、
結果は100件完全一致だった。**先に `<script>` を探す。**

## 1. robots.txt

### 確認方法

```bash
curl -s <origin>/robots.txt
```

`urllib.robotparser` で機械的に判定できるが、**戻り値の意味を取り違えやすい。**

| 状況 | `can_fetch` | 評価 |
|---|---|---|
| `read()` 未実行 | False | 安全側 |
| `read()` が失敗（到達不能） | **False** | 安全側（fail-closed） |
| robots.txt が **404** | **True** | 慣習上は正しいが**誤読しやすい** |
| `Disallow: /` | False | 正しい |

### 404 を許可の根拠にしない

A-5a の対象サイトは2つとも robots.txt が存在せず、判定は「許可」と出た。
これは**規定が無いだけ**で、確認した結果の許可ではない。

顧客への説明で「robots.txt を確認しました」を安全性の根拠として出さない。
**後で問題になったとき、確認したと言った側の責任になる。**

### robots.txt で分からないこと

| 確認項目 | robots.txt で分かるか |
|---|---|
| クローラへの規定 | あれば分かる |
| **利用規約での禁止** | **分からない。別途読む** |
| ログインの要否 | 分からない |
| 個人情報を含むか | 分からない |
| アクセス頻度の妥当性 | Crawl-delay があれば一部 |

## 2. 利用規約

**robots.txt とは別に読む。** 以下の記述があれば、技術的に可能でも受けない。

- 自動化されたアクセス・クローラ・ボットの禁止
- 取得したデータの再利用・再配布の禁止
- API が別途提供されており、そちらを使うよう指定されている

### API があるなら API を使う

「スクレイピングしたい」という依頼でも、**公式 API があればそれを使う提案に変える。**
理由は技術的なもので、規約以前に壊れにくい。

- HTML の変更で壊れない（セレクタ破壊の心配がない）
- 利用条件が明示されている
- レート制限が明示されている

A-5a で観察したとおり、セレクタ破壊は**例外を出さず件数も正常なまま**中身が空になる。
この検知の仕組みを作って運用する手間が、そのまま API を使わない代償になる。

---

## 3. ログインの要否

**ログインが必要な案件は原則断る。** 技術的にできるかどうかとは別の理由。

| 問題 | 内容 |
|---|---|
| 認証情報を預かることになる | 保管・漏洩時の責任が発生する |
| 規約違反の可能性が高い | 会員向けページの自動取得を禁じている規約が多い |
| アカウント停止のリスク | 停止された場合、顧客の業務そのものが止まる |
| 多要素認証 | 自動化できない、または回避することになる |

### 受ける場合の条件

顧客が**自社のサービス**（自分が管理している側）に対して行う場合は検討できる。
その場合も次を確認する。

- 認証情報は顧客側の環境に置き、こちらは受け取らない
- テスト用アカウントで検証する
- **CAPTCHA やボット検知がある場合は断る。** 回避は行わない

## 4. 個人情報

取得対象に次が含まれるなら、**含まれる項目を明示した上で顧客に判断を戻す。**

- 氏名、メールアドレス、電話番号、住所
- SNS のアカウント名と投稿内容の紐付け
- 公開されていても、**集約すると個人を特定できる**組み合わせ

「公開されているから問題ない」で進めない。
公開情報の集約は、単体では特定できない情報を特定可能にする。

### 受ける場合の条件

- 取得項目を最小限にする（目的に不要な項目は取らない）
- 保管期間と削除方法を決めておく
- **検証・開発段階では実データを使わない**（A-5a では練習用サイトのみを使った）

---

## 5. アクセス間隔と所要時間

### 間隔は Crawl-delay の指定に関係なく空ける

A-5a の対象は Crawl-delay の指定が無かったが、**1秒以上空けた。**
指定が無いことは無制限の意味ではない。

### 見積もりは「ページ数 × 間隔」が支配的

A-5a の実測。

| 項目 | 値 |
|---|---|
| 1ページの取得（静的） | 0.45〜0.61 秒 |
| 70ページの合計 | **103.8 秒** |
| うちアクセス間隔の待ち時間 | **約70秒（約7割）** |

**取得処理を速くしても全体は縮まない。** 縮めるには間隔を詰めることになり、
それは礼儀と負荷の問題なので詰めない。

顧客に説明するときは「ページ数 × 1秒 + α」で概算を示す。
**1万ページなら間隔だけで約3時間**になる、という形で規模の話を先にする。

### ブラウザを使う場合の追加コスト

| 項目 | 実測 |
|---|---|
| Playwright の chromium | **約554MB**（本体359MB＋headless shell 195MB） |
| ダウンロード時間 | 42秒 |
| **初回起動**（新規展開分のスキャン） | **75.1秒**（10ページ） |
| 2回目以降 | 8.7秒（**8.6倍速い**） |

**初回だけ極端に遅い。** エンドポイント保護が新規ファイルをスキャンするため。
顧客環境では「初回の起動に数分かかります」と手順書に明記する必要がある
（→ `a4-endpoint-protection-blocks-import.md`）。

## 6. 継続運用できるか（ここを見落とすと後で効く）

一度取るだけなら簡単だが、**定期実行は別の話。**

### 壊れたことに気づける設計が必要

セレクタ破壊を4通り試した結果。

| ケース | 件数 | 例外 | 素朴な差分通知 |
|---|---|---|---|
| クラス名が変わった | 0 | なし | 差分なし |
| 階層が1段増えた | **20（正常）** | なし | 差分なし |
| 価格だけ変わった | **20（正常）** | なし | **差分なし** |

**件数の監視だけでは3ケース中1ケースしか捕まえられない。**
必要なのは次の3点。

1. 件数が0
2. 前回比の急減
3. **必須フィールドごとの空率**

3番目が無いと、「件数は正常だが監視対象の項目だけが空」という状態を見逃す。
**差分検出は健全性の判定に使えない。** 壊れると差分が出なくなる。

### 異常時の扱い

異常値を次回の基準にすると、**1回見逃すと以降ずっと見逃す。**

```
1000件 → 0件（異常）→ 0件を基準に記録
       → 次回も0件 → 「前回比100%」で正常扱い
```

異常時は基準値を更新しない。

### 通知の設計

- **差分がないことを通知しない。** 毎回メールが来ると読まれなくなる
- 初回は全件が「追加」になるので通知しない
- 異常は必ず通知する。**沈黙を正常の合図にしない**

### 定期実行の置き場所（macOS）

保護対象フォルダ（**Desktop / Documents / Downloads**）に置かない。

- TCC により launchd から読めない（`Operation not permitted`）
- **iCloud Drive の同期対象**だと、実体化されていないファイルの読み込み、
  同期の競合、オフライン時の失敗が起きる

フルディスクアクセスを付与すれば動くが、
**顧客に「バッチのために全ディスクアクセスを許可してください」とは言わない。**
置き場所で解決できるものを権限で解決しない。

Windows のタスクスケジューラでも同型の確認が必要
（PATH、cwd、**コンソールがない** → `a4-windows-stdout-encoding.md`）。

## 7. 判定の早見表

| 状況 | 判断 |
|---|---|
| 利用規約が自動アクセスを禁じている | **断る** |
| CAPTCHA・ボット検知がある | **断る**（回避しない） |
| 第三者サービスへのログインが必要 | **断る** |
| 公式 API がある | **API を使う提案に変える** |
| 個人情報を含む | 項目を明示して顧客に判断を戻す |
| 規約の解釈が争点になる | **判断せず持ち帰る** |
| JS 描画・数万ページ規模 | 受けられるが、工数と初回コストを先に示す |
| 静的・小規模・公開データ | 受ける |

---

## 8. 見積もりに必要な情報（顧客に聞く）

技術的な確認事項に限定した一覧。

```
□ 対象 URL（一覧ページと詳細ページの両方）
□ 取得したい項目（列単位で）
□ 想定ページ数 / 件数
□ 実行頻度（1回のみ / 日次 / 週次）
□ 実行する場所（顧客の PC / サーバ / どちらでもよい）
□ 出力形式（CSV / Excel / データベース / API 連携）
□ 異常時の連絡先（誰に、どの経路で）
□ ログインの要否
□ 取得対象に個人情報が含まれるか
```

**「異常時の連絡先」を最初に聞く。** 通知先が決まらないと、
壊れたことに気づける設計にできない。A-3 の引き渡しで空欄にした
「誰が対処するか」と同じ項目で、技術ではなく顧客組織の事情で決まる。
