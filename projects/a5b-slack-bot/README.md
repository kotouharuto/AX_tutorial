# A-5b：Slack Bot

Slack のスラッシュコマンド `/inquiry` で問い合わせを受け、A-1 と同じ方法（Gemini）で分類して返す。
分類に応じて担当チャンネルに振り分ける。Socket Mode で動かすので公開 URL は要らない。

### 照合で確認した仕様

| 項目 | 内容 |
|---|---|
| 応答期限 | **3秒（3000ミリ秒）**。過ぎると利用者に `operation_timeout` |
| 推奨 | **重い処理の前に、すぐ `ack()` する** |
| 既定の返し方 | `ephemeral`（送った本人にだけ見える）。`in_channel` でチャンネルに出る |
| Socket Mode | 公開 URL 不要。スラッシュコマンドも WebSocket で届く。アプリレベルトークン（`xapp-`）を使う |
| 受領確認をしなかった場合 | Slack は**再送する**（受領確認が再送の判断に使われる） |
| **Socket Mode のアプリはマーケットプレイスに出せない** | 顧客ごとに個別のアプリとトークンが要る |

### ドキュメントで確かめられなかったこと

- **権限（スコープ）を足したとき、再インストールが要るか**。マニフェストのリファレンスに記述が無い。
  方針書の観察対象なので、実際に試して確かめる

インストールした実物で API も確かめた：`App`・`SocketModeHandler`・`@app.command`、
`process_before_response` の既定は `False`。

## 設計の判断

| 判断 | 選んだもの | 理由 |
|---|---|---|
| LLM | **Gemini（A-1 と同じ）** | 「A-1 の分類結果」と比べられる。プロンプト・モデル・温度0を揃えた |
| 送り方 | **スラッシュコマンド** | 応答期限の超過が利用者の画面に `operation_timeout` として出るので観察しやすい |
| アプリの作り方 | **マニフェストから作る** | 要求する権限がファイルに残る。権限を足すときも差分で説明できる |
| 最初の権限 | **`commands` だけ** | 振り分け通知で `chat:write` が要る段で足し、**再インストール前の挙動を観察する** |
| 設定の検査 | `src/settings.py` | 値を出さずに、空・取り違え・空白の混入・キー名の打ち間違いを見つける（A-6a の反省） |

## 観察対象1：LLM を待ってから応答すると何が起きるか（2026-10-17）

### 素朴な実装は「今日は動いた」

分類が終わってから ack する素朴な実装で、実際に送ると**成功した。ただし受信から 2.80 秒。**
期限の3秒に対して残り 0.2 秒で、しかも Slack の3秒には Slack とこちらの間の通信時間も含まれる。
問い合わせ文が長い、Gemini が少し混んでいる、それだけで超える。**今日は動いたが明日は動かない実装。**

### 観察用に4秒遅らせると

| 時刻 | 起きたこと |
|---|---|
| 0秒 | 問い合わせを受信 |
| **3秒** | **Bolt 自身が「ack が呼ばれなかった」と判断して Slack に失敗を返した** → 利用者の画面に「アプリが応答しなかったため、/inquiry は失敗しました。もう一度試すか…」 |
| 7.4秒 | 分類が終わり、遅れて ack → **遅れて分類結果も表示された** |

同じ問い合わせが2回処理されることは無かった（スラッシュコマンドは Slack から再送されない）。

#### Bolt のログが誤解を招く

```
WARNING handle_inquiry didn't call ack()
WARNING Unhandled request ({'type': None, 'command': '/inquiry'})
INFO    Unsuccessful Bolt execution result (status: 404, body: {"error": "unhandled request"})
```

実際は ack を呼んでいる（遅れただけ）し、処理もされている。ログだけ読むと
「ack を書き忘れた」「コマンド名が合っていない」と疑い、**原因（遅すぎる）に辿り着けない。**

#### 失敗と成功が両方表示される

利用者は「失敗しました。もう一度試してください」を見たあと、遅れて結果を見る。
**言われたとおり再送すると二重に登録される。** 振り分け通知が付けば担当に二重に通知が飛ぶ。

### 対処：受信したらすぐ ack し、分類はそのあとで respond() で送る

同じ4秒の遅延で、ack は**受信から 0.00 秒**、結果は 7.25 秒後に届き、Bolt の警告も消えた。
`respond()` はスラッシュコマンドに付く返信用の URL を使うので、`commands` の権限だけで送れる。
分類が失敗したら「受け付けました」の後に、**失敗したことと次に何をすればよいか**を改めて送る。

## 日本語で太字が効かない（2026-10-17）

`分類：*申請手続き*　緊急度：*低*` と書くと、画面にアスタリスクがそのまま出た。
当初「ack の本文がプレーンテキスト扱いだった」と考え blocks の mrkdwn に変えたが、**同じだった（私の誤った推測）**。

5通りを見比べる観察用の Bot（`tests/probe_format.py`）で確かめた。

| 書き方 | 結果 |
|---|---|
| `*` が全角の「：」・全角スペースに直接くっつく | **✗ 太字にならない** |
| `*` の前後に半角スペース | ✓ |
| `*` の前後にゼロ幅スペース | ✓ |
| 半角コロンと半角スペース | ✓ |
| 行頭から行末まで全体を囲む | ✓ |

**書式記号の前後の文字が原因だった。** 半角スペースを採った。ゼロ幅スペースは見た目が崩れないが、
**見えない文字を本文に埋め込む**ことになり、利用者がコピーした文に紛れ込む（A-6a で見えない全角スペースが設定を壊した）。

## Gemini が HTTP 402 を返した（2026-10-16〜17）

API キーは正しかったが、Google AI Studio が**前払いへの切り替え**を求めて拒否していた（402 = Payment Required）。
ユーザーがクレジットを購入して復旧した。

**A-1 の GAS も同じキーで分類しているので、A-1 の自動分類も止まっていた可能性が高い。**
A-1 の「モデル名が時間で腐る（404）」と同じ型で、**外部の課金体系の変更で、昨日まで動いていた仕組みが壊れる。**

階層（Tier 1）には支出の上限（250 米ドル）と、10分間で 10 米ドルを超えると `429` になる制限がある。
上限が月ごとか累計かはドキュメントに記述が無かった。

## 振り分け通知と、観察対象2（2026-10-17）

分類に応じて担当チャンネルに通知する。対応表は `routing.json`（コードに書かない・チャンネルは ID で指定）。

| 分類 | 通知先 |
|---|---|
| システム障害 | `#inq-system` |
| 申請手続き・備品・設備 | `#inq-general` |
| その他（担当未設定） | `#inq-ops` |

雛形の値 `C00000000` は形としては正しいので、**書き換え忘れを明示的に弾く**
（A-6b のフックの参照先が雛形のまま黙って何もしていなかったのと同じ型）。

### 壊れ方を順に見た

| 段階 | 状態 | Slack の返したエラー |
|---|---|---|
| 1 | マニフェストの権限は `commands` だけ | `missing_scope` |
| 2 | **マニフェストに `chat:write` を足して保存・再インストール前** | **`missing_scope`（必要：`chat:write:bot`／トークンの権限：`commands`）** |
| 3 | 再インストール後 | `not_in_channel` |
| 4 | Bot を3つのチャンネルに招待 | **成功**（`#inq-system` に届いた） |

**観察対象2の答え：マニフェストに権限を足して保存しても、再インストールするまでトークンの権限は増えない。**
マニフェストは「次にインストールするときに求める権限」の宣言にすぎない。

- **足す前と後でエラーが同じ `missing_scope`。** 開発者からは「足したのに直らない」としか見えない。
  Slack の応答に入っている `needed`（必要な権限）と `provided`（トークンが今持つ権限）を記録して区別できるようにした
- **エラーに出る名前（`chat:write:bot`）とマニフェストに書く名前（`chat:write`）が一致しない。**
  エラー文の権限名をそのままマニフェストに貼っても直らない可能性がある
- **再インストールしても Bot トークンの文字列は変わらなかった。** `.env` のまま新しい権限が効いた
- 権限が揃っても、**Bot がチャンネルに招待されていないと `not_in_channel`。** 利用者が必ず踏む

### 自分の誤り：失敗が画面に出ていなかった

段階1で、ログには `missing_scope` が出ているのに、利用者の画面には分類結果しか出なかった。
**Slack は `blocks` があると `text` を画面に表示しない**（`text` は通知用の代替文）。
私は「担当への通知に失敗しました」を `text` にだけ入れており、
**利用者には分類結果しか見えず、担当に届いたと思い込む状態だった。**
失敗の文を `blocks` に入れ、テストで固定した。

### 実際の負荷で3秒を超えていた

段階4の成功時、観察用の遅延なしで **Gemini だけで 3.12 秒**かかった。
素朴な実装のままなら、**実際の負荷だけで期限を超えていた。** 受信してすぐ ack する修正が実運用の条件で効いた。

## 失敗時の通知経路（2026-10-18）

A-1 と同じ考え方（失敗したら予備の宛先に知らせる）で、**分類や通知に失敗したら `#inq-ops` に知らせる。**

| 失敗 | `#inq-ops` に出すもの |
|---|---|
| 分類の失敗 | 原因・送った人・**問い合わせの本文**（手で振り分けられるように） |
| 通知の失敗 | 原因・**直し方**（`missing_scope` なら再インストール、`not_in_channel` なら `/invite` など）・必要な権限とトークンの権限 |
| **`#inq-ops` への通知自体も失敗** | ログに残し、利用者に「運用担当にも連絡できなかった。担当者に直接連絡を」と伝える（最後の手段） |

利用者への文面も、運用担当に知らせられたかで変える。知らせられたら「**もう一度送る必要はありません**」と書く
（観察対象1で見た「もう一度試して」→ 二重登録を避けるため）。

**実機で確認**：Gemini のキーだけを無効な値にして起動し、分類を失敗させた。
`#inq-ops` に「🚨 分類の失敗・原因（HTTP 400）・送った人・本文」が届いた（コネクタでチャンネルを読んで確認）。

## プロセスは生きているのに Bot が死んでいた（2026-10-18）

一晩動かしたままにした Bot に問い合わせを送ると、「アプリが応答しなかったため…失敗しました」と出た。
ログを見ると、**深夜 01:56 から約7時間45分、2,557回**、Slack との接続が「つながる → 直後に `BrokenPipeError` で切れる
→ 10秒後に再接続」を繰り返していた。

```
ERROR slack_bolt.App on_error invoked (... error: BrokenPipeError, message: [Errno 32] Broken pipe)
INFO  slack_bolt.App The connection has been closed
INFO  slack_bolt.App The session seems to be already closed. Reconnecting...
```

- **プロセスは動き続けていた。**「プロセスが生きているか」を見る監視では正常に見える
- 利用者には「アプリが応答しなかった」としか出ない。**Gemini や API の問題に見える**（実際に「API が呼べないのか」と質問が出た）
- **同じプロセスの中での自動再接続では回復しなかった。** プロセスを起動し直すと即座に正常に接続した
- きっかけは夜間のネットワークかスリープの状態変化と考えられるが、確証は無い

**常駐させる場合は、「プロセスが動いているか」ではなく「Slack とつながっているか」を見る仕組みが要る。**
