# 第1部：観測できた事実

## 1. コンテナバインド（実装・検証済み）

`projects/a1-gas/minimal/` および `workflow/`

```bash
clasp create-script --type sheets --title "A1-minimal" --rootDir src
# → Created new document: https://drive.google.com/open?id=...
# → Created new script: https://script.google.com/d/.../edit
```

**スプレッドシート等のドキュメントに従属する。** ドキュメントと一体で動く。

| 項目 | 観測結果 |
|---|---|
| `.clasp.json` | **`parentId` を持つ**（所属先ドキュメントのID） |
| `getActiveSpreadsheet()` | そのドキュメントを返す |
| 必要スコープ | `spreadsheets.currentonly`（**このシートのみ**） |
| 承認画面の文言 | 「このアプリケーションで使用されているスプレッドシートのみ」 |
| 誰のアカウントで動くか | 承認した個人 |
| トリガー | ドキュメントに対して設定（フォーム送信・編集など） |

## 2. スタンドアロン（実装・検証済み）

`projects/a1-gas/standalone/`

```bash
clasp create-script --type standalone --title "A1-standalone" --rootDir src
# → Created new script のみ（ドキュメントは作られない）
```

**独立したファイルとして Drive に置かれる。**

| 項目 | 観測結果 |
|---|---|
| `.clasp.json` | **`parentId` を持たない** |
| `getActiveSpreadsheet()` | **`null`**（「現在の」という概念がない） |
| シートの開き方 | `SpreadsheetApp.openById(id)` |
| 必要スコープ | `spreadsheets`（**全スプレッドシート**） |
| 承認画面の文言 | 「**すべての**スプレッドシートの参照、編集、作成、削除」 |
| 誰のアカウントで動くか | 承認した個人 |

### 決定的な差（実験の主目的）

**処理内容は1文字も違わない。** シートを1行読んでメールを1通送るだけ。
それでも配置を変えるだけで、要求権限が「このシートのみ」から
「利用者の全スプレッドシート」に広がる。

`openById` は「IDを知っていれば任意のシートを開ける」ため、
`currentonly` のように対象を限定する手段がない。

## 3. サービスアカウント（**未検証**・調査ベース）

> **正確に言うと、これは「GAS の配置パターン」ではない。**
> Apps Script のコードは**常にユーザーアカウントの権限で実行される。**
> サービスアカウントとして GAS を動かす仕組みは存在しない。

実態としての選択肢は次の2つ。

### 3-a. GAS からサービスアカウントの資格情報で API を叩く

GAS 自体はユーザー権限で動くが、内部で JWT を作って
サービスアカウントとして Google API を呼ぶ。

- 必要：GCP プロジェクト、サービスアカウント鍵（JSON）
- Workspace のデータにアクセスするには**ドメイン全体の委任**が要る
  （Workspace 管理者の設定が必要）
- **個人 Gmail アカウントでは検証不可**（ドメイン管理者が存在しないため）

### 3-b. 実行基盤を GAS の外に出す

Cloud Functions / Cloud Run などで動かし、サービスアカウントで実行する。
GAS の6分制限もトリガー制約も無くなるが、Workspace との距離は遠くなる。

**このブロックでは未検証。** 個人アカウントでは環境が用意できないため。

## 4. 実行者に関する補足（Webアプリの場合）

Web アプリとしてデプロイする場合、「誰として実行するか」を選べる。

| 設定 | 実行者 |
|---|---|
| 自分（デプロイした人） | 常にデプロイ者の権限。利用者は権限不要 |
| アクセスしているユーザー | 利用者ごとの権限で動く |

**「自分」を選ぶと、デプロイした人が退職した時点で止まる。**
今回は Web アプリを作っていないため未検証。

## 5. 共通して観測されたこと

- 承認画面は**権限を個別に拒否できる**（→ [記録](../../docs/pitfalls/a1-gas-granular-consent.md)）
- 「編集」権限の表示には**「削除」が含まれる**
- 「Google で検証されていません」警告と**開発者のメールアドレス**が表示される

## 6. 引き継ぎに関する調査結果（**調査ベース・実物未検証**）

個人 Gmail では共有ドライブが使えないため、以下は公式ドキュメントの記述に基づく。
Workspace 環境が手に入った時点で実物確認すること。

### 6-1. スクリプトの所有権

**コンテナバインドのスクリプトは、親ファイルの所有者が所有する**（誰が書いたかに関わらず）。
アクセス権も親ファイルの共有設定に従う。

→ **親ファイルの所有権を移せば、スクリプトの所有権も移る。**

スタンドアロンはスクリプト自体が独立したファイルなので、
そのファイルの所有権を直接移すことになる。

### 6-2. 共有ドライブに置いた場合

**共有ドライブ上のファイルは個人ではなくグループが所有する。**
メンバーが抜けても所有権は組織に残る。

コンテナバインドのスクリプトを共有ドライブに置けば、
スクリプトも共有ドライブの共同編集者がアクセスできる。

→ **「退職で所有権が失われる」問題は、共有ドライブで解決できる。**

### 6-3. トリガーは移管できない（**ここが核心**）

**インストーラブルトリガーは、作成した人のアカウントで実行される。**
そして**所有権を移しても、トリガーは移らない。**

同様に、**バージョン付きデプロイの所有権も移管できない。**

→ **ファイルの所有権を移しても、トリガーは元の作成者のアカウントで動き続ける。
　 その人のアカウントが停止されれば、そこで止まる。**

これが「引き継いだつもりで止まる」の正体。
所有権の移管は完了し、ファイルは開ける。コードも残っている。
**それでも動かない。** しかも「引き継ぎ済み」という認識があるため、
原因の候補から外れやすい。

### 6-4. 対処の方向

| 対象 | 対処 |
|---|---|
| ファイル・スクリプトの所有権 | **共有ドライブに置く**（組織所有にする） |
| トリガー | **引き継ぐ人が自分で作り直す。** 移管はできない |
| OAuth 承認 | 引き継ぐ人が自分で承認し直す |
| デプロイ（Webアプリ等） | 移管できない。引き継ぐ人が再デプロイ |

**トリガーの作り直しを手順書に書くだけでは不十分。**
`setup()` のようにコードから登録できる形にしておけば、
引き継ぐ人が関数を1つ実行するだけで済む
（`workflow` の `ensureFormSubmitTrigger_` がこの形になっている）。

### ケース1：今日作ったもの

社内の問い合わせフォーム。回答は1つのスプレッドシートに溜まる。
フォーム送信をきっかけに分類して担当者へ振り分ける。
その組織には情シスの権限審査がある。

```
選ぶパターン：コンテナバインド
決め手：一つのスプレッドシートに留まるため。単一のファイルごとに動作するこの手法が適切であります。
```

### ケース2：複数ファイルの横断集計

部署ごとに5つのスプレッドシートがあり、それぞれ担当者が更新している。
月末にすべてを集計して1つのレポートシートにまとめたい。
ファイルは今後増える可能性がある。

```
選ぶパターン：スタンドアロン
決め手：複数ファイルを横断して動作するためです。
```

### ケース3：将来の拡張が読めない

いまは営業部の1シートだけ。ただし「うまくいったら他部署にも広げたい」と
言われている。時期も範囲も未定。

```
選ぶパターン：コンテナバインド
決め手：確実に発生する費用のみを会社に請求できるため、承認が通りやすい。「うまくいったら他部署に広げたい」などの拡張意思は不確実なものであり、費用の確定などもできません。コンテナバインドであれば一つの部署で動かす費用を確定でき、本当にうまく行けば他部署で動かした際の費用も計りやすいので。
（この設問の狙い：未確定の要件にどこまで先回りするか。
　先回りしすぎると権限が広がり、しなさすぎると作り直しになる）
```

### ケース4：ここは判断材料が足りないはず

経理部から「請求書の処理を自動化したい」と相談された。
それ以上の情報はまだない。

```
配置を決めるために、最低限あと何を聞く必要があるか：判断材料が不足しているので、どう言う要件なのか、誰が使用するのか、何人使用するのか、対象のファイルはいくつあるのかを聞きます。
```

## Q3. 選択を誤ると何が起きるか

パターンごとに、最悪のケースを書く。

```
コンテナバインドを選んで失敗する場合： 親ドキュメントを削除してしまうと、GASのスクリプトも削除されてしまう。親ファイルの管理者が退職した際に、アカウントが削除されると、全体のフローが削除されてしまう

スタンドアロンを選んで失敗する場合： 対象を限定する手段がないが故に、全てのシートの権限を付与してしまう
```

## Q4. 顧客に説明するとしたら何と言うか

技術用語を使わずに、3行で。

コンテナバインド
```
単一のスプレッドシートに埋め込む形。
そのファイル専用になりますが、必要な権限は「そのファイルだけ」になります。
ファイルを削除するとその自動化も同時に消えてしまいます。
```
スタンドアロン
```
独立したプログラムとしての管理。
複数のファイルを横断できますが、全てのスプレッドシートの参照・編集・削除などの権限を求められます。
貴社の情シス部や規定などがブロッカーとなり、承認が進まないことがあります。
```

## Q5. 「作った人がいなくなったとき」への対処

今回作ったものは、あなたのアカウントで動いている。
これを他人の組織に渡すとしたら、何をしておく必要があるか。

```
ファイルやスクリプトの所有権は共有ドライブとして保管すれば問題ありません。インストーラブルトリガーは移行できないため、設定をドキュメントとして共有しておく必要があります。認証やAPIキーの設定などは手順をドキュメントに残し、誰でも再実行できる形にする必要があり、その支援が必要です。
```
