# A-4：Python バッチ（Excel＋ファイル処理）

支店別に届く月次の問い合わせ集計ファイルを結合し、書式付きの報告帳票を出力する。
あわせて支店別 PDF の結合と、命名規則に沿ったリネームを行う。

題材は Phase A と同じ架空企業の問い合わせ業務。

---

## 実行方法

```bash
cd projects/a4-python-batch
uv sync --extra dev
uv run python src/generate_testdata.py   # テストデータを生成（初回のみ）
uv run python src/main.py                # バッチ実行
uv run pytest tests/ -v                  # テスト
```

対象月を変える場合：`uv run python src/main.py --month 2026-09`

## 構成


## 出力

|---|---|
| `normalized.csv` | **正規化後の全明細。元ファイルと突き合わせて検証するためのもの** |
| `load_report.txt` | 読み込み内訳（何行除去したか、警告） |
| `report_YYYY-MM.xlsx` | 書式付き帳票。2枚目に読み込み内訳のシート |

**正規化後の明細を必ずファイルに残す**設計にしている。

## 観察結果

### 素朴な実装で何が起きたか

対策を入れずに `pd.read_excel` / `pd.read_csv` で読んだ結果（`src/naive_aggregate.py`）。

**cp932 の CSV だけがエラーになり、残り4つは黙って通った。**

| 現象 | 気づけるか |
|---|---|
| cp932 → `UnicodeDecodeError` | **気づける**（例外で止まる） |
| 結合セルのタイトルをヘッダと誤認 → 支店ごとに違う列ができ、列が横に増える | 気づきにくい |
| 日付が `'2026/08/11'` と `'2026-08-02 00:00:00'` で混在 | 気づきにくい |
| 件数に全角 `１７` が混入 | 気づきにくい |
| 「大阪」と「大 阪」が別支店として集計される | **ほぼ気づけない** |
| ヘッダ行・空行がデータ行として混入（`支店 4件`） | 気づきにくい |

80行という「それらしい件数」が出て、処理は正常終了する。
Phase A で27件中の約半数を占めた「**成功したように見えて中身が違う**」型と同じ。

### 数式セルの読み込み挙動

同じセル（合計行）を3つの方法で読んだ結果。**実際の合計は 176。**

| 読み方 | 返る値 |
|---|---|
| `load_workbook()`（既定） | `'=SUM(D4:D18)'` — 数式の文字列 |
| `load_workbook(data_only=True)` | **`None`** |
| `pd.read_excel()` | `NaN`（内部で `data_only` 相当） |

**どの方法でも 176 は取れない。**

xlsx は「数式」と「最後に計算された値」を別々に持つが、
openpyxl が書いたファイルには計算結果が入っていない。Excel が計算してキャッシュするため。

実務での現れ方：

| ファイルの出どころ | `data_only=True` の結果 |
|---|---|
| 人が Excel で作って保存した | 値が入っている（動く） |
| システムが自動生成した | `None`（動かない） |
| 人が作ったが、数式を変えてから保存していない | **古い値**（もっと悪い） |

3番目が最悪で、エラーも出ずに古い値を集計に使う。
開発中は手元の Excel ファイルで確認するので気づかず、本番で自動出力を食わせた瞬間に壊れる。

**対処：合計行を読まない。明細から自分で計算する。**

## CI で見つかった不具合：画面出力の文字コード

macOS で完成させたあと CI に載せたところ、**windows-latest だけが failure** になった。
テスト以前、テストデータ生成の `print` で落ちていた。

```
print(f"生成完了: ... → {OUT_DIR}")
UnicodeEncodeError: 'charmap' codec can't encode characters in position 0-3
```

Windows の Python は **stdout のエンコーディングを OS のロケールから決める**。
印字している非ASCII文字51種の扱いは次のように分かれる。

| 環境 | stdout の既定 | 出せない文字 |
|---|---|---|
| macOS / Linux | UTF-8 | 0 / 51 |
| 日本語 Windows のコンソール | cp932 | **0 / 51（動いてしまう）** |
| 英語ロケールの Windows / CI | cp1252 | **51 / 51** |

**顧客が日本語 Windows で手動実行すると再現しない。**
壊れるのはタスクスケジューラ経由、出力のリダイレクト、英語ロケールの端末。
つまり「手で動かすと動くのに、自動化した途端に落ちる」形で出る。

対処は `src/console.py` の `force_utf8_stdio()` を各エントリポイント冒頭で呼ぶこと。
**環境変数（`PYTHONUTF8`）にしなかった理由**は、それがワークフローや起動スクリプトの
設定でしかなく、配布先には付いていかないため。CI だけが緑になって実害が残る。

修正すると CI が緑になり、将来この呼び出しが抜けても気づけなくなるので、
`PYTHONIOENCODING: cp1252` を強制するステップを**全 OS に**追加した
（Windows ランナーのロケール設定に検知を依存させないため）。

### 2回目の失敗：検証側のコードにも同じ不具合があった

修正後も windows-latest だけ failure。ただし本体（生成・pytest・cp1252 での通し実行）は
すべて通過し、落ちたのは**ワークフローに直書きしていた検証用のワンライナー**だった。
`TKY_202608_報告書.pdf` を印字していたため。

**ワンライナーは `console.py` を import しないので、対処の網から漏れる。**
`src/check_output.py` に切り出して同じ入口を通した。

副産物として、従来のワンライナーが見逃していた異常を検出できるようになった。
