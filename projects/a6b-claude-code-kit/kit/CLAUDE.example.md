# 週次レポート生成ツール 運用ルール

> **これは記入例。** `CLAUDE.md`（雛形）を埋めるときの参考にする。
> 架空のプロジェクト（問い合わせログから週次レポートを作る社内ツール）を題材にしている。
> **粒度の参考として見る。** 内容をそのまま使わない。

---

## 1. このリポジトリは何か

サポート窓口の問い合わせログ（CSV）を読み、週次レポート（Excel）を生成するツール。
毎週月曜の朝、カスタマーサポート部のリーダー3名が受け取る。

**このリポジトリでは本番データを扱わない。** 検証には `fixtures/` の匿名化済みデータを使う。
本番の集計はデータ基盤チームが別環境で実行する。

## 2. 説明の粒度

読み手はデータ分析の担当者。Python は日常的に書くが、**Excel の書式制御と
Windows 環境の扱いには慣れていない。**

**説明不要：** pandas の基本操作、統計の一般論、git の使い方

**優先して示すもの：**
- openpyxl の書式制御で詰まりやすい箇所（結合セル、数式の読み取り）
- Windows 環境で挙動が変わる箇所（文字コード、パス区切り、改行）
- 受け取る側（非技術者）が誤読しそうな出力の見せ方

**不慣れな領域（丁寧に扱う）：** Excel の書式、タスクスケジューラ、文字コード

## 3. 進め方

- 実装前に計画を共有し、確認を得る
- 小さく反復可能な単位で進める
- **集計ロジックの変更は、変更前後の数値を並べて提示する。**
  「正しくなった」ではなく「どの行がどう変わったか」を示す
- レポートの項目を増やす要望は、**受け取る3名に確認してから**着手する

## 4. コーディング

- Python 3.12 / `uv` で仮想環境管理 / PEP 8 / 型注釈を付ける
- コメントは日本語。**「なぜそう書くか」を残す**
- 新機能にはユニットテストを含める（カバレッジ 80% 以上）
- エラーは握り潰さない。`try/except` で捕まえた場合は**必ずログに出す**
- ruff（行長 100）を使う
- **ファイル入出力では `encoding` を必ず明示する。** 既定に任せると環境で変わる
- **画面出力も文字コードを固定する。** Windows の自動実行で落ちた経験があるため

## 5. ディレクトリ

```
src/            集計と出力のコード
  loader.py     CSV の読み込みと正規化
  report.py     Excel の生成
  main.py       実行の入口
tests/          ユニットテスト
fixtures/       匿名化済みのテストデータ（コミットする）
input/          実行時の入力（コミットしない）
output/         生成物（コミットしない）
docs/
  runbook.md    運用手順（担当者向け）
```

## 6. セキュリティ

- 認証情報・APIキー・実データを**コミットしない**。`.gitignore` を確認してから `git add` する
- シークレットは環境変数で管理し、`.env.example` を用意する
- **ログに問い合わせ本文を出力しない。** 個人を特定できる記述が含まれる
- `fixtures/` のデータは匿名化済み。**本番データを置き換えて使わない**
- レポートの配布は社内ストレージ経由。**メール添付にしない**（誤送信の経路になる）

## 7. やってはいけないこと

- **`input/` の元ファイルを上書き・削除する処理を書くこと。** 読み取り専用で扱う
- データ基盤チームの本番 DB へ直接接続すること
- main ブランチへの直接 push
- 依存パッケージの追加を相談なしに行うこと（配布先の環境に影響する）
- **集計結果を手で修正してレポートに入れること。** 直すのはコード側
