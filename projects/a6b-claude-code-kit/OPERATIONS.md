# 運用ルール

Claude Code をチームで使うときの取り決め。**導入手順とは別に、合意が必要な部分。**

---

## 1. 秘密情報の扱い

### 設定で防ぐ

`.claude/settings.json` の `deny` に入れている。**これが第一の防壁。**

```
Read(**/.env)      Read(**/*.pem)      Read(**/*token*)
Read(**/secrets/**)  Read(**/.ssh/**)    Read(**/*.key)
```

### 設定だけでは防げないこと

| 経路 | 防げるか | 対処 |
|---|---|---|
| ファイルを読ませる | **防げる**（deny） | — |
| **チャットに貼り付ける** | **防げない** | 貼らない。これは人の運用で守る |
| コードに直書きされたキーを読む | **防げない**（ファイル名が安全なため） | `/commit-check` で差分の中身を見る |
| ログ・エラー出力に出る | **防げない** | ログにキーを出さない実装にする |

**最も多い漏洩経路はチャットへの貼り付け。** 設定では止められない。

- エラーメッセージを貼るときは、**トークン・接続文字列を伏せてから貼る**
- 「とりあえず全部貼る」をやらない
- 顧客データ・個人情報は貼らない。**題材にする場合は匿名化する**

### コミット前の確認

`/commit-check` を使う。ファイル名だけでなく**差分の中身**も見る。

### キーが漏れたときの手順

**消しても履歴に残る。** `git commit --amend` や `git rm` では解決しない。

1. **先にキーを無効化する**（ローテーション）。履歴の削除より優先する
2. push 済みなら、GitHub 等のリモートからも消す必要がある
3. 履歴の書き換え（`git filter-repo` 等）は、他のメンバーのクローンに影響する。**相談してから行う**

**順番が重要。** 履歴を消してからキーを無効化すると、その間に使われる。

## 2. 生成コードのレビュー方針

### レビューを省略してよいもの

- 使い捨てのスクリプト（1回実行して捨てるもの）
- テストコード（**ただしテストが通ることを確認する**）
- 書式の修正のみ（フォーマッタの適用）

### 必ず人がレビューするもの

| 対象 | 見る理由 |
|---|---|
| **外部にデータを送る処理** | 送信先・送信内容が意図と合っているか |
| **認証・認可** | 誤りが即座に穴になる |
| **削除・更新の処理** | 元に戻せない操作が含まれていないか |
| **お金・数量の計算** | 計算そのものは正しくても、前提が違うことがある |
| **設定ファイルの変更** | 他人の環境で何が起きるか |
| **依存パッケージの追加** | 何が増えたか、ライセンス、サイズ |

### 「動いた」をレビューの根拠にしない

**これが最も重要な項目。** 動いたことと正しいことは別。

実例として、Claude Code を使った検証で次が起きている。

- 終了コード0で何もしていなかった（`clasp push` が「Skipping push.」で終了）
- 例外なく0件を返し、正常終了した（JS 描画ページの静的取得）
- **件数は正常なまま、中身が全件空だった**（セレクタの階層が1段変わった）
- 権限の承認は通るのに何も起きなかった（実行対象の関数が別だった）

いずれもエラーが出ていない。**「エラーが出ていない」は確認したことにならない。**

レビューでは次を聞く。

```
□ 出力の中身を1件でも目で見たか（件数だけを見ていないか）
□ 失敗したときにどうなるか（例外が出るか、黙って続行するか）
□ 他人の環境で違う結果になる箇所はどこか
```

### レビューの記録

**誰がレビューしたかを残す。** PR の承認で足りる。
「Claude が書いたので誰も読んでいない」状態を作らない。

---

## 3. CLAUDE.md の更新

- **同じ説明を2回した時点で CLAUDE.md に書く。** これが更新の合図
- 「やってはいけないこと」は**実際に起きてから**書く。想像で増やさない
- 長くなったら削る。読まれない長さになると、全体が読まれなくなる

---

## 4. 設定変更の合意

| 変更 | 誰が決めるか |
|---|---|
| `deny` を**緩める** | **チームで合意する。** 1人の判断で緩めない |
| `allow` を増やす | 提案 → レビュー（PR と同じ扱い） |
| `ask` → `allow` に移す | 提案 → レビュー |
| 自分だけの上書き | 各自（`.claude/settings.local.json`） |
| フックの追加 | 提案 → レビュー（**他人の環境で壊れるため**） |

`.claude/settings.json` は**コードと同じ扱い**にする。差分を見てからマージする。

---

## 5. 困ったときの切り分け

Claude Code 固有の問題で時間を溶かさないための順序。

1. **設定が読まれているかを確認する。** 権限の確認が出ない・スキルが候補に出ないなら、
   配置が間違っている可能性が高い（`SETUP.md` の完了判定を再実行する）
2. **仕様が変わった可能性を疑う。** `docs-verification.md` の照合日を見る。
   3か月以上経っていたら公式ドキュメントを引き直す
3. **公式ドキュメントのドメイン。** `docs.claude.com/en/docs/claude-code/...` は
   `code.claude.com/docs/en/...` へリダイレクトする。古いリンクを使い続けない

### 聞く前に用意すること

- `claude --version` の出力
- 実際に打ったコマンドと、返ってきた表示
- `.claude/settings.json` の該当部分（**キーは伏せる**）
