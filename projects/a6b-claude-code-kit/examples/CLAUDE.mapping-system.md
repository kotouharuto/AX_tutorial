# 科目突合マッピングシステム 運用ルール

> **記入例（壁打ちで作成）。** 雛形 `kit/CLAUDE.md` を埋めるときの参考にする。
> 架空の案件だが、業務の前提は実務に基づいている。

---

## 1. このリポジトリは何か

顧客から受領した出荷・入荷データ（xlsx）を読み、
自社製品「出荷・入荷管理システム」のマスタに突合するためのマッピングシステム。

導入時のデータ移行で使う。**顧客ごとに数回動かすもので、常時稼働しない。**

### 突合の対象

| 対象 | 突合の性質 |
|---|---|
| 品目 | どのマスタに当たるか |
| 取引先 | どのマスタに当たるか |
| 倉庫 | どのマスタに当たるか |
| **単位** | **どのマスタに当たるか＋換算係数**（後述。他と性質が違う） |

### 処理の流れ

```
顧客から xlsx を受領（エンジニアが受け取る）
  → エンジニアが実行：読み込み・正規化・突合
  → 確認用ファイルを導入担当に渡す
  → 導入担当が確定欄に記入
  → エンジニアが確定結果を規則に取り込み、再実行
  → 顧客が承認
  → 製品のマスタに取り込む形式で出力
```

**実行するのはエンジニアのみ。** 導入担当はファイルを見て判断・記入するだけで、
このツールを動かさない。

### このリポジトリでやらないこと

- 製品本体（出荷・入荷管理システム）の改修
- 顧客環境での実行（**自社で受領して処理する**）
- 導入担当の PC での実行（**配布しない**）
- 常時稼働・定期実行

## 2. 説明の粒度

読み手は自社のエンジニア。Python は日常的に書く。

**説明不要：** pandas の基本操作、型ヒントの書き方、git の使い方

**優先して示すもの：**
- **突合の判断が分かれる箇所**と、どちらを選ぶと何を失うか
- 顧客の xlsx に起きる汚れと、その検出方法
- **導入担当が受け取るファイル**に何を出すか（非エンジニアが誤読しないか）

**不慣れな領域（丁寧に扱う）：** Excel の書式制御、単位換算の業務知識

## 3. 進め方

- 実装前に計画を共有し、確認を得る
- 小さく反復可能な単位で進める

### 突合ロジックを変更するときの手順

**変更前後の突合結果を並べて提示する。** 「精度が上がった」では判断できない。

```
変更前：一致 820 / 候補あり 140 / 不一致 40
変更後：一致 865 / 候補あり 100 / 不一致 35
→ 変化した 45 件の内訳（どの行が、どのルールで、何に変わったか）
```

**件数だけを見せない。** 変化した行の実物を出す。
件数が改善しても、**以前正しく突合できていた行が壊れている**ことがある。

### 汚れを先に観察する

新しい顧客の xlsx を受領したら、**正規化を書く前に何が入っているかを見る。**
想定していない汚れがあるのが普通で、綺麗なデータ前提のコードは現場で止まる。

## 4. コーディング

- Python 3.12 / `uv` で仮想環境管理 / PEP 8 / 型注釈を付ける
- コメントは日本語。**「なぜそう書くか」を残す**
- 新機能にはユニットテストを含める（カバレッジ 80% 以上）
- ruff（行長 100）

### 入出力

- **ファイル入出力では `encoding` を必ず明示する。** 既定に任せると環境で変わる
- 顧客の CSV は `utf-8-sig` → `cp932` → `utf-8` の順で試し、**全部失敗したら例外にする**。
  推測で読み進めない
- xlsx の読み込みで `data_only` に頼らない。**数式セルは実際の値が取れない**
  （`data_only=False` なら数式文字列、`True` なら `None`。
  人が Excel で保存したファイルでは動き、自動生成では動かない）

### 突合の実装

- **確度を必ず返す。** 「一致した／しなかった」の2値にしない
- **黙って1件に決めない。** 候補が複数あるなら候補のまま返し、人に出す
- 正規化（NFKC・空白除去・大文字小文字）は**比較時のみ**に適用し、
  **元の値を保持する。** 出力に正規化後の値を混ぜない
- **対象（品目・取引先・倉庫・単位）ごとに規則を差し替えられる構造にする。**
  1つの突合関数に分岐を積み上げない
- マッピング規則は**コードに埋め込まない**（`rules/` に置く）

### 単位は換算係数まで確定する

単位だけは「どのマスタに当たるか」で終わらない。
**「ケース」が12個か24個かは名前から分からない。**
突合が合っていても係数を間違えると、数量がそのままずれて在庫が狂う。

- **係数を名前から推測しない。** 「ケース」「箱」「CS」に既定の係数を当てない
- 係数が未確定の単位を含む行は、**数量を出力しない**（未確定として導入担当に出す）
- 同じ名前の単位でも、**品目ごとに係数が違う**ことを前提にする
  （ボールペンの1箱と、コピー用紙の1箱は入数が違う）

### エラー処理

- エラーは握り潰さない。`try/except` で捕まえた場合は**必ずログに出す**
- **0件・急減を成功として扱わない。** 突合結果が0件なら異常として止める
- **件数が正常でも中身が空の場合を検出する。** 必須項目の空率を見る

## 5. ディレクトリ

```
src/
  loader.py       xlsx/CSV の読み込みと正規化
  master.py       自社マスタの読み込み
  matchers/       突合（対象ごとに分ける）
    item.py
    partner.py
    warehouse.py
    unit.py       換算係数を伴う
  review.py       確認用ファイルの出力と、確定結果の読み込み
  exporter.py     製品取り込み形式での出力
  main.py         実行の入口
rules/            マッピング規則（顧客ごと。顧客データを含まない）
fixtures/         匿名化済みのテストデータ（コミットする）
input/            受領した xlsx（コミットしない・期間後に削除）
output/           突合結果・出力（コミットしない・期間後に削除）
audit/            監査記録（コミットしない・長期保存。顧客データを含まない）
docs/
  runbook.md      エンジニア向けの実行手順
  review-guide.md 導入担当向けの確認ファイルの見方
```

## 6. 突合結果の確定と記録

**最終判断は自社の導入担当が行い、顧客が承認する。** 自動で確定しない。

### 導入担当との往復

導入担当はツールを動かさない。**ファイルで往復する。**

```
エンジニア → review_<顧客>_<日時>.xlsx → 導入担当
              （候補・確度・確定欄）
導入担当   → 確定欄に記入して返す
              （マスタIDを選ぶ／「新規」／「対象外」）
エンジニア → 確定欄を読み込み、rules/<顧客>.yaml に反映 → 再実行
```

**確定結果を規則に取り込む経路が必須。** これが無いと、再実行のたびに
導入担当が同じ行を判断し直すことになる。
確定済みの行は次回「手動指定」の規則で一致させ、**二度聞かない。**

### 確定欄の検査

導入担当の記入を**そのまま信用しない。** 読み込み時に検査する。

- 記入されたマスタIDが**実在するか**
- 1つの顧客コードに**複数のマスタIDが記入されていないか**
- 単位の行に**換算係数が記入されているか**

問題があれば、**どの行の何が問題かを示して差し戻す。** 黙って飛ばさない。

### 導入担当に渡すファイルの条件

- **Excel で開けて、確定欄に記入できる形**にする
- 確度は数値だけでなく**「確実／要確認／候補なし」の区分**でも出す
  （非エンジニアに 0.73 と 0.68 の差は判断できない）
- 確定済みの行と未確定の行を**見た目で区別できる**ようにする

### 顧客の承認

**承認した版が特定できるようにする。** 規則ファイルのハッシュか版番号を出力に含める。
「承認後に規則が変わっていた」が起きると、顧客との合意が崩れる。

## 7. 受領データの保管と監査記録

### 保管期間

**期間は契約で定める**（目安：検収完了後30日以内に削除）。
期間が契約で決まっていない案件は、**受領前にエンジニアと導入担当で確認する。**

削除の対象：`input/`、`output/`、確認用ファイル、**顧客ごとのハッシュ鍵**（後述）。

### 監査記録は顧客データを含めずに長期保存する

誤突合は顧客の在庫データを壊すため、**後から「なぜこう突合したか」を説明できる必要がある。**
一方、受領データは期間後に削除する。この2つを両立させるため、記録を2層に分ける。

| 層 | 中身 | 保存期間 |
|---|---|---|
| 出力（`output/`） | **元の値**・突合先・規則・確度・確定者 | **受領データと同じ**（期間後に削除） |
| 監査記録（`audit/`） | **元の値のハッシュ**・突合先のマスタID・**規則ID**・確度・確定者・日時 | 長期 |

**監査記録に元の値を入れない。** 品目名や取引先名は顧客データそのもので、
受領データを削除しても監査記録に残っていれば削除したことにならない。

### ハッシュは顧客ごとの鍵で作る

**品目名を単純にハッシュ化しても匿名にならない。**
「ボールペン 黒」のような値は候補が限られるため、総当たりで元に戻せる。

- 顧客ごとに鍵を作り、**鍵付きハッシュ（HMAC）**にする
- 鍵は受領データと同じ扱いにし、**期間後に一緒に削除する**
- 削除後、ハッシュは元の値と結び付けられなくなる。
  **規則ID とマスタID は残る**ので、「どの規則で何に突合したか」は説明できる

## 8. セキュリティ

- 認証情報・APIキー・**顧客の実データ**をコミットしない。
  `.gitignore` を確認してから `git add` する
- シークレット（ハッシュ鍵を含む）は環境変数で管理し、`.env.example` を用意する
- **顧客の実データを開発・検証環境に持ち込まない。** 検証は `fixtures/` の
  匿名化済みデータで行う
- **ログに顧客の品目名・取引先名を出力しない。** 件数とマスタIDのみにする
- 確認用ファイルの受け渡しは社内ストレージ経由。**メール添付にしない**

### 匿名化データで検証することの限界

**本番で初めて出る汚れを踏む危険が残る。**
そのため `fixtures/` には**意図的に汚れを仕込み、一覧で明記する。**
意図した汚れと、生成時の事故を区別できるようにするため。

```
結合セル / 多段ヘッダ / 日付の型混在（文字列と日付が混在）
全角数字 / 半角カナ / 全角スペース混入（「大 阪」）
途中の空行 / 合計行の混入 / 数式セル / cp932 の CSV
同じ単位名で品目ごとに入数が違う（「箱」が 10個 と 500枚）
```

## 9. やってはいけないこと

- **`input/` の元ファイルを上書き・削除する処理を書くこと。** 読み取り専用で扱う
  （期間後の削除は手順に従って人が行う）
- **確度が低い突合を自動確定すること。** 候補のまま人に出す
- **単位の換算係数を名前から推測すること**
- **突合結果を手で修正して出力に入れること。** 直すのは規則ファイル側
- **監査記録に元の値を書き込むこと**
- 顧客の実データを `fixtures/` に置くこと
- 製品の本番マスタへ直接書き込むこと（出力は取り込み用ファイルまで）
- main ブランチへの直接 push
- 依存パッケージの追加を相談なしに行うこと
