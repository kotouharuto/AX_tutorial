# チーム向け説明資料（30分）

**想定**：Claude Code を使い始めるチーム 3〜10人。全員が技術者でなくてもよい。
**形式**：この資料を画面に出して話す。実演を2回挟む。

> 進め方の目安：説明 20分 / 実演 5分 / 質疑 5分。
> **実演を飛ばさない。** 口頭の説明だけでは、何が自動で起きるかが伝わらない。

---

## 0. この30分で伝えること（1分）

1. 設定が何をしているか（**勝手に危ないことをしない仕組み**）
2. どこに何を書くか（CLAUDE.md・スキル・権限）
3. 守ってほしい2つのこと（**秘密情報を貼らない / 動いたをレビューの根拠にしない**）

導入手順そのものは `SETUP.md` にある。ここでは**なぜそうするか**を話す。

---

## 1. 設定は3層に分かれている（4分）

| 層 | ファイル | 誰のもの | コミット |
|---|---|---|---|
| 管理者 | 組織が配る | 会社 | — |
| **チーム共有** | **`.claude/settings.json`** | **全員** | **する** |
| 個人 | `.claude/settings.local.json` | 自分だけ | しない |

上の層が優先される。**チーム共有の設定を自分用に変えたいときは、個人の層に書く。**
共有設定を直接書き換えない（他の人に影響する）。

### 話すときの要点

「自分の環境だけ変えたい」と「全員の設定を変えたい」を**最初に区別させる**。
ここを混同すると、共有設定が各自の好みで書き換えられていく。

---

## 2. 権限設定が何をしているか（6分）

3種類ある。

| 分類 | 挙動 | 入れているもの |
|---|---|---|
| `allow` | 確認なしで実行 | 読み取り、`ls`、`cat`、`git status` / `log` / `diff` |
| `ask` | **毎回確認する** | `rm`、`mv`、`curl`、`git commit` / `push` / `merge` |
| `deny` | **実行させない** | `.env` や鍵の読み取り、`sudo`、`rm -rf`、`ssh` |

### 設計の考え方

- **元に戻せる操作は `allow`。** 読み取りと `git` の参照系
- **元に戻せない・外に出る操作は `ask`。** 削除、移動、送信、push
- **取り返しがつかない・漏れると困るものは `deny`**

### 実演①（ここで画面を見せる）

```
「.env の中身を見せて」と依頼する  → 拒否される
「git push して」と依頼する        → 確認を求められる
```

**拒否と確認の違いを目で見せる。** 口頭だと「全部確認が出る」と誤解される。

### 注意点（質問が出る箇所）

`defaultMode` で「全部自動承認」にする設定があるが、
**チーム共有のファイルに書いても効かない**（公式仕様）。
各自のユーザー設定でのみ有効。**共有設定に書いて「効かない」と悩まないこと。**

## 3. CLAUDE.md は何のためにあるか（5分）

**毎回同じ説明をしないための場所。**

```
このリポジトリは何か / 読み手の前提 / 進め方 / コーディング規約
ディレクトリ構成 / セキュリティ / やってはいけないこと
```

### 更新の合図

**同じ説明を2回した時点で書く。** これが唯一のルール。

- 想像で増やさない。**実際に起きたことだけ書く**
- 長くなったら削る。**読まれない長さになると全体が読まれなくなる**
- 「やってはいけないこと」は、暗黙の了解を明文化する欄。
  **新しく入った人には伝わらないものを書く**

## 4. スキル：繰り返す作業を登録する（6分）

`.claude/skills/<名前>/SKILL.md` に手順を書くと `/<名前>` で呼べる。

キットに2つ入っている。

| スキル | 何をするか |
|---|---|
| `/commit-check` | コミット前に差分を見て、秘密情報と生成物の混入を検出する |
| `/explain-change` | 変更内容を、コードを読めない人向けに言葉にする |

### 実演②（ここで画面を見せる）

```
適当なファイルを編集して git add し、/commit-check を実行する
```

**「何を確認したか」が出力されることを見せる。**
「問題ありません」だけを返す作りにしていないのが要点。

### 自分で作るとき

```
.claude/skills/<名前>/SKILL.md
---
description: 何をするか（Claude がこれを見て使うか判断する）
---
手順を書く
```

- **変更はセッション中に反映される**（再起動不要）
- 補助ファイル（`reference.md`、`scripts/`）を同じディレクトリに置ける
- 古い形式（`.claude/commands/*.md`）も動くが、**新規はスキルで作る**

## 5. 守ってほしい2つのこと（6分）

### ① 秘密情報をチャットに貼らない

設定で防げるのは**ファイルの読み取りだけ**。

| 経路 | 設定で防げるか |
|---|---|
| ファイルを読ませる | 防げる |
| **チャットに貼り付ける** | **防げない** |
| コードに直書きされたキー | 防げない |

**最も多い漏洩経路は貼り付け。** エラーを貼るときはトークン・接続文字列を伏せる。

漏らしてしまったら、**先にキーを無効化する。** 履歴の削除より優先。
消しても履歴とリモートに残るため、順番を逆にするとその間に使われる。

### ② 「動いた」をレビューの根拠にしない

実際に起きた例。**どれもエラーが出ていない。**

- 終了コード0で、**何もしていなかった**
- 例外なく**0件**を返して正常終了した
- **件数は正常なまま、中身が全件空**だった
- 権限の承認は通るのに、**何も起きなかった**

レビューで聞くこと。

```
□ 出力の中身を1件でも目で見たか（件数だけを見ていないか）
□ 失敗したときにどうなるか（例外が出るか、黙って続行するか）
□ 他人の環境で違う結果になる箇所はどこか
```

### 必ず人が見るもの

外部にデータを送る処理 / 認証・認可 / 削除・更新 / お金と数量の計算 /
設定ファイルの変更 / 依存パッケージの追加

---

## 6. 質疑（5分）

### よく出る質問への答え

**「全部自動で承認させたい」**
→ 各自のユーザー設定で可能。ただし `deny` を緩める判断は**チームの合意**が必要。
共有設定に書いても効かない。

**「確認が多くて煩わしい」**
→ `ask` に入っているものを `allow` に移す提案をしてよい。
**PR と同じ扱い**でレビューする。個人の環境だけなら `settings.local.json`。

**「どこまで任せていいか」**
→ 元に戻せるかで判断する。戻せない操作は人が確認する。

**「設定どおりに動かない」**
→ 配置の間違いか、仕様変更。`SETUP.md` の完了判定を再実行し、
`docs-verification.md` の照合日を見る。3か月以上経っていたら公式ドキュメントを引き直す。
