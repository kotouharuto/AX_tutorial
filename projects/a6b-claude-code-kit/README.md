## 設計の判断

### 丸ごとコピーではなく汎用化した雛形にした

元にしたのは作成者自身の設定だが、**そのままパッケージ化していない。**

- 業務に関わるプラグイン・マーケットプレイスの設定は**除いた**
- `model` と `effortLevel` は**入れていない**（各自の契約・好みで決まる）
- **フックは入れていない**（後述）
- 権限設定は個人のパスを含まない汎用パターンのみで構成した

### 雛形とは別に記入例を用意した

雛形（`CLAUDE.md`）は項目名しかないため、**何を書けばよいかは分かっても
どこまで具体的に書くかが分からない。**

さらに、**導入手順の検証をするときは埋める中身が存在しない**
（テスト用の空リポジトリに背景がない）。
これに気づかず「CLAUDE.md を埋める（10分）」という工程を置いていたため、
**原理的に完了できない手順になっていた。**

→ `kit/CLAUDE.example.md` に、架空のプロジェクトで全項目を埋めた例を置いた。

- 検証時：`cp "$KIT/CLAUDE.example.md" CLAUDE.md` で中身を考える工程を飛ばす
- 実運用時：粒度の基準として読んでから雛形を埋める

`check_kit.py` で「雛形には `<>` が残っている」「記入例には残っていない」を
両方検査している。記入例に空欄が残ると、基準として機能しなくなるため。

### フックを入れていない

他人の環境で壊れやすい。元の設定を調べた結果、**実際に2件が壊れていた。**

| 症状 | 原因 |
|---|---|
| PreToolUse が何もしていない | 参照先が `/path/to/check-command.sh`（**雛形のまま**で存在しない） |
| PostToolUse が将来失敗する | `prettier` が未インストール。**`.ts`/`.js` を編集するまで発火しない** |

1件目は公式仕様と関係している。**フックのスクリプトが実行できない場合、
フックは失敗するがツールの実行は止まらない。**
つまり「設定したのに何も起きていない」状態になり、気づけない。

2件目は「入れた直後は正常に見えて、後から壊れる」型。
このリポジトリは Python と Markdown が中心なので、対象の拡張子を触らず**一度も発火していなかった**。

→ フックの追加手順と注意点は `SETUP.md` の末尾に書き、**雛形には含めない。**

### MCP は公開サーバを例にした

方針書では「A-6a を例に」とあるが、A-6a（自作 MCP サーバ）が未着手のため、
**既に使っている公開サーバ（context7）を実例にした。**
A-6a 完了後に1節追加すれば差し替えられる。

API キーは `${CONTEXT7_API_KEY}` の形で環境変数参照にしてある。
`.mcp.json` はコミットするファイルなので**キーを直書きしない。**

### コマンドではなくスキル形式にした

公式ドキュメントに「Custom commands have been merged into skills.」とある。
既存の `.claude/commands/` は動き続けるが、**新規はスキルで作る。**

スキルの方が、補助ファイルを置ける・`paths` で自動呼び出しを制限できる・
**変更がセッション中に反映される**（コマンドは再起動が必要）。
