### 構成の判断

到達条件に挙がっていた5項目（利用規約・robots.txt・アクセス間隔・
ログインの要否・個人情報）だけでは受注判断として足りないと判断し、2節を追加した。

- **「最初の3分で判定できること」を冒頭に置いた。**
  ログインの要否・個人情報・JS 描画の3つは即座に判定でき、
  **ここで断る案件に時間を使わない**ため
- **「継続運用できるか」を独立した節にした。**
  一度取るだけなら簡単だが、定期実行は別の話。
  セレクタ破壊の4ケース（うち2つは件数が正常なまま中身が空）と
  置き場所（TCC・iCloud）を根拠として入れた

### 気づき

- **法的判断はしないと明記した。** 規約の解釈が争点になる案件は
  「判断せず持ち帰る」と書いた。技術的に可能かどうかとは別の軸であり、
  ここを曖昧にすると「技術的にできます」が「やってよい」に読み替えられる。
- **公式 API があれば API を使う提案に変える**という項を入れた。
  規約以前の理由がある。セレクタ破壊は例外を出さず件数も正常なまま中身が空になるので、
  **その検知を作って運用する手間がそのまま API を使わない代償**になる。
- **「robots.txt を確認しました」を安全性の根拠として出さない**と書いた。
  404 は許可の根拠にならず、利用規約・ログイン・個人情報は robots.txt では分からない。
  後で問題になったとき、確認したと言った側の責任になる。
- **見積もりの説明材料が実測で揃った。** 「ページ数 × 間隔」が支配的で、
  70ページ103.8秒のうち約7割が待ち時間。
  「1万ページなら間隔だけで約3時間」という形で規模の話を先に出せる。
- 最後の項目に「**異常時の連絡先を最初に聞く**」を入れた。
  通知先が決まらないと壊れたことに気づける設計にできない。
  A-3 の引き渡しで意図的に空欄にした「誰が対処するか」と同じ、
  **技術ではなく顧客組織の事情で決まる項目**。
