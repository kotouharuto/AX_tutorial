# A-3 工程書：他人が使い続ける形にする

目安 2〜3週（締切ではない）／ 実装先：`projects/a3-handover/`
完了条件のチェックは [docs/progress.md](../progress.md) で管理する。

## 狙い

**ここが最大の弱点。** 自分用のツールと、他人が使い続ける仕組みは別物。
「作れる」と「渡せる」の間の距離を埋める。

A-1・A-2 で作ったものを題材にする。先に概念だけ学んでも身につかないため、
このブロックは最後に置かれている。**A-1/A-2 の成果物がないうちは着手しない。**

---

## ステップ① 自動化の使い分けを確立する

n8n（または Dify のワークフロー）で1本組み、GAS との境界を体感する。

**目安：**
- Workspace 内で完結し、相手の資産にしたい → **GAS**
- 外部SaaSを跨ぎ、運用画面が要る → **n8n**

ただし目安を覚えるのが目的ではない。
**実際に両方で同じ処理を組んでみて、自分の言葉で境界を言えるようにする。**
A-1 で作ったものと同じ処理を n8n で組み直すのが最短。

比較の観点：構築の速さ／変更のしやすさ／**誰が保守できるか**／ホスティングの必要性／
相手の組織に残せるか。最後の2つが納品では効く。

---

## ステップ② 非エンジニアに渡せる形に落とす

A-1・A-2 の成果物を、Cowork / Projects / Skills として
「その組織専用の作業環境」に組み直す。

**社内で作った設計ファイルは持ち込まない。白紙から書き起こす。**
（流用すると、その組織固有の前提が混ざったまま納品されるため）

構成の目安：

| 要素 | 内容 |
|---|---|
| 業務ルール | その組織で何をどう扱うか |
| 用語集 | 社内語・略語・表記ゆれの正 |
| 判断基準 | 迷ったときにどちらへ倒すか |
| 手順 | 具体的な作業の流れ |
| 禁止事項 | やってはいけないこと |
| 出力フォーマット | 成果物の形 |

成果物：`projects/a3-handover/context-template/`
これは**副業用のテンプレートとして再利用する**ので、特定組織の内容を残さない形にする。

## ステップ③ 運用を想定して壊す

引き渡し後に起きることを、**意図的に起こして**対処する。想像で対策を書かない。

| 起こすこと | 確認 | 対処の方向 |
|---|---|---|
| 想定外の入力が来る | 何が起きるか（黙って壊れる／止まる／誤処理） | バリデーションと「未処理」への退避 |
| 作った人がいなくなる | 動き続けるか | 配置パターン（A-1 ⑤）と所有者の設計 |
| 業務ルールが変わる | 誰がどこを直すのか | ルールをコード外（シート等）に出す |
| エラーが起きる | 誰がどうやって気づくのか | 通知経路。**気づけない仕組みは壊れている** |

「作った人がいなくなったとき」は A-1 ステップ⑤の配置パターンと直結する。
ここで初めて、あの選択が効いてくる。

## ステップ④ 引き渡しドキュメントを書く

**非エンジニアが読んで運用できる粒度で。**
これが書けない仕組みは、渡した時点で壊れる仕組み。

雛形：[docs/templates/handover.md](../templates/handover.md)

書けるかどうかが仕組みの品質判定になる。書きにくい箇所は、たいてい設計が悪い。
ドキュメントで補わず、**仕組みの側を直す。**

---

## ステップ⑤ 実際に他人に触ってもらう

同僚・知人に触ってもらい、**詰まった箇所を記録する。**

- 説明を先に足さない（詰まる場所が見えなくなる）
- 詰まった箇所は [pitfalls](../pitfalls/README.md) に「引き渡し」観点で記録する
- 「ドキュメントを読めば分かる」で済ませない。読まれなかった事実がデータ

このステップの記録は Phase B の設計に直接効く。
