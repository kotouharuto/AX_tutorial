## ステップ① 開発環境（clasp）

ブラウザのスクリプトエディタで書いている限り Claude Code の恩恵を受けられない。
ローカルから書ける状態を作る。

**現在の症状：** `npm install -g @google/clasp` 済み、`clasp login` が `command not found`。
環境は macOS + bash（`~/.bash_profile`）。PATH 未設定が有力。

**確認の順序（上から潰す）:**

1. `npm bin -g` / `npm prefix -g` でグローバル bin の場所を出す
2. その場所に `clasp` の実体があるか確認する
3. あれば PATH の問題 → `~/.bash_profile` に bin ディレクトリを追加して読み直す
4. なければインストールが失敗している → 権限エラーが出ていなかったか再インストールで確認

**判断の分岐：** グローバルインストールで権限問題が出るなら、`npx @google/clasp` や
Node のバージョン管理（nodenv/nvm）配下へ切り替える。sudo で押し通すと後で別の場所が壊れる。

**この段階で踏みがちな点：**
- macOS の Terminal が zsh の場合、`~/.bash_profile` は読まれない（シェルを確認する）
- `clasp login` はブラウザ認証。**認証情報は `~/.clasprc.json` に出る。リポジトリに置かない。**
- Apps Script API がアカウント側で無効だと push が通らない（Google 側の設定を有効化する）

**到達点：** `clasp login` が通り、`clasp create` → `clasp push` が成功する。

## ステップ③ 実務が回る1本

推奨題材：

```
Googleフォーム受付 → 内容をAPIで分類 → 担当者へ振り分けメール → シートに記録
```

この形に還元できる業務が非常に多い。1本作れば**分類基準の差し替えで転用できる**。

**実装の勘所（分類パート）:**

- 分類は **JSON で返させて `JSON.parse()` する**。自然文で返させると表記ゆれで必ず壊れる。
- プロンプトで「JSONのみ出力、前置き・コードフェンス禁止」と縛る。
- **それでもコードフェンス除去の処理を入れる。** 縛っても混ざる前提で書く。
- `JSON.parse()` の失敗は握り潰さない。未分類として記録し、人が気づける経路に流す。
- 分類先が想定外の値だった場合の扱いを決めておく（未分類に倒す／再問い合わせ）。

**設計の分岐点：** 分類基準をコードに埋めるか、シート上に置くか。
シートに置けば非エンジニアが直せる（A-3 の「ルールが変わったとき誰が直すか」に効く）が、
バリデーションの責務が増える。ここは A-3 を見据えて**シート側に寄せるのを推奨**。

## ステップ④ 4つの落とし穴を意図的に踏む【本丸】

**うまく動かすことより壊すことを優先する。** 先に事故っておくのが目的。
それぞれ「再現させた」→「対処した」の両方を [pitfalls](../pitfalls/README.md) に記録する。

### 1. 実行時間制限（6分）

- **現象：** 1実行6分で強制終了。100件を外部APIに投げれば簡単に超える。
- **踏み方：** 意図的に件数を増やし、実際に打ち切らせてログを見る。
- **対処：** 処理位置を `PropertiesService` に保存。経過時間を監視して安全域で自ら中断し、
  次回トリガーで続きから再開する分割実行にする。
- **設計判断：** 安全域を何秒に取るか（1件あたりの最長処理時間 × 余裕）。
  ここを詰めすぎると、たまに来る遅い1件で打ち切られて状態が壊れる。

### 2. トリガー多重起動

- **現象：** 時間主導トリガーと編集トリガーが同時に走り、二重処理・二重送信。
- **踏み方：** 両方のトリガーを仕掛けて同時に走らせる。二重送信を実際に発生させる。
- **対処：** `LockService` で排他制御。加えて**処理済みフラグ列**を持つ。
- **重要：** ロックだけでは不十分。**冪等性**（同じ行を2回処理しても結果が変わらない）を
  設計に入れる。ロックは同時実行を防ぐが、再実行までは防がない。

### 3. 外部API失敗

- **現象：** 外部APIは落ちる。タイムアウト、レート制限（429）、一時障害（503）。
- **踏み方：** 不正なキー／存在しないエンドポイント／連続大量呼び出しで実際に失敗させる。
- **対処：** `UrlFetchApp` に `muteHttpExceptions: true` を付けてステータスで分岐。
  429/503 は**指数バックオフ**で再試行。4xx（クライアント側の誤り）は再試行しない。
- **落とし穴の落とし穴：** GAS には**日次クォータ**がある。**無限リトライは書かない。**
  最大試行回数を決め、超えたら諦めて通知に回す。
- **通知経路：** 失敗が誰にも届かない実装は「動いているように見えて壊れている」。
  失敗はシートへの記録＋メール等、**人が気づける形**にする。

### 4. 権限スコープ

- **現象：** 過剰な権限を要求すると納品先で説明できず、承認が下りない。
- **対処：** `appsscript.json` の `oauthScopes` を**明示的に**書く（自動推論に任せない）。
  `gmail.send` で済むなら `gmail.readonly` を要求しない。
- **到達点：** 各スコープについて「なぜ必要か」を1行で説明できること。
  説明できないスコープは削って、動かなくなるか試す。

## ステップ⑤ 配置パターンの理解

| パターン | 誰のアカウントで動くか | 向き／リスク |
|---|---|---|
| コンテナバインド | スクリプトを承認した個人 | 手軽。**その人が退職すると止まる** |
| スタンドアロン | 承認した個人 | 複数ファイルから使える。所有者移管の設計が要る |
| サービスアカウント経由 | サービスアカウント | 個人に依存しない。設定が重く、Workspace の委任設定が要る |

**核心：誰のアカウントで動くかを間違えると、その人が退職した瞬間に止まる。**
他人の組織に納品する前提では避けて通れない。到達点は「どの案件でどれを選ぶか」を
自分の言葉で説明できること。
