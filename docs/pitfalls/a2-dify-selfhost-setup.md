# Dify セルフホスト構築で踏んだ落とし穴（8件）

- **ブロック：** A-2
- **日付：** 2026-09-08〜13
- **一般性：** Dify をセルフホストで立てる全ケース（一部は macOS 固有）
- **溶かした時間：** 合計 約 3.5 時間（構築だけで。評価は別）

「構築さえできればいい」と始めたが、動くまでに8つの独立した問題を踏んだ。
**1件ずつは些細でも、連続すると「GUI で手軽」という前提が崩れる。**

## 1. 同じ UI の Cloud とセルフホストで操作先を間違えた

API キーを2回発行したが、どちらも `localhost:8080` の DB に存在しなかった。
nginx のログを見ると**当日のアクセスがゼロ**で、操作は `cloud.dify.ai` 側で行われていた。

UI が同一なので、タブの URL を見ないと気づけない。
**納品先でも顧客が Cloud と社内版の両方にアカウントを持つ状況は普通にある。**

## 2. プラグインの「更新」が失敗すると、アンインストール済みになる

Gemini プラグインを更新しようとして `resource deadlock avoided` で失敗。
その時点で**既存プラグインは消え、新版は入っていない**状態になった。

原因は macOS の Docker Desktop で bind mount したボリュームのファイルロック競合。
Linux サーバでは起きない。対処は残骸ファイルの退避と再インストール。

**動いている環境で「更新があります」を押すと止まる**、という形で納品先でも起きる。

## 3. 非推奨モデルが既定で選ばれる

プラグインは `embedding-001` を `deprecated: true` とマークし、表示順でも
`gemini-embedding-001` を先頭に置いている。にもかかわらず、ナレッジ作成時の既定は
`embedding-001`（API は 404 を返す）だった。

**プラグイン側の非推奨マークが、Dify 本体の既定選択に反映されていない。**
A-1 の「モデル名の腐敗」（→ [記録](a1-gemini-model-name-rot.md)）が3層で起きている：
API がモデルを消し、プラグインは非推奨マークを付け、本体はそれを既定に選ぶ。

## 4. 設定変更が再インデックスに反映されない

埋め込みモデルを `gemini-embedding-001` に変更して保存した12秒後に走った再インデックスが、
**古い `embedding-001` で API を叩いて 404**。DB は新しい値になっているのに実行側が古い値を使う。

worker 再起動＋手動再インデックスで解消。
「保存しました」と DB の更新は両方本当なのに、実行が追いついていない。

## 5. アップロードのバッチ上限が既定5件

60ファイルを投入しようとして1件ずつしか選べなかった。`UPLOAD_FILE_BATCH_LIMIT` の既定が5。
`.env` で変更してコンテナ再作成が必要。**非エンジニアには手が出ない操作。**
（結局 UI では解決せず、Knowledge API 経由の投入スクリプトを書いた）

## 6. ポート80の空き確認を lsof でやると見落とす

→ [独立して記録済み](a2-privileged-port-check.md)

## 7. パスワードを忘れると、コンテナ内コマンドしか手段がない

セルフホストでは SMTP を設定していないため、「パスワードを忘れた」リンクは機能しない。
`docker exec docker-api-1 flask reset-password --email ... --new-password ...` が唯一の手段。
**引き渡し後に必ず起きる事象で、対処できるのは技術者だけ。**

## 8. テンプレートが特定プロバイダー前提

テンプレートから作ったアプリの LLM ノードが `gpt-5.4-mini` で「非互換」。
OpenAI プラグインが無いので存在しない。エラー文は
`Provider langgenius/openai/openai does not exist` で、**何をすべきか利用者に伝えていない。**

## 共通する構造

8件のうち **1・3・4・8 は「成功したように見えて実際の状態が違う」**タイプ。
A-1 の `clasp push` が終了コード0で何もしなかった件と同じ構造が、GUI ではより見えにくくなる。

**GUI は「動いているように見える情報」を出すことに最適化されていて、
「実際に何が起きたか」は DB かログを見ないと分からない。**
今回 Dify で問題を切り分けられたのは、毎回 PostgreSQL を直接見たから。
GUI だけで運用する前提の納品では、この手段が無い。

## 他人の環境に納品するときの含意

- 「Dify なら顧客が自分で運用できる」は、**構築が終わった後の話。** 構築そのものは技術者の仕事。
- 引き渡しドキュメントに最低限：パスワードリセット手順、プラグイン更新は押さない、
  URL の確認（Cloud と混同しない）、ポート変更の手順。
- **セルフホストの Dify は「ノーコード」ではなく「ローコード＋インフラ運用」。**
  この認識の差が、見積もりと期待値のずれになる。
