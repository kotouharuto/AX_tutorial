# マニフェスト変更時、非対話シェルで clasp push が「Skipping push.」と出て何もしない

- **ブロック：** A-1
- **日付：** 2026-08-25
- **一般性：** どの環境でも（CI・スクリプト・エージェント経由の実行すべて）
- **溶かした時間：** 約 0.1 時間

## 現象

`appsscript.json`（マニフェスト）を編集した状態で `clasp push` すると、
エラーではなく次の1行だけが出て終了する。

```
Skipping push.
```

**終了コードは 0。** 見た目上は正常終了だが、リモートには何も反映されていない。

## 原因

マニフェストの変更はスコープや実行環境を変えうるため、clasp は上書き前に
対話プロンプトで確認を取る。**非対話シェル（TTY なし）ではプロンプトに応答できず、
デフォルトの「いいえ」に倒れて push がスキップされる。**

危険なのは、これが**失敗ではなく成功として扱われる**こと。
スクリプトや CI に組み込むと、静かに反映漏れが起き続ける。

## 再現手順

1. `src/appsscript.json` を編集する（例：`oauthScopes` を追加）
2. TTY のない環境で `clasp push`
3. `Skipping push.` のみ出力、終了コード 0、リモート未反映

## 対処

```bash
clasp push --force
```

`--force` はマニフェストの確認プロンプトを省略して上書きする。

**ただし無条件に付けない。** `--force` はリモートのマニフェストを
ローカルで**上書き**する。エディタ側で誰かがスコープを足していた場合、
それを消す。リモートが正の可能性があるなら、先に `clasp pull` で差分を見る。

## 効かなかった対処

出力を見て「変更が無いからスキップされた」と解釈しかけた。
**`clasp status` は tracked files を出すだけで、push されたかは分からない。**
反映確認は push 後の出力（`Pushed N files at ...`）で見る。

## 他人の環境に納品するときの含意

- 自動化スクリプトに `clasp push` を組み込むなら、**出力を検査して
  `Skipping push.` を失敗として扱う**か、`--force` の是非を明示的に決める。
- 「成功しているように見えて何もしていない」は、引き渡し後に最も発見が遅れる障害。
  A-3 の「エラーが起きたとき誰がどうやって気づくのか」の実例として使える。
