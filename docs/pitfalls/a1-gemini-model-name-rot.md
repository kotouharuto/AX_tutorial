# ハードコードしたモデル名が時間で腐って 404 になる

- **ブロック：** A-1
- **日付：** 2026-08-25
- **一般性：** どの環境でも（LLM API を使う全実装）
- **溶かした時間：** 約 0.1 時間

## 現象

分類処理が失敗し、シートの詳細列にこう記録された。

```
Gemini API がステータス 404 を返しました: {
  "error": {
    "code": 404,
    "message": "This model models/gemini-2.5-flash is no longer available to
    new users. Please update your code to use models/gemini-3.6-flash ...
```

コードは一切変えていない。**外部側の都合で、ある日動かなくなる。**

## 原因

モデル名はバージョン番号を含む文字列であり、提供終了する。
今回は「新規ユーザーには提供しない」という段階的な打ち切りだった。

**厄介な性質：**
- コードのバグではないので、テストを厚くしても防げない
- 既存ユーザーには当面動き続けることがあり、**環境によって再現しない**
- 「動いていたものが、ある日突然止まる」ため、直前の変更を疑って時間を溶かす

## 対処

### 1. モデル名を定数として1箇所に集約する

```js
// 【注意】モデル名は時間で腐る。定数を1箇所に集約しているのは、
// この差し替えを1行で終わらせるため。
const GEMINI_MODEL = 'gemini-3.6-flash';
```

散らばっていると差し替え漏れが起きる。今回は1行の修正で済んだ。

### 2. エラー本文を十分な長さで記録する

当初は 200 字で切り詰めており、**API が示していた代替モデル名が途中で切れて読めなかった。**
600 字に広げた。API キーはヘッダで送っており本文には含まれないため、長くしても漏洩しない。

**切り詰めの長さは「秘密が漏れない範囲で、原因が読める長さ」で決める。**
短くしすぎると、せっかく親切なエラーを返す API の情報を捨てることになる。

### 3. エラーを業務側から見える場所に出す

今回これが機能した。分類は失敗したが、
**シートの詳細列にエラー全文が残り、通知メールも飛んだ。**
握り潰していれば「なぜか未分類になる」という調査困難な状態になっていた。

## 他人の環境に納品するときの含意

**これは A-3 の「作った人がいなくなったとき、動き続けるか」の実例。**

- 納品した仕組みは、**コードを変えなくても数ヶ月後に止まりうる。**
  引き渡し時に「止まる可能性がある箇所」として明示しておく。
- 引き渡しドキュメントに、使用モデル名と**その差し替え手順**を書く。
  「`Config.js` の `GEMINI_MODEL` を新しいモデル名に変える」まで具体的に。
- 保守契約の有無に関わらず、**モデル名の更新だけは誰かが担う必要がある。**
  誰が担うのかを引き渡し時に決めておく。決めないと止まってから慌てる。
