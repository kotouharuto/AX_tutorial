# 承認画面は権限を個別に拒否できる（部分承認で「承認したのに動かない」が起きる）

- **ブロック：** A-1
- **日付：** 2026-08-26
- **一般性：** どの環境でも
- **溶かした時間：** 0.2 時間（実物確認）

## 承認画面の実物（スタンドアロン版）

```
⚠ このアプリは Google で検証されていません
  このアプリの検証を Google にリクエストする必要があることを、
  アプリ デベロッパー（haruto.k.0321@gmail.com）に知らせることができます

A1-standalone がアクセスできる情報を選択してください

  □ すべて選択
  ● Google スプレッドシートのすべてのスプレッドシートの
    参照、編集、作成、削除 です。                        □
  ● ユーザー本人に代わってメールを送信 です。             □

ℹ A1-standalone のプライバシー ポリシーや利用規約への
  リンクが表示されない理由をご確認ください
```

## 発見1：権限は個別に拒否できる（最重要）

**チェックボックスが権限ごとに独立しており、初期状態は未チェック。**

利用者は「スプレッドシートは許可するが、メール送信はチェックしない」という
**部分承認**ができる。そしてその状態でスクリプトは起動する。

### 何が起きるか

実行時に権限不足で落ちる。症状は
[承認は通ったのに何も起きない](a1-gas-approved-but-nothing-happens.md) と同じだが、
**原因がコードの外にある。** コードをいくら読んでも分からない。

納品先での典型的なやりとり：
- 利用者「許可しました」（本当。部分的に許可した）
- 開発者「権限を要求しています」（本当。マニフェストに書いてある）
- **どちらも嘘をついていないのに噛み合わない。**

### 対処の方向

- 実行の入口で**必要な権限が揃っているかを確認する**処理を持つ。
  `ScriptApp.getAuthorizationInfo()` で承認状態を取得できる。
- 権限不足で落ちたとき、**エラーメッセージに「承認画面で全項目に
  チェックを入れる必要がある」と書く。** 技術的なメッセージだけでは
  利用者は自分の操作が原因だと気づけない。
- 引き渡しドキュメントに承認画面のスクリーンショットを載せ、
  **「すべて選択」にチェックを入れる手順**を明示する。

## 発見2：開発者のメールアドレスが利用者に表示される

警告文に**アプリ開発者の Gmail アドレスがそのまま出る。**
納品先の利用者全員がこれを見る。

技術的制約として記録しておく（対処の検討は Phase A の範囲外）。

## 発見3：「編集」には「削除」が含まれる

```
参照、編集、作成、削除 です。
```

コードは**読み取りしかしていない**のに、この表示になる。
Google のスコープは粒度が粗く、書き込み権限に削除が含まれるため。

**「削除はしません」と口頭で説明しても、画面と矛盾する。**
説明する側が不利になるので、読み取りだけで済むなら
`readonly` 系スコープを選ぶ意味は大きい。

## 発見4：配置パターンによる文言の差（実験の主目的）

| 配置 | スコープ | 承認画面の文言 |
|---|---|---|
| コンテナバインド | `spreadsheets.currentonly` | 「このアプリケーションで使用されているスプレッドシートのみ」 |
| スタンドアロン | `spreadsheets` | 「**すべての**スプレッドシートの参照、編集、作成、削除」 |

**処理内容は1文字も違わない。** シートを1行読んでメールを1通送るだけ。
配置を変えただけで、利用者の全スプレッドシートへの権限要求になる。

情シスに「なぜ全部のシートを触るのか」と聞かれたとき、
コンテナバインドなら「このファイルだけです」と答えられる。
スタンドアロンでは答えられない。**技術的には同じことをしているのに。**

## 他人の環境に納品するときの含意

- **部分承認は必ず起きる前提で設計する。** 権限確認と、
  利用者が自分で直せるエラーメッセージを用意する。
- 承認画面には「検証されていません」警告、開発者アドレス、
  ポリシー欠如の表示が出る。**組織のセキュリティ意識が高いほどここで止まる。**
- 配置パターンの選択は、権限表示を通じて**納品先の心理的ハードルを直接変える。**
