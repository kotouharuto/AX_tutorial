# トリガー多重起動で二重処理が起きる（フラグ列だけでは防げない）

- **ブロック：** A-1
- **日付：** 2026-08-26
- **一般性：** どの環境でも（トリガーを複数持つ全 GAS プロジェクト）
- **溶かした時間：** 約 0.6 時間（意図的な再現実験）

## 実験と結果

1分間隔のトリガーを2本登録し、同一シートの未処理20行を処理させた。
処理済みフラグ列によるスキップは**実装済み**の状態で比較した。

| | 排他なし | 排他あり（`LockService`） |
|---|---|---|
| 処理件数 | **23**（対象20件） | 20 |
| 二重処理された対象 | **3 件** | 0 件 |
| ロックで見送った実行 | 0 | **1** |

**対象20件のうち3件、15% が二重処理された。**

## 原因：フラグ列は同時実行を防げない

```js
const status = sheet.getRange(row, 3).getValue();  // ← 読む
if (status) continue;
doWork();                                          // ← 時間がかかる
sheet.getRange(row, 3).setValue('完了');            // ← 書く
```

**読んでから書くまでに隙間がある。**
別の実行が同じ瞬間に「空」を読めば、両方が処理に進む。

処理済みフラグが防げるのは**順次実行での再処理**であって、**同時実行**ではない。
両者は別の問題なので、対策も別に要る。

| 防ぎたいもの | 有効な手段 |
|---|---|
| 同時実行（並行して同じ行を掴む） | `LockService` |
| 再実行（後から同じ行をもう一度処理する） | 処理済みフラグ・冪等な設計 |

**片方だけでは足りない。**

## 観察：トリガーは同時刻には走らない

実行履歴の開始時刻：

```
6:37:22, 6:37:59, 6:38:22, 6:38:59, 6:39:22, 6:39:59, 6:40:22, 6:40:59
```

**「1分ごと」を2本登録しても、GAS が起動時刻を約23秒ずらして分散させる。**
そのため競合ウィンドウは狭い。実際に競合したのは、期間 **9.369秒** の実行が
走っている最中に次が始まったときだけで、1〜3秒で終わる実行は重ならなかった。

### これが最も厄介な性質

**競合ウィンドウは処理時間に比例する。**

- 開発中は再現しない（データが少なく処理が速く終わる）
- 本番で件数が増え、処理が長引いたときに初めて出る
- 報告を受けても再現できず「気のせい」で片付けられる
- **二重送信されたメールの受け手だけが気づく**

つまり **成功して利用が増えるほど壊れやすくなる。**

## 対処

```js
const lock = LockService.getScriptLock();
// tryLock(0) で即座に諦める。waitLock で待たせないのは、
// 定期実行では「前の実行が動いているなら今回は何もしない」で十分だから。
// 待たせると実行が積み上がり、6分制限に当たる原因になる。
if (!lock.tryLock(0)) {
  console.log('他の実行が処理中のため、今回は何もしない。');
  return;
}
try {
  processRows();
} finally {
  // finally で必ず解放する。例外時に解放し忘れると、
  // ロックが残って以降の実行が全て空振りする。
  lock.releaseLock();
}
```

### 設計判断：`tryLock(0)` か `waitLock(n)` か

| | 向く場面 | 失うもの |
|---|---|---|
| `tryLock(0)` | 定期実行。取れなければ次回に回せる | 即時性（今回の分は次の起動まで待つ） |
| `waitLock(n)` | ユーザー操作起点。処理を落とせない | 実行が積み上がり6分制限に当たる危険 |

今回は定期実行なので `tryLock(0)`。**「待つ」設計は6分制限と衝突する。**

### ロックの種類

- `getScriptLock()` — スクリプト全体で1つ。今回はこれ
- `getUserLock()` — 実行ユーザーごと。他人の実行は止められない
- `getDocumentLock()` — ドキュメントごと

**同じシートを複数人が触る仕組みで `getUserLock()` を選ぶと、排他しているつもりで
全く排他できていない。** ロックの単位と、守りたい資源の単位を一致させる。

## 検証で気をつけたこと

**「二重処理0件」だけでは、ロックが効いたのか競合が起きなかっただけなのか区別できない。**
そのため「ロック取得に失敗した回数」も記録した。これが1以上あって初めて
「競合は起きたが防がれた」と言える。

**対策の検証では、対策が働いた証跡を残す。** 症状が消えたことだけを見ない。

## 他人の環境に納品するときの含意

- **トリガーを2つ以上持つ仕組みは、原則として排他が要る。**
  時間主導と編集トリガー、フォーム送信と定期バッチなどは同時に走る。
- 引き渡し後にトリガーを追加されると、排他のない仕組みは壊れる。
  引き渡しドキュメントに「トリガーを増やすときの注意」を書く。
- **実験用トリガーの消し忘れに注意。** 1分ごとに永久に動き続け、
  実行回数のクォータを消費する。停止手段（`demoStop` に相当するもの）を
  最初から用意しておく。「作った人がいなくなっても動き続ける」ものを
  作ってしまう典型例。
