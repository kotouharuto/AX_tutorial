# Socket Mode の Bot が、プロセスは生きたまま Slack との接続だけ壊れ続ける

- **ブロック：** A-5b
- **日付：** 2026-10-18
- **一般性：** 同じ構成なら誰でも（Socket Mode の Bot を常駐させる）
- **溶かした時間：** 未計測

## 現象

一晩動かしたままの Bot に問い合わせを送ると、利用者の画面に「アプリが応答しなかったため、/inquiry は失敗しました」。
ログでは、**深夜 01:56 から約7時間45分、2,557回**、次を繰り返していた。

```
ERROR slack_bolt.App on_error invoked (... error: BrokenPipeError, message: [Errno 32] Broken pipe)
INFO  slack_bolt.App The connection has been closed
INFO  slack_bolt.App The session seems to be already closed. Reconnecting...
```

- **プロセスは動き続けていた**（プロセスの生死を見る監視では正常に見える）
- 利用者からは Gemini や API の問題に見える（実際に「API が呼べないのか」と質問が出た）

## 再現手順

確実な再現手順は無い。夜間のネットワークかスリープの状態変化がきっかけと考えられるが確証は無い。
**ネットワークを切る**ことで「切れたまま」の状態は再現できる（下の実機確認）。

## 原因

- slack-bolt 1.30.0 / slack-sdk 3.45.0 の Socket Mode は、同じプロセスの中で自動再接続を試みるが、
  この事例では**同じプロセスの中では回復しなかった。** プロセスを起動し直すと即座に正常に接続した
- 自動再接続があるので例外で落ちず、**「生きているが仕事をしていない」状態が続く**

## 対処

**「Slack とつながっているか」を見張り、切れたまま一定時間たったら自分で終了し、常駐の仕組みに起動し直させる。**

- `projects/a5b-slack-bot/src/watchdog.py`：`SocketModeHandler.client.is_connected()` を30秒ごとに見て、
  300秒切れたままなら終了コード3で終了
- 終了時は Slack に通知できないことが多いので、**記録をファイルに書き、次に接続できたら運用チャンネルに送る**
- launchd：`KeepAlive` の `SuccessfulExit: false`（異常終了のときだけ起動し直す）、`ThrottleInterval: 30`

**実機確認**（Wi-Fi を約2分切断・確認用に 10秒／60秒 に短縮）：

| 時刻 | 起きたこと |
|---|---|
| 11:31:56 | 接続が切れる。再接続は名前解決できず失敗し続ける |
| 11:32:49 | 見張りが終了。運用チャンネルへの通知は失敗 → 記録だけ残る |
| 11:32:50 | launchd が起動し直すが、オフラインで起動時の `auth.test` に失敗して異常終了 |
| 11:33:20 | 30秒後の起動で接続し、記録を読んで運用チャンネルに「前回、接続が60秒切れたため起動し直した」を投稿 |

## 効かなかった対処

- Bolt の自動再接続に任せる（約7時間45分回復しなかった）
- プロセスの生死の監視（プロセスは生きていた）

## 他人の環境に納品するときの含意

- 常駐 Bot の監視は「プロセスがあるか」ではなく**「外部とつながって仕事ができる状態か」**で見る
- 自分で終了する作りにするなら、**起動し直す仕組み（launchd・systemd・コンテナの再起動方針）とセットで渡す**
- 落ちている間に送られた依頼は受け付けられていない。復旧時にそれを運用担当に知らせる経路を作る
- 置き場所のマシンがスリープすれば Bot も止まる。常時稼働のマシンを顧客側で確保できるかを最初に確認する
