# エンドポイント保護のスキャンで、新規インストールしたパッケージの import が数十秒ブロックされる

- **ブロック：** A-4
- **日付：** 2026-09-25〜26
- **一般性：** エンドポイント保護（EDR/アンチウイルス）が入った端末すべて。企業支給 PC では標準的
- **溶かした時間：** 約 1.0 時間（原因特定まで）

## 事象

`uv pip install pandas openpyxl pypdf reportlab` の直後、
自作コードの動作確認をしようとしたところ、実行が返ってこなくなった。

最初は自分のコードを疑ったが、切り分けると **`import pandas` だけで30秒以上**かかっていた。

```
import pandas    → 30秒超（完了せず）
import openpyxl  → 12秒超
import pypdf     → 12秒超
import (標準ライブラリ) → 即座
```

**標準ライブラリだけが速い。** 新しくインストールした third-party パッケージが全部遅い。

## 切り分けの手順

### 1. プロセスの状態を見る

```bash
ps aux | grep python
```

CPU **0%** で残り続けていた。計算していない＝待っている。

### 2. スタックを採取する（macOS）

```bash
sample <PID> 3 -mayDie
```

最深部がこうなっていた。

```
_io_FileIO_readall_impl
  _Py_read
    read (in libsystem_kernel.dylib)   ← ここで 1718 サンプル
```

**ファイルの `read()` でブロックしている。** Python が `.so` や `.pyc` を読もうとして止まっていた。

### 3. CPU を食っているプロセスを見る

```bash
ps aux | sort -rn -k3 | head
```

```
96.2%  com.broadcom.mes.systemextension    ← エンドポイント保護
50.7%  Docker Desktop
ディスク I/O: 124 MB/s、1583 tps
```

## 原因

**エンドポイント保護が、新規作成されたファイルを1つずつスキャンしている。**

Python の `import` は数百〜数千の `.so` / `.pyc` を読むため、
ファイルを開くたびにスキャンが走り、`read()` がブロックされる。

pandas だけで site-packages に数百ファイルが展開されるので、影響が大きい。

## 対処

### 待つ（スキャンは1ファイル1回）

**途中で kill しない。** kill するとスキャンが完了せず、次回も最初からになる。
一度完走させればキャッシュされ、以降は通常の速度に戻る。

実測：

```
1回目: real 11m14s / user 0m0.7s / sys 0m0.5s
2回目: real  0m0.37s
```

**CPU 時間は 0.7 秒。11分のうち 99.9% がスキャン待ちだった。**
完走後は 1800 倍速くなる。

これに気づかず、遅いたびに kill していたため状況が改善しなかった。
`user` 時間が極端に小さい実行は、計算ではなく待機だと判断できる。

### 負荷を下げる

Docker など他の重いプロセスを止める。今回は Docker 停止で 96% → 31% に下がった。

### 依存を減らす（設計として）

そもそも80行程度のデータ処理に pandas は過剰だった。
標準ライブラリ＋openpyxl だけで書けば、スキャン対象のファイル数が桁で減る。

**「他人の環境で動かす」観点では、依存の少なさがそのまま起動の速さになる。**

## 納品時の含意（重要）

これは開発機だけの問題ではない。

- **顧客の PC にはほぼ確実にエンドポイント保護が入っている。** 企業支給 PC では標準
- **初回実行が極端に遅い**ため、利用者は「動かない」と判断して報告してこない
- PyInstaller などで固めた実行ファイルは、**単一の大きなバイナリ**になるため、
  初回起動時に丸ごとスキャンされる。数十秒〜数分かかることがある
- 手順書に「**初回の起動には時間がかかります。1〜2分待ってください**」と明記する必要がある

A-4 の到達条件に「Python 未導入の Windows PC 向けの配布方法」があるが、
配布形式を決めるときに**スキャンの影響**を考慮する必要がある。

## 一般化

「実行が返ってこない」ときの切り分け順序。

1. **プロセスの CPU 使用率を見る** — 0% なら待っている、100% なら計算している
2. **0% なら、何を待っているかをスタックで見る**（macOS は `sample`、Linux は `py-spy` や `gdb`）
3. **自分のコードの外を疑う** — 今回はセキュリティソフト、ディスク I/O、ネットワーク

最初に自分のコードを疑って読み直したが、そこには原因がなかった。
**待っているのか計算しているのかを最初に見れば、1時間は短縮できた。**
