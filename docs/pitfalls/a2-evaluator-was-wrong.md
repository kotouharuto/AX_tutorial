# 評価する側が間違っていた（正解の誤り・意図しない汚れ）

- **ブロック：** A-2
- **日付：** 2026-09-01
- **一般性：** どの環境でも（評価セットを作る全ての場面）
- **溶かした時間：** 約 0.3 時間

## 事象

30問の評価セットを作り、既製方式2つに通したところ、
**評価される側ではなく、評価する側の欠陥が3つ見つかった。**

### 1. 正解が間違っていた（Q19）

`expected` に「担当役員」と書いていたが、根拠の表 `TBL-502` を見ると
備品購入の5万〜20万円帯は「所属長＋総務」だった。

**両方式ともこの正解を答えており、評価セット側が誤っていた。**
気づいたのは、回答が想定と違ったので表を確認したとき。

**そのまま採点していれば、正しい回答を不正解と判定していた。**

### 2. 意図しない重複（被評価側に指摘された）

Claude Projects が「質問していないのに」文書側の課題を挙げ、
その中に **FAQ-800/809・801/810・802/811・803/812 が完全重複**という指摘があった。

原因は生成スクリプトのバグ。FAQ の元データが8件しかないのに13件生成しており、
`FAQ_PAIRS[i % len(FAQ_PAIRS)]` で循環していた。

**「意図的に汚した」つもりの中に、意図していない汚れが混ざっていた。**

### 3. 意図しない不整合（同じく指摘された）

`ASSET-401`（1万円以上10万円未満：所属長＋総務／10万円以上：経理協議）と
`TBL-502`（5万〜20万円：所属長＋総務）で、**金額帯の区切りが一致していない。**

これも意図して作ったものではない。ただし実務では頻出する種類の不整合なので、
題材としては結果的に妥当だった。

## 対処

### 正解は必ず検算する

`expected` を書いた後、**根拠文書を開いて1問ずつ突き合わせる。**
Q19 に気づいた後、残り29問も検算した（誤りはQ19のみ）。

**評価セットは「作って終わり」ではなく、それ自体が検証対象。**

### 評価開始後はコーパスを変更しない

FAQ の重複バグは見つかったが、**修正しなかった。**

既に2方式を同じコーパスで測っており、途中で変えると比較が壊れる。
重複はノイズが増えただけで、評価問題の根拠文書には影響していない。

**「バグを見つけたら直す」が常に正しいわけではない。**
測定中に測定条件を変えれば、それまでのデータが使えなくなる。
直すのは全方式を測り終えた後。

### 意図した汚れと事故を区別する

作業中、生成データにキリル文字・ハングルを3回混入させた。
うち1件はコメントに「わざと表記誤りを含む」と書いていたが、**単なるタイプミスだった。**

**汚れは意図して入れたものだけを汚れと呼ぶ。**
事故を後から意味づけると、何を測っているのか分からなくなる。

## 他人の環境に納品するときの含意

- **「精度が出ない」の原因が評価セット側にあることは実際にある。**
  顧客に精度を報告する前に、正解の検算を済ませておく。
- 評価セットは顧客と合意する対象。
  こちらの正解が間違っていれば、合意そのものが無効になる。
- **被評価側（LLM）が評価セットの欠陥を指摘してくることがある。**
  それを「余計な出力」として捨てず、検証に使う。
  今回は指摘された2点とも実在の欠陥だった。
