# スラッシュコマンドの3秒期限：LLM を待ってから応答すると「失敗」と「結果」が両方出て、Bolt のログは原因を指さない

- **ブロック：** A-5b
- **日付：** 2026-10-17
- **一般性：** 同じ構成なら誰でも（Slack のスラッシュコマンド＋時間のかかる処理）
- **溶かした時間：** 未計測

## 現象

分類（Gemini）が終わってから `ack()` する素朴な実装で、観察用に処理を4秒遅らせると：

| 時刻 | 起きたこと |
|---|---|
| 0秒 | 問い合わせを受信 |
| 3秒 | 利用者の画面に「アプリが応答しなかったため、/inquiry は失敗しました。もう一度試すか…」 |
| 7.4秒 | **遅れて分類結果も表示される** |

ログ：

```
WARNING handle_inquiry didn't call ack()
WARNING Unhandled request ({'type': None, 'command': '/inquiry'})
INFO    Unsuccessful Bolt execution result (status: 404, body: {"error": "unhandled request"})
```

遅延なしでも受信から 2.80 秒で、期限の3秒に対して残り 0.2 秒だった。実際の負荷では Gemini だけで 3.12 秒かかった回もある。

## 再現手順

1. Bolt for Python（1.30.0）で `@app.command("/inquiry")` の中で、重い処理を終えてから `ack(結果)` する
2. 処理に4秒以上かける（`time.sleep` でよい）
3. Slack からコマンドを送る

## 原因

- Slack はスラッシュコマンドの受領確認を **3秒（3000ミリ秒）** 待つ。ここには Slack とこちらの間の通信時間も含まれる
- Bolt 自身も3秒で見切りをつけ、「ack されなかった」として失敗を返す。**実際には ack は呼ばれる（遅れただけ）**ので、
  ログの「ack を呼ばなかった」「Unhandled request (404)」は事実と違い、**コマンド名の不一致や ack の書き忘れを疑わせる**
- 遅れた ack の本文は捨てられず表示されるので、利用者は失敗と成功の両方を見る。
  「もう一度試して」に従うと**二重登録**になる（振り分け通知があれば担当に二重に飛ぶ）

## 対処

**受信したらすぐ `ack()` し、重い処理の結果は `respond()` で後から送る。**

```python
@app.command("/inquiry")
def on_inquiry(ack, respond, command):
    ack("受け付けました。分類しています…")   # 3秒以内に必ず返す
    result = classify(command["text"])        # 重い処理は ack の後
    respond(text=..., blocks=...)              # 返信用 URL を使うので commands の権限だけで送れる
```

同じ4秒の遅延で、ack は受信から 0.00 秒、結果は 7.25 秒後に届き、Bolt の警告も消えた。
失敗したら「受け付けました」の後に、失敗したことと次にすべきこと（再送不要かどうか）を改めて送る。

## 効かなかった対処

- 「今日は動いた」（2.80 秒）で済ませること。入力が長い・LLM が混む、それだけで超える

## 他人の環境に納品するときの含意

- LLM を呼ぶ Bot は**最初から ack 先行で書く。** 開発時に速くても本番で超える
- 「アプリが応答しなかった」が出たときに、ログの「didn't call ack()」を鵜呑みにしないよう引き渡し文書に書く
- 失敗の案内文に「もう一度試して」を安易に書かない（二重処理になる）
