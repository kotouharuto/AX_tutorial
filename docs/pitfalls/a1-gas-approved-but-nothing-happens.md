# OAuth 承認は通るのにメールが届かない（実行関数の既定選択 × プロパティ未設定）

- **ブロック：** A-1
- **日付：** 2026-08-25
- **一般性：** どの環境でも（Apps Script エディタから初回実行する全員）
- **溶かした時間：** 約 0.4 時間

## 現象

`clasp push` は成功。Apps Script エディタで実行ボタンを押すと**OAuth 承認画面が正しく出て、
承認も通る。** にもかかわらずメールが届かない。エラーも表示されない。

## 原因（2つが重なっていた）

### 1. 実行対象の関数が意図したものではなかった

**Apps Script エディタは「ファイル内で最初に定義された関数」を実行対象として既定選択する。**
このとき `Code.js` の先頭にあったのは補助関数 `getNotifyTo()` だった。

厄介なのは、**補助関数を実行しても承認画面は正しく出る**こと。
承認スコープはマニフェストの `oauthScopes` に基づくため、実際に何を呼ぶかとは無関係。
「承認画面が出た＝目的の処理が走った」と誤認させる。

### 2. スクリプトプロパティ `NOTIFY_TO` が未設定だった

仮に正しい関数を選んでいても、`getNotifyTo()` が例外を投げて手前で止まっていた。

**2つの原因が重なると、片方を直しても症状が変わらない。**
「対処したのに直らない → その対処は間違い」と誤って結論づけやすい。

## 再現手順

1. 補助関数をファイル先頭、エントリポイントを後方に置く
2. スクリプトプロパティを未設定のままにする
3. エディタで実行ボタンを押す → 承認画面が出て、承認後も何も起きない

## 対処

### エントリポイントをファイル先頭に置く

```js
// 【エントリポイント】Apps Script エディタはファイル内の最初の関数を既定選択する。
// 補助関数を先頭に置くと、実行ボタンで意図した処理が走らない。
function sendMinimalNotification() { ... }

// 補助関数は後ろに置く（JS の巻き上げにより呼び出し順の制約はない）
function getNotifyTo() { ... }
```

実行時は**関数プルダウンを明示的に確認する**習慣をつける。

### 副作用を伴わない診断関数を用意する

```js
function checkSetup() {
  // メールを送らずに前提だけ確認する。
  // 宛先そのものは個人情報なのでログに出さず、設定の有無だけを報告する。
  console.log(`NOTIFY_TO: ${to ? '設定あり' : '未設定'}`);
  console.log(`Gmail 残り送信可能数: ${MailApp.getRemainingDailyQuota()}`);
}
```

**原因が複数重なっているときは、1つずつ潰すより「前提を全部一度に可視化する」方が速い。**

## 関連：実行対象プルダウンの仕様（後日追記 2026-08-25）

同じ「実行したい関数が実行できない」系で、追加で2つ踏んだ。

### プルダウンには「いま開いているファイル」の関数しか出ない

`Main.js` に関数を追加して push したのに、プルダウンに現れない。
リモートには反映済み（`clasp push` は `Script is already up to date.`）だった。

**エディタの実行対象プルダウンは、エディタで開いているファイル内の関数だけを列挙する。**
別ファイルの関数を実行したければ、左のファイル一覧でそのファイルを開く必要がある。

複数ファイルに分割した瞬間に効いてくるため、ローカルで clasp を使い
ファイルを分けている場合ほど踏みやすい。

### 引数を取る関数はプルダウンに出ない

`testWithSampleRow(row)` のように引数のある関数は列挙されない。
手動実行したい関数は**引数なしで定義する**か、引数なしのラッパーを用意する。

### ローカルの .js はエディタで .gs と表示される

clasp が変換している。中身は同じだが、
「エディタで探しているファイルが手元の名前と違う」という混乱の元になる。

## 効かなかった対処

- 迷惑メールフォルダ・フィルタの確認 → 無駄だった。
  **先に Gmail の「送信済み」を見るべきだった。** 0件なら `sendEmail()` 未到達が確定し、
  受信側の調査は全部不要になる。
- `clasp tail-logs` での確認 → GCP プロジェクト未設定で使えず
  （→ [記録](a1-clasp-logs-need-gcp-project.md)）。

## 切り分けの原則（今回得たもの）

**ログが無いときは、副作用の有無で二分する。**
「送信済みが空か否か」で、原因を実行側と受信側に一刀両断できた。
届かない話を受信側から調べ始めると、原因が送信側にある場合に必ず遠回りする。

## 他人の環境に納品するときの含意

- **「承認は通ったが何も起きない」は納品直後に最も起きやすい事象。**
  相手はエラーを見ていないので「壊れている」とすら報告してこない（黙って使わなくなる）。
- 引き渡し前提の設計では、**利用者に関数を選ばせない。**
  メニュー（`onOpen` のカスタムメニュー）やトリガー経由にして、
  実行入口を1つに固定する。
- 設定不足は起動時に検知して、**業務側から見える形**で知らせる。
