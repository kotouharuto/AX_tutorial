# 自動採点が誤答を正解と判定した（期待値に誤答例を書いていたため）

- **ブロック：** A-2
- **日付：** 2026-09-01
- **一般性：** どの環境でも（評価を自動化する全ての場面）
- **溶かした時間：** 約 0.3 時間

## 事象

30問 × 7構成 = 210回答を手で採点するのは非現実的なため、
`expected` に含まれる数値との照合で自動採点を実装した。

ベースライン構成を手動で検算したところ、**3問でズレていた。**

| 問題 | 自動判定 | 手動採点 | 原因 |
|---|---|---|---|
| **Q17** | **0.5** | **0** | **誤答を部分正解と判定した** |
| Q19 | 0.5 | 1 | 完全正答だが数値照合が失敗 |
| Q23 | 判定不能 | 1 | 正解に数値が含まれない（「取締役会」） |

自動判定 26.0/29 に対し、手動採点 28.0/30。

## 最も危険だったもの（Q17）

質問「パスワードの有効期限は何日ですか？」
正解は 60日（社内通達で90日から短縮）。

**回答は「90日」で、明確な誤答だった。** にもかかわらず自動判定は 0.5 を付けた。

原因は `expected` の書き方。

```yaml
expected: |
  2025年7月1日より60日（社内通達 SCN-602）。
  手順書 IT-110 には90日と記載が残っている。   # ← ここ
```

**期待値の中に誤答例（90日）を書いていたため、数値照合で誤答がマッチした。**

`expected` に「なぜ間違えやすいか」を親切に書いたことが、
そのまま自動採点を壊した。

## なぜ見逃すと重大か

Q17 は**画像PDFにしか正解がない問題**で、自作構成の構造的な弱点を検出するための問いだった。

自動判定を検算せずに使っていれば、
**「自作でも既製とほぼ同等」という誤った結論**を出していた。
弱点を検出するために置いた問題が、弱点を隠す方向に働いた。

## 対処

### 1. 自動採点は必ず手動で検算してから使う

ベースライン構成だけは全問を目視で確認した。
**自動採点は「手で採点する量を減らす道具」であって、
「採点しなくてよくする道具」ではない。**

### 2. 期待値に誤答例を書かない

判定に使うフィールドと、人間向けの解説を分ける。
解説（なぜ間違えやすいか）は `detects` に書き、`expected` には正解だけを書く。

### 3. そもそも自動採点が要る設計かを疑う

今回は**測定方法自体を変えて解決した。**

チャンクサイズ・オーバーラップ・検索方式の効き幅は、本質的に**検索性能**の問題で、
生成部分は全構成で共通。そこで正答率ではなく
**「正解の根拠文書を検索で拾えたか（Recall）」**で測ることにした。

| | 正答率で測る | Recall で測る |
|---|---|---|
| 判定 | LLM 出力の意味判断が必要 | `sources` と照合するだけ。完全に自動・正確 |
| API 呼び出し | 210回 | **ゼロ** |
| 測れるもの | 総合性能 | 検索性能（＝効き幅の本体） |

**採点が難しいのは、測るものを間違えているサインだった。**
生成を挟むと LLM の揺らぎが混ざり、チャンクの効果とノイズを切り分けられない。
測定対象を検索に絞れば、判定の曖昧さそのものが消える。

## 他人の環境に納品するときの含意

- **精度を数値で報告するなら、その数値の出し方を説明できる必要がある。**
  「自動評価で 87%」は、判定ロジックを検算していなければ根拠にならない。
- LLM-as-judge を使う場合も同じ。判定器の妥当性を別途検証しない限り、
  出た数字は「判定器の出力」であって「精度」ではない。
- 顧客に見せる指標は、**判定が機械的に定まるもの**を選ぶ方が安全。
  Recall や再現手順のある数値は、意味判断が入らないので争いにならない。
