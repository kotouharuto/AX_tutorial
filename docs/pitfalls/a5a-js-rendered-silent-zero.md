# JS 描画ページを静的取得すると、10ページ巡回して0件・終了コード0で終わる

- **ブロック：** A-5a
- **日付：** 2026-09-27
- **一般性：** requests / BeautifulSoup など、ブラウザを使わない取得手段すべて
- **溶かした時間：** 0 h（意図的に踏んだ。**回避せず観察するのが目的**）

## 事象

同一のコードで3つの URL を取りに行った結果。

| 対象 | ページ数 | 取得件数 | 終了コード |
|---|---|---|---|
| books.toscrape.com | 50 | 1000 件 | 0 |
| quotes.toscrape.com | 10 | 100 件 | 0 |
| **quotes.toscrape.com/js/** | **10** | **0 件** | **0** |

例外なし、HTTP エラーなし、終了コード0。それでいて0件。

## なぜ「失敗に見えない」のか

JS 版の生 HTML を調べると、3つの条件が重なっている。

```
div.quote の数   : 0     ← 欲しいデータは無い
li.next > a の数 : 1     ← ページネーションは静的に存在する
script タグの数  : 2     ← データは <script> の var data = [...] の中
HTML の長さ      : 5806  ← 空のレスポンスではない
```

**ページ送りのリンクだけがサーバ側で出力されている。**
そのためスクレイパーは10ページを正常に巡回でき、
「接続できない」「ページが無い」ではなく
**「巡回は全部成功したが、どのページにも1件も無かった」**という結果になる。

これは**サイト側が本当に空である場合と区別できない。**

出力も正常に見える。`quotes_js.json` は 2 bytes の妥当な JSON（`[]`）で、
これを読む側はエラーにならず空リストを受け取る。

```bash
# 確認方法：件数ではなく中身を見る
python3 -c "
import requests
from bs4 import BeautifulSoup
h = requests.get('https://quotes.toscrape.com/js/', timeout=15).text
s = BeautifulSoup(h, 'html.parser')
print('div.quote:', len(s.select('div.quote')))
print('li.next  :', len(s.select('li.next > a')))
print('HTML長   :', len(h))
"
```

## 原因

サーバが返す HTML には**枠だけ**が入っており、一覧の中身は
ブラウザが JavaScript を実行して初めて DOM に挿入される。
`requests` は HTTP クライアントであって JavaScript を実行しないため、
挿入前の HTML を見ている。

## 対処

### 見分け方（実装前に判定する）

取得対象を決める段階で確認する。**実装してから気づくと作り直しになる。**

1. ブラウザの「ページのソースを表示」（開発者ツールの Elements ではない）で
   目的のデータが含まれるか見る。**Elements は JS 実行後の DOM なので判定に使えない**
2. `curl <URL> | grep <データの一部>` でヒットするか
3. `<script>` の中に JSON が埋まっていないか探す

3 に当たる場合、**Playwright を使わずに script 内の JSON を直接読む方が速い**
（ブラウザを起動しない、数百MBのダウンロードも不要）。
今回の quotes/js は `var data = [...]` に**そのページの10件**が入っていた
（全件ではないので、ページ送り自体は従来どおり必要）。

### 取得手段を変える

ブラウザを動かす手段（Playwright 等）に切り替える。
ただしブラウザ本体のダウンロード（数百MB）と起動コストが増える。
**顧客の PC に入れる前提なら、この容量と初回スキャン時間が問題になる**
（→ `a4-endpoint-protection-blocks-import.md`）。

### 0件を異常として扱う（本質的な対処）

取得手段を正しく選んでも、**サイト側の変更で同じ状態に落ちる。**
「0件は正常な結果ではなく異常」という判定を入れないと、
定期実行では初回が0件で成功した後、2回目以降は「差分なし」と報告し続ける。

→ 別途記録（セレクタ破壊の実験とあわせて）

## 納品時の含意

- **「取得できるか」を件数で報告してはいけない。** 0件も件数である
- 定期実行に載せる場合、**0件を成功として通知しない設計が必須**。
  利用者は「変化がなかった」と受け取り、報告してこない
- 見積もり時、対象サイトが JS 描画かどうかで工数と依存関係が変わる。
  **契約前に「ページのソースを表示」で確認する**

## 一般化

- **例外が出ないことは、正しく動いたことを意味しない。**
  Phase A で踏んだ落とし穴の約半数がこの型
- **部分的に成功するケースが最も危ない。** 今回はページ送りだけが動いたため、
  「巡回は成功」という誤った手応えが出た。全部失敗していれば気づけた
- 取得系の処理では、**成功の定義に件数の下限を含める**必要がある
