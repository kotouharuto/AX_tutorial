# 外部API失敗のリトライ設計（本体は「再試行しない条件」の方）

- **ブロック：** A-1
- **日付：** 2026-08-26
- **一般性：** どの環境でも（外部 API を叩く全実装）
- **溶かした時間：** 約 0.7 時間

## 前提：狙って起こせない

429（レート制限）も 503（一時障害）も、**意図的に起こそうとしても起きない。**
150件を実処理しても一度も出なかった（1件4.1秒 ≒ 15 RPM で、無料枠の制限に届かない）。

一方で 404 は**何もしていないのに起きた**
（→ [モデル名の腐敗](a1-gemini-model-name-rot.md)）。
**起きてほしいものは起きず、起きてほしくないものが起きる。**

## 検証方法：fetch を差し替え可能にする

実際に起きないものを「実装した」で済ませると、本番で初めて起きたときにバグが分かる。
そこで `fetchWithRetry_(url, options, maxAttempts, fetchFn)` の第4引数に
fetch の実装を注入できるようにし、任意のステータス列を返すスタブで検証した。

**本番コードのリトライ経路をそのまま通すこと**が重要。
実験用に別実装を書くと、検証したものと動くものが別物になる。

スタブは `getResponseCode` と `getContentText` の2つだけ実装すれば足りる。
リトライ処理がその2つしか使っていないため。

## 検証結果

| 1 | 503 → 429 → 200 で3回目に成功 | OK（呼び出し3回・2952ms） |
| 2 | 401 で**1回**で諦める | OK（呼び出し1回） |
| 3 | 上限3回で諦める | OK（無限リトライではない） |
| 4 | 待機が指数的に伸び、ジッターで散る | OK（下記） |

```
4回目の待機: 9007, 4425, 9185, 4847, 5627 ms（幅 4425〜9185）
```

## 設計の要点

### 1. 本体は「再試行しない条件」の方

```js
function isRetryableStatus_(status) {
  // 429: レート制限、5xx: サーバ側の一時障害。時間を空ければ回復しうる。
  return status === 429 || (status >= 500 && status < 600);
}
```

| ステータス | 扱い | 理由 |
|---|---|---|
| 429, 5xx | 再試行 | 時間を空ければ回復しうる |
| 400, 401, 403, 404 | **即座に諦める** | こちらの誤り。何度投げても直らない |

**検証2の「呼び出し1回」が最も重要な確認項目。**
ここが2回以上なら、直らないエラーでクォータを浪費している。
何でも再試行する実装は、障害時にクォータを食い潰して**復旧を遅らせる。**

### 2. 諦める条件を必ず持つ

GAS には日次クォータ（`UrlFetch` 呼び出し回数）がある。
**無限リトライは書かない。** 諦めた後は通知に回す。

### 3. ジッターを必ず入れる

```js
const base = RETRY_BASE_MS * Math.pow(2, attempt - 1);
// 待機時間が揃っていると、同時に失敗した実行が同時に再試行して再び衝突する。
return Math.round(base * (0.5 + Math.random()));
```

多重起動の実験で見たとおり、**複数の実行は現実に並行する。**
それらが同時に 429 を受けると、固定待機では再試行も同時になり、また 429 になる。

**観察：** 3回目（3474〜5240ms）と4回目（4425〜9185ms）の範囲は**重なる。**
ジッター幅が 0.5〜1.5 倍のため、4回目が3回目より短くなることがある。
「必ず間隔が伸びる」わけではない点は理解した上で使う。
厳密に単調増加させたいなら、前回の待機時間を下限に使う方式にする。

## 通知との組み合わせ

リトライで回復しなかったものは、**業務側から見える場所に出す。**
今回は行ごとに失敗理由をシートへ記録し、`FALLBACK_TO` へ通知した。
404 のときにこれが実際に機能し、原因の特定に直結した。

**リトライは「気づかなくてよくする」仕組みではない。**
回復できなかったときに確実に気づける経路とセットで初めて意味を持つ。

## 他人の環境に納品するときの含意

- **リトライ回数と待機時間は、相手の API クォータを踏まえて決める。**
  無料枠と有料枠でレート制限が違う（→ [無料枠の条件](a1-gemini-free-tier-data-use.md)）。
- 「リトライしています」は運用者にとって**何も言っていないに等しい。**
  何回試して、諦めたらどうなるかを引き渡しドキュメントに書く。
- 429 が頻発する状態は設計の問題（処理間隔・並列度）であって、
  リトライで隠すべきものではない。**リトライは一時障害のための仕組み。**
