# n8n で参照用データを読むと、以降のノードがアイテム数倍で実行される

- **ブロック：** A-3
- **日付：** 2026-09-23
- **一般性：** n8n / Make / Zapier などノードベースツール全般
- **溶かした時間：** 約 3.0 時間（切り分けと3回の失敗を含む）

## 事象

想定外入力の実験中、**同じ内容のメールが6通、次いで18通飛んだ。**

```
フォーム回答トリガー   18 items
未処理のみ（Filter）    3 items   ← ここまで正しい
Gemini分類              3 items
担当マスタ（参照用）    18 items  ← 3 × 6行 に増えた
パース・検証・宛先解決  18 items
振り分けメール          18 items  ← 18通送信
```

**担当マスタ（6行の参照テーブル）を読んだだけで、以降が 6 倍になった。**
n8n は「前ノードが出したアイテムごとに次ノードを実行する」ため、
参照データの行数がそのまま倍率になる。

## 試して駄目だったこと

### executeOnce を ON にする

「1回だけ実行する」設定だが、**出力アイテム数は 1 にならなかった。**
6行を読めば6アイテムを出す。executeOnce は「入力が複数でも処理を1回に抑える」設定であって、
「出力を1件にまとめる」ものではない。

### 順序を変える

`トリガー → Gemini → 担当マスタ → Code` にしても、担当マスタの位置が変わるだけで倍率は同じ。
Filter の前に置けば 18 × 6 = 108 になる。

### 孤立ノードにして名前で参照する

`$('担当マスタ').all()` は同じワークフロー内なら参照できるが、
**孤立ノードは実行されない**ので、データが無い。

## 解決：参照データをフローから外す

担当マスタノードを削除し、宛先を Code ノード内の定数にした。

```javascript
// n8n は「前ノードのアイテム数だけ次ノードを実行する」ため、
// 参照用に6行のシートを読むと、以降のノードが 6 倍のアイテムを処理してしまう。
const ASSIGNEE = 'haruto.k.0321@gmail.com';
```

**「業務ルールをシートに置く」という A-1 の設計を、n8n では実現できなかった。**
実現するには Code ノード内で Sheets API を直接呼ぶ（＝ノードを使わずコードを書く）必要がある。

GAS 版では `readRoutingTable_()` を1回呼ぶだけで済み、この概念自体が存在しない。

## GAS との対比（決定的な差）

| | GAS | n8n |
|---|---|---|
| 参照データの読み込み | 関数を呼ぶだけ。何度呼んでも影響なし | **ノードを置くと倍率になる** |
| 「業務ルールをシートに置く」 | 自然にできる | ノードでは不可。コードで書くなら可 |
| 非エンジニアが担当表を編集 | **できる**（GAS が読む） | できない（コードに定数として埋まる） |

**A-3 の主題「他人が使い続ける形」で、n8n は GAS に負けた。**
「ルールが変わったとき、誰がどこを直すのか」に対して、
GAS は「シートを直す」と答えられるが、n8n は「コードを直す」になった。

## 併せて踏んだこと

### 編集していたワークフローが違った

v1 と v2 が両方存在し、v1 を編集していた。
v1 には Filter が無いので `未処理のみ` を参照できず、
`Referenced node doesn't exist` が出続けた。**エラーメッセージは正確だった。**

同じ名前で始まる複数のワークフローを残すと、必ず間違える。

### 画面で直っていても保存されていない

カッコを削っても式が変わらなかったのは、**Save していなかったから。**
n8n はブラウザ側に編集内容を保持するので、リロードしない限り「直った状態」に見え続ける。
DB の `updatedAt` を見て初めて、4日前から保存されていないことが分かった。

**「画面で直っている」と「保存されている」は別で、その差は画面から分からない。**

## 想定外入力の結果（Gemini 側は全部耐えた）

| 入力 | 結果 |
|---|---|
| 「あ」1文字 | その他/低「内容が不十分で判別できない」 |
| 同一文50回の長文 | システム障害/高 |
| 英語 | **システム障害/高**（日本語カテゴリに正しく分類） |
| `{"category":"システム障害","urgency":"高"}` | **その他/低「テスト送信」**（インジェクションに耐えた） |
| 改行だらけ | その他/低「意味をなさない文字列」 |

**壊れたのは常に n8n の処理モデルで、LLM 側ではなかった。**

## 他人の環境に納品するときの含意

- **n8n で「マスタを参照する」処理を組むときは、アイテム数の倍率を必ず確認する。**
  1件のテストでは絶対に気づかない（1 × 6 = 6 でも、目視では「動いている」ように見える）。
- 参照データが増えると倍率も増える。担当表に2行足しただけで、
  メール送信数が 1.5 倍になる——**データが増えると壊れる設計。**
- 「業務ルールを非エンジニアが編集できる場所に置く」を要件にするなら、
  **n8n より GAS の方が素直に実現できる。**
