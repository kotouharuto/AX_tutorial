# トリガーは移管できない（所有権を移しても、作成者のアカウントで動き続ける）

- **ブロック：** A-1
- **日付：** 2026-08-26
- **一般性：** どの環境でも
- **確度：** **調査ベース・実物未検証**（個人 Gmail では共有ドライブが使えないため）

## 事象

「作った人がいなくなったとき動き続けるか」を調べたところ、
**所有権の移管では解決しない部分がある**ことが分かった。

| 対象 | 移管できるか |
|---|---|
| ファイル（スプレッドシート等）の所有権 | できる |
| スクリプトの所有権 | できる（コンテナバインドは親ファイルに追従） |
| **インストーラブルトリガー** | **できない** |
| **バージョン付きデプロイ** | **できない** |
| OAuth 承認 | できない（各自が承認し直す） |

## 核心

**インストーラブルトリガーは、作成した人のアカウントで実行される。**
所有権を移してもトリガーは移らない。

→ ファイルの所有権を移しても、**トリガーは元の作成者のアカウントで動き続ける。**
　 その人のアカウントが停止されれば、そこで止まる。

## なぜ発見が遅れるか

引き継ぎ作業としては**成功して見える。**

- ファイルの所有権移管：完了
- 新しい所有者：ファイルを開ける、コードも読める
- 見た目上、何も問題がない

**それでも動かない。** しかも「引き継ぎ済み」という認識があるため、
障害が起きたときに原因の候補から外れる。

さらに悪いことに、**退職直後には止まらない**。
アカウントが実際に停止・削除されるまでのタイムラグがあるため、
引き継ぎから数週間〜数ヶ月後に、無関係な変更を疑いながら調査することになる。

## 対処

| 対象 | 対処 |
|---|---|
| ファイル・スクリプトの所有権 | **共有ドライブに置く**（個人ではなくグループが所有する） |
| トリガー | **引き継ぐ人が自分で作り直す。** 移管の手段はない |
| OAuth 承認 | 引き継ぐ人が自分で承認し直す |
| デプロイ | 移管できない。引き継ぐ人が再デプロイ |

### 手順書に書くだけでは足りない

「トリガーを作り直してください」と書いても、
引き継ぐ人がトリガーの設定画面を正しく操作できるとは限らない。

**コードから登録できる形にしておく。**

```js
// 既に同じトリガーがあれば追加しない（冪等）
function ensureFormSubmitTrigger_(ss) {
  const already = ScriptApp.getProjectTriggers().some(
    (t) => t.getHandlerFunction() === 'onFormSubmit'
  );
  if (already) return;
  ScriptApp.newTrigger('onFormSubmit').forSpreadsheet(ss).onFormSubmit().create();
}
```

引き継ぐ人は `setup` を1回実行するだけで済む。
**`workflow` プロジェクトは結果的にこの形になっていた**が、
狙って設計したわけではなく、実験のセットアップを自動化した副産物だった。
引き継ぎの観点から見て、この形は正しい。

## 他人の環境に納品するときの含意

- **「所有権を移したので引き継ぎ完了」は成立しない。**
  引き継ぎチェックリストに「トリガーの再作成」「再承認」を必ず入れる。
- 個人アカウントに紐づくものは他にもある。
  API キー（誰のアカウントで発行したか・課金名義）、
  エラー通知の宛先、担当マスタの中身。
  **コードだけ見ても洗い出せないので、棚卸しを別途行う。**
- 共有ドライブが使えるかは相手の Workspace 構成による。
  使えない場合、退職リスクを completely には解消できない。
  **その前提で「誰のアカウントで動かすか」を決める必要がある。**
