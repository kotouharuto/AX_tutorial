# エラー検知：同じ障害で GAS は「届く」、n8n は「見に行かないと分からない」

- **ブロック：** A-3
- **日付：** 2026-09-18〜19
- **一般性：** どの環境でも
- **溶かした時間：** 約 1.5 時間（GAS 側の自然発生障害の切り分け含む）

## 実験

Gemini の API キーを末尾1文字削って無効化し、フォームから送信した。GAS 版と n8n 版で比較。

| | GAS 版 | n8n 版（初期状態） | n8n 版（Error Workflow 追加後） |
|---|---|---|---|
| 失敗の記録 | シートの状態列「エラー」＋詳細列に 401 全文 | Executions タブ | 同左 |
| **能動的な通知** | **メールが届く**（試行 1/4 で諦めた旨も） | **なし** | **メールが届く** |
| 気づく条件 | 受信箱を見る | n8n の画面を開いて Executions を見る | 受信箱を見る |

差は技術の優劣ではなく、**エラー経路を設計したかどうか**。
n8n にも Error Workflow の仕組みがあり、設定すれば同等になる。A-1 で設計した経路を移植し忘れていた。

## n8n の Error Workflow で踏んだ2件

### Error Workflow はテスト実行では動かない

「Execute workflow」で手動実行して失敗させても、Error Workflow は起動しない。
**本番実行（トリガー起動、mode=trigger）のエラーでしか呼ばれない。**

「テストで通知を確認してから本番へ」ができない。
Publish して、実際にトリガーを発火させて初めて検証できる。

### ワークフローが Unpublish されたままだった

GAS 版の実験のために Active を OFF にし、戻し忘れていた。
Active=0 ではポーリングが動かず本番実行が発生しないため、手動実行しかできず、
上の制約と合わさって「何をしても通知が来ない」状態になった。

**n8n の「Publish」に相当するものは GAS では「トリガー登録」。**
GAS は setup を1回実行すれば以後は勝手に動くが、n8n は Active を明示的に管理する必要がある。

## 実験前に自然発生していた障害（「ルール変更」の実例）

### シート名の変更で GAS が黙って止まっていた

n8n の制約（シート名にスペース不可）で `フォームの回答 1 → 回答` に変えた時点で、
GAS の `getSheetByName('フォームの回答 1')` が `null` を返し、`processRow_` の冒頭で throw していた。

**その throw は `handleFailure_` の外**なので、通知経路に乗らない。
「エラーは握り潰さない」「通知経路に流す」と設計したのに、**通知経路の手前で落ちる例外があった。**
A-1 の設計の穴。

### setup がフォームを増殖させた

`createInquiryForm_` を冪等にしていなかった。setup を再実行するたびにフォームが増え、
Google Forms が回答先シートを「フォームの回答 2」「フォームの回答 3」と分裂させた。
新しいフォームから送ると別シートに入り、GAS は `回答` を見ているので**黙って処理されない。**

担当マスタとトリガーは「作成済みならスキップ」にしたのに、フォームだけ漏れていた。
→ フォーム ID をスクリプトプロパティに保存して冪等化。

### 2つのシステムが同じシートを監視すると、先着が勝つ

GAS のトリガーが残ったまま n8n を動かしたら、GAS が即時処理して状態列を埋め、
n8n は1分後に「処理済み」と判定して止まった。冪等性チェックは正しく機能したが、
**後発から見れば「なぜか動かない」にしか見えない。**

もし GAS 側が壊れていたら、n8n は「GAS がエラーにした行」を処理済みとしてスキップする。
**フォールバック構成のつもりで2つ動かしても、片方が壊れたときにもう片方はリカバリしない。**

## 切り分けで踏んだこと：SQLite の WAL

n8n の DB（SQLite）を `docker cp` でコピーして見たら、**4日前のスナップショット**だった。
SQLite は WAL モードで、直近の変更は `database.sqlite-wal` にあり、
メインファイルは checkpoint まで更新されない。`-wal` と `-shm` も一緒にコピーする必要がある。

「DB を直接見れば確実」と思っていた手段が、コピーの仕方で嘘をつく。
Dify（PostgreSQL）では起きなかった。

## 他人の環境に納品するときの含意

- **エラー通知は、ツールの標準機能ではなく設計項目。** GAS でも n8n でも「設定しなければ届かない」。
- 通知経路の**手前で落ちる例外**を潰す。`try` の外にある処理（シート取得など）が失敗すると、
  通知経路そのものが機能しない。
- **セットアップ関数は全部冪等にする。** 1つでも漏れると、再実行が新しい障害を生む。
- 同じデータソースを複数のシステムで監視しない。するなら「どちらが正か」を決め、
  もう片方は監視専用にする。
