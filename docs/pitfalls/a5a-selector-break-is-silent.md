# セレクタが合わなくなっても例外は出ない。件数が正常なまま中身だけ空になる

- **ブロック：** A-5a
- **日付：** 2026-09-27
- **一般性：** BeautifulSoup / Playwright / lxml など、セレクタで抽出する実装すべて
- **溶かした時間：** 0 h（意図的に壊して観察した）

## 事象

サイト改修でクラス名や階層が変わる状況を模し、**同じ HTML** に対して
4通りのセレクタで抽出した。

| ケース | 件数 | 書名が空 | 価格が空 | 例外 |
|---|---|---|---|---|
| 正しい | 20 | 0 | 0 | なし |
| クラス名が変わった | **0** | 0 | 0 | なし |
| 階層が1段増えた | **20** | **20** | 0 | なし |
| 価格だけ変わった | **20** | 0 | **20** | なし |

**4ケースすべてで例外が出ない。**

`select()` は一致しなければ空リスト、`select_one()` は `None` を返すだけ。
`if link else ""` のような素朴な書き方をしていると、
**欠損が空文字として正常に記録される。**

## 差分検出と組み合わせると全て沈黙する

「前回＝正しい結果」「今回＝壊れた結果」として比較した。

| ケース | 追加 | 削除 | 素朴な差分通知の判定 |
|---|---|---|---|
| クラス名が変わった | 0 | 20 | 差分なし（通知されない） |
| 階層が1段増えた | 0 | 20 | 差分なし（通知されない） |
| 価格だけ変わった | **0** | **0** | 差分なし（通知されない） |

「追加された分だけ通知する」実装では**3ケースすべてが無通知**になる。

3番目が最も危ない。書名は正しく取れているので**差分キーが一致し、追加0・削除0**。
件数も20で正常。それでいて価格が全件空。
価格の変動を監視する目的だったなら、**監視対象だけが静かに失われている。**

## 対処

### 件数だけでは足りない

「0件または急減を異常とする」という監視は、**3ケース中1ケースしか捕まえられない。**
件数が正常なまま中身が空になる壊れ方があるため。

必要な判定は3つ。

| 判定 | 捕まえるケース |
|---|---|
| 件数が0 | クラス名が変わった |
| 前回比の急減 | ページ送りが途中で切れた |
| **フィールドごとの空率** | 階層が増えた／価格だけ変わった |

空率の閾値は 0% ではなく 5% にした。
1件だけ欠けるサイト側の事情はあり得るため。
観察した壊れ方は**空率100%**なので、この閾値でも確実に捕まる。

### 異常時は前回値を更新しない

急減判定の基準に異常値を使うと、次回から判定が効かなくなる。

```
1000件 → 0件（異常）→ 0件を前回値として記録
       → 次回も0件 → 「前回比100%」で正常扱い
```

**異常を1回見逃すと、以降ずっと見逃す。** 異常時は記録を止める。

### 「フィールドが無い」と「空」を区別する

実装後、自分でフィールド名を打ち間違えて誤警報を出した
（`price` と指定したが実際のキーは `detail`）。
判定としては正しい（fail-loud）が、**セレクタ破壊と指定ミスが同じ文言**になり、
原因の切り分けに手間がかかる。

```
- price というフィールドが存在しない（実際のキー: detail, source_url, title）
- detail が空の割合 100%（閾値 5%）
```

キーが全件に無ければ指定ミス、一部にあるならセレクタ破壊。**対処が違うので文言を分ける。**

## テストで見つかった別の不具合

テストを書いた副産物として、既定引数の束縛タイミングの問題が出た。

```python
def load_state(path: Path = STATE_PATH) -> dict[str, int]:
```

既定引数は**関数定義時**に評価される。そのため呼び出し側でモジュール属性
`STATE_PATH` を差し替えても効かず、**テストが本物の状態ファイルを読み、
`--update-state` なら書き込む**ところだった。

テストが実データに触れると、実行順で結果が変わる。
`main()` から明示的に渡す形に直した。

**`validate()` 単体のテストでは出ず、CLI のテストを書いて初めて出た。**

## 納品時の含意

- **「動いています」の根拠を件数にしない。** 件数が正常でも中身は壊れうる
- 定期実行の監視には、**取得件数・必須フィールドの空率・前回比**の3点が要る
- 顧客は「通知が来ない＝正常」と受け取る。**沈黙を正常の合図にしない設計**が必要

## 一般化

- **部分的に成功するケースが最も危ない。** 全部失敗すれば気づける
- 差分検出は「変化を見つける」仕組みであって「壊れを見つける」仕組みではない。
  **壊れると差分が出なくなる**ので、差分の有無で健全性を判断できない
- 監視の設計は、**先に壊して観察してから決める**。
  今回は件数だけの監視で十分だと考えていたが、実測で否定された
