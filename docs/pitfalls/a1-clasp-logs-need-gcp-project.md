# clasp から実行ログが見えない（GCP project ID is not set）

- **ブロック：** A-1
- **日付：** 2026-08-25
- **一般性：** どの環境でも（標準 GCP プロジェクトのまま作った全スクリプト）
- **溶かした時間：** 約 0.1 時間

## 現象

「メールが届かない」の切り分けで実行ログを見ようとしたら失敗した。

```
$ clasp tail-logs
GCP project ID is not set, unable to continue.
```

## 原因

`clasp tail-logs` は **Cloud Logging** を読む。しかし clasp で新規作成したスクリプトは
Google が自動割り当てする**標準 GCP プロジェクト**に紐づいており、
その ID は開発者から見えず、Cloud Logging も参照できない。

ログを CLI から読むには、スクリプトを**自前の GCP プロジェクトに切り替える**必要がある。

## 影響（軽視できない）

**「ローカルで書いて push する」ワークフローは、ログだけブラウザに戻される。**
clasp を入れた目的の半分（CLI で完結する）がここで崩れる。
`console.log` を書いても、読むのは Apps Script エディタの実行ログ画面。

## 対処

**当面：** ブラウザの Apps Script エディタで「実行数」画面と実行ログを見る。
最小構成の検証段階なら、GCP プロジェクトを立てるコストの方が高い。

**必要になったら：** 自前の GCP プロジェクトを作成し、
`clasp open-api-console` / `setup-logs` から紐づける。
自前プロジェクトが要るのは他にも `clasp run-function`（CLI から関数実行）。
**CLI から実行とログ確認までやりたくなった時点が、切り替えの分岐点。**

## 切り分けの代替手段（ログが見られないとき）

外形から事実を取りにいく。今回は「送信されたか」を Gmail 側から確認した。

- Gmail の**送信済み**を件名で検索 → 0件なら `sendEmail()` に到達していない
- 0件なら原因は実行側（関数が走っていない / 手前で例外）に絞れる

**ログが無くても、副作用の有無で切り分けられる場所を作っておく**のは設計の話でもある。

## 他人の環境に納品するときの含意

- 標準 GCP プロジェクトのまま納品すると、**障害時にログを追う手段が
  「エディタを開ける人」に限定される。** 非エンジニアには実質不可能。
- A-3 の「エラーが起きたとき誰がどうやって気づくのか」に直結する。
  ログに頼らず、**シートへの記録やメール通知など、業務側から見える経路**に
  失敗を出す設計が要る。ログは開発者のためのものであって、運用者のためのものではない。
