# 承認画面は読まれない（権限の説明を承認画面に依存できない）

- **ブロック：** A-1
- **日付：** 2026-08-26
- **一般性：** どの環境でも（人間の挙動の話なので技術に依存しない）
- **溶かした時間：** 再承認のやり直しで約 0.1 時間

## 事象

配置パターンの比較実験で、コンテナバインド版とスタンドアロン版の
**承認画面の文言の差**を確認するのが目的だった。

にもかかわらず、**承認画面を読み飛ばして承認した。**

## なぜこれが重要か

読み飛ばしたのは、A-1 で**スコープに最も時間をかけた本人**である。

- `oauthScopes` を自動推論に任せず1つずつ手で書いた
- `MailApp` で権限が1つ増えたことを検知して削除した
  （→ [記録](a1-gas-mailapp-vs-gmailapp-scope.md)）
- 各スコープの必要理由を表にまとめた

**それでも読み飛ばした。**
承認画面は「作業を始める前に出てくる邪魔なもの」であって、
権限を検討する場として機能していない。

**納品先の利用者はもっと読まない。**

## 結論

### 1. 権限の説明を承認画面に依存できない

引き渡しドキュメントに「この仕組みが要求する権限と、その理由」を明記する。
承認画面で伝わることを前提にした設計は成立しない。

情シスや管理者に説明を求められるのは、**承認から数ヶ月後**であることも多い。
そのとき参照されるのは画面ではなくドキュメント。

### 2. だからこそスコープを絞る意味がある

読まれない画面で広い権限を通せば、誰も気づかないまま許可される。
**気づかれないからこそ、実装側が絞るしかない。**

「承認画面に出るから利用者が判断できる」は成り立たない。
権限設計は利用者のチェックを当てにせず、こちらで完結させる責務がある。

## 再現方法（承認画面をもう一度見る）

1. [myaccount.google.com/permissions](https://myaccount.google.com/permissions) を開く
2. 対象のスクリプト名を探す
3. 「アクセス権を削除」
4. 再度スクリプトを実行すると承認画面が出る

**検証手順に「承認画面を読む」が含まれる場合、
先に取り消し手順を用意しておく。** 一度承認すると二度と出ないため、
「後で見よう」ができない。

## 他人の環境に納品するときの含意

- 引き渡しドキュメントに**権限とその理由の一覧**を入れる（承認画面の代わり）。
- 権限を追加する変更をしたら、**利用者に明示的に伝える。**
  再承認画面が出ても気づかれない前提で運用する。
- 「承認したのだから同意している」は実態と乖離している。
  広い権限を要求しておいて後から問題になったとき、
  承認記録は説明の根拠として弱い。
