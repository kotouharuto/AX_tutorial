## 2. 作業原則（全ブロック共通）

### 2-1. 到達条件で進める
期間ではなく、各ブロックの到達条件（チェックリスト）で進める。
**条件を満たしたかの最終判断はユーザーが行う。** Claude は「満たしたと考える根拠」と「ユーザーが確認する方法」を提示するところまで。

### 2-2. 落とし穴を先回りして回避しない
本書で「観察対象」と書いた箇所は学習の中心である。
1. まず素朴な実装で動かす
2. 壊れ方・誤った結果をユーザーに見せる
3. 原因を説明し、ユーザーの了承を得てから直す

回避策を最初から入れたくなった場合は、実装せずに「提案」として止まること。

### 2-3. 成功表示を信用しない
終了コード0、例外なし、画面上の表示だけで「完了」と報告しない。
報告時は**出力の中身を確認する具体的な手段**（ファイルの該当セル、件数、ログの該当行など）を併記する。

### 2-4. 正解データはユーザーが確認する
期待値・評価データ・テストの正解を生成した場合は「未確認」と明記し、ユーザーの確認後に確定扱いにする。

### 2-5. 生成テキストの混入チェック
日本語のテストデータを生成したら、キリル文字・ハングル等の想定外の文字が混入していないか機械的に検査する（Phase A で3回発生）。
「意図的に汚したデータ」は README に一覧で明記し、意図しない汚れと区別できるようにする。

### 2-6. 実測値を残す
見積もりに使うため、処理件数・所要時間を記録する。構築時間はユーザーに申告してもらい progress.md に残す。

### 2-7. ハマりポイントの記録
`docs/pitfalls/` の既存形式に合わせて追記する。**書く前に既存ファイルを読んで形式を確認すること。**

### 2-8. 秘密情報
API キー・トークン類はコードにもコミットにも含めない。`.env` と `.gitignore` を使い、`.env.example` を用意する。

### 2-9. セッションの進め方
- 開始時：progress.md を読み、今回の作業計画を短く提示し、ユーザーの承認を得てから着手
- 終了時：progress.md を更新（やったこと・到達条件の状態・次にやること・未解決の疑問）
- Python の環境管理やディレクトリの流儀は既存プロジェクトに合わせる。不明ならユーザーに確認

## 4. A-4：Python バッチ（Excel＋ファイル処理）　目安6時間

**題材**：支店別に届く月次の問い合わせ集計 Excel（5ファイル程度）を結合し、書式付きの報告帳票（xlsx）を出力する。あわせて支店別 PDF の結合と、命名規則に沿ったリネームを行う。

**テストデータ**（生成スクリプトで作成）に含める汚れ：
- 全角・半角の混在
- 結合セル
- 日付の文字列とシリアル値の混在
- 途中の空行
- 数式セル
- cp932（Shift_JIS）の CSV を1本

**到達条件**
- [ ] 上記の汚れをすべて正しく処理できる（期待値はユーザー確認済み）
- [ ] 数式セルの読み込み挙動を観察し、記録した
- [ ] Windows 環境（GitHub Actions の windows-latest）でテストが通る
- [ ] Python 未導入の PC 向けの配布方法を設計し、手順書を書く
      → **Windows 実機がないため実機検証は未実施**。固有のリスクを README に列挙する
- [ ] Claude Code の外の環境で実行を確認した（**ユーザーが実施**・macOS 上で可）
- [ ] 実測：ファイル数×行数と処理時間

**観察対象**
- openpyxl で数式セルを読んだときの値（`data_only` の有無、Excel で一度も保存されていないファイルの場合）
- 文字コードを指定せずに cp932 の CSV を読んだときの挙動
- 日付の混在が集計結果に与える影響

## 5. A-5a：スクレイピング　目安5時間

**対象は練習用サイトのみ**（books.toscrape.com、quotes.toscrape.com）。それ以外のサイトへのアクセスは必ずユーザーの承認を得る。アクセス間隔は1秒以上空ける。

**到達条件**
- [ ] 静的ページを取得できる（requests＋BeautifulSoup）
- [ ] JavaScript で描画されるページを取得できる（Playwright）
- [ ] 定期実行し、前回との差分だけを通知できる
- [ ] 取得件数が0件または急減したとき、成功ではなく異常として通知する（セレクタを意図的に壊して確認）
- [ ] 受注判断基準 `acceptance-criteria.md` がある（利用規約、robots.txt、アクセス間隔、ログインの要否、個人情報の有無）
- [ ] 実測：1ページあたりと全件の所要時間

**観察対象**
- セレクタが合わなくなったとき、0件のまま正常終了すること
- JS 描画ページを静的取得したときに空の結果が返ること

## 6. A-5b：Slack Bot　目安7時間

テスト用の Slack ワークスペースを使う。Bolt for Python の Socket Mode で、公開 URL なしで動かす。

**到達条件**
- [ ] Slack から問い合わせ文を送ると、A-1 の分類結果が返る
- [ ] LLM の処理が遅くてもタイムアウトしない
- [ ] 振り分け通知を Slack に流せる
- [ ] 処理失敗時の通知経路がある（A-1 と同じ考え方）
- [ ] スコープ追加時の手順が引き渡し文書に書かれている

**観察対象**
- 最初は LLM 呼び出しを同期で待ってから応答する実装にし、タイムアウト時の挙動を確認する
- スコープを追加し、アプリを再インストールする前の挙動を確認する

## 7. A-6a：MCP サーバー　目安5時間

公式の Python SDK を使う。公開するツール：
- 社内文書検索（A-2 のコーパスと検索を再利用）
- 問い合わせ記録シートの参照（A-1 のシート）

Claude Desktop と Claude Code の両方から接続する。

**実装前の確認**：SDK と各クライアントの設定方法は変更が速い。実装前に公式ドキュメントで現行の書き方を確認し、確認した URL と日付を README に残すこと。

**到達条件**
- [ ] ツールが2つ以上ある
- [ ] 失敗時に、Claude が理解して利用者に説明できるエラーを返す
- [ ] 認証情報を環境変数から読む
- [ ] Claude Desktop と Claude Code の両方で動作する

**観察対象**
- stdio 方式で標準出力にログを出したときの壊れ方

## 8. A-6b：Claude Code 導入キット　目安5時間

ユーザーが普段使っている Claude Code の設定を、**他のチームに渡せるパッケージ**にする。

**含めるもの**
- CLAUDE.md の雛形
- 権限設定
- よく使うカスタムコマンド
- MCP 設定（A-6a を例に）
- 導入手順書
- チーム向けの30分程度の説明資料
- 運用ルール（秘密情報の扱い、生成コードのレビュー方針）

**到達条件**
- [ ] 手順書だけを見て、新規リポジトリに30分以内で同じ環境を再現できる
- [ ] 説明資料がある
- [ ] 機能に関する記述が公式ドキュメントと照合済み

**Claude の役割は下書きと整合性チェックまで。**
再現確認は**ユーザーが手順書だけを見て手作業で行う**。Claude Code が確認すると、手順書の抜けを文脈から補って成功してしまうため、検証には参加しない。
