## 1. 何をやったか

題材は Phase A と同じ架空企業の問い合わせ業務に揃え、A-1 の分類処理と A-2 の文書コーパスを再利用した。
各ブロックとも「素朴な実装で壊れ方を見てから直す」順で進めた。

**A-4　Python バッチ（Excel＋ファイル処理）**
支店別の月次集計 Excel 5本を結合し、書式付きの報告帳票を出す。支店別 PDF の結合とリネームも行う。
テストデータには汚れを9種仕込んだ（全角半角の混在・結合セル・日付の文字列とシリアル値の混在・空行・数式セル・
cp932 の CSV など）。Windows 実機が無いため、GitHub Actions の windows-latest で検証した。
Python 未導入 PC への配布方式を3案比較し、uv の同梱スクリプト方式を推奨とした（exe 化は非推奨）。

**A-5a　スクレイピング**
練習用サイト（books.toscrape.com・quotes.toscrape.com）だけを対象に、静的取得と JS 描画ページの取得、
前回との差分の通知、件数とフィールドの空率による異常判定を作った。macOS の launchd で毎日定期実行している。
受注するかを判断するための基準（利用規約・robots.txt・アクセス間隔・ログイン・個人情報・継続運用）を文書にした。

**A-5b　Slack Bot**
スラッシュコマンド `/inquiry` で問い合わせを受け、A-1 と同じ方法（Gemini・同じプロンプト・温度0）で分類し、
担当チャンネルに振り分ける。失敗したら運用チャンネルに原因と本文を知らせる。
Socket Mode（公開 URL 不要）で動かし、launchd で常駐させている。
到達条件の外で、Slack との接続を見張って切れ続けたら起動し直させる仕組みを足した。

**A-6a　MCP サーバー**
公式 Python SDK（v2）で、社内文書の検索（A-2 のコーパス・BM25）と問い合わせ記録シートの参照（A-1 のシート・
GAS をウェブアプリ化）の2ツールを公開した。Claude Code と Claude Desktop の両方から接続して確認した。

**A-6b　Claude Code 導入キット**
普段の Claude Code の設定を、他のチームに渡せる形にした：CLAUDE.md の雛形と記入例、権限設定、スキル、
MCP 設定、導入手順書、運用ルール、30分の説明資料。公式ドキュメントとの照合記録を付けた。
再現確認は、方針どおり Claude が参加せず、ユーザーが手順書だけを見て行った。

## 3. 何が「黙って」壊れたか

Phase A の総括では、27件の約半数が「成功の表示と実際の状態が食い違う」型だった。
追加ブロックでも同じ型が続いた。ブロックごとに、終了コード0・例外なし・画面上は正常で、実際には壊れていたもの：

| ブロック | 正常に見えたもの | 実際 |
|---|---|---|
| A-4 | 80行の集計が出て正常終了 | 「大阪」と「大 阪」が別の支店として集計されていた。5つの汚れのうちエラーになったのは cp932 だけ |
| A-4 | 数式セルの値 | どの読み方でも実際の値が取れない。保存されていないファイルでは**古い値**が返る |
| A-5a | JS 描画ページを10ページ巡回し終了コード0 | 0件。ページ送りのリンクだけが静的に存在していた |
| A-5a | セレクタが合わなくなっても件数は正常 | 中身だけが空。4通り壊したうち2通りは件数監視では見つからない |
| A-5a | robots.txt の確認で「許可」 | robots.txt が存在しない（404）のを許可と表示していた |
| A-5b | マニフェストに権限を足して保存 | 再インストールするまで効かず、エラーも足す前と同じ |
| A-5b | プロセスは動き続けている | Slack との接続だけが7時間45分壊れていた |
| A-6a | stdio で print しても通信は成功 | 通信路に不正な行が流れていた。クライアントが寛容なだけ |
| A-6a | 個人を特定できる列を除いて返す | 列ずれした行でメールアドレスが別の列に入っていた |
| A-6b | `cp -R` でキットをコピーして終了コード0 | `.claude/` と `.mcp.json` が黙って落ちていた |
| A-6b | 設定ファイルの手編集 | 全角スペース1つで読めなくなり、キー名の打ち間違いはエラーにならず未設定扱い |

対処はどれも、**「正常」の判定を表示ではなく中身で行う**ことだった：変換後の行を出力して突き合わせる、
件数に加えて空率を見る、トークンが今持つ権限をエラーから読み出す、プロセスではなく接続を見る、
値を出さずに設定の中身を検査するスクリプトを作る。

## 4. 各ブロックの中心的な発見

### A-4：壊れるのは「実運用の経路」だけだった

日本語の print が Windows で落ちた。ただし落ちるのは英語ロケール（cp1252）で、
日本語 Windows（cp932）では印字している非 ASCII 文字51種がすべて出せる。
**顧客が日本語 Windows で手で実行すると再現しない。** 壊れるのはタスクスケジューラ経由・出力のリダイレクト・
英語環境で、A-4 は自動で回すバッチなので、壊れる側が実際に使われる経路だった。

Windows 実機が無いことは、検証の質の上限を決めなかった。CI で敵対的な環境変数を強制する方が、
実機を手で触るより確実に見つかる。一方で、**CI を緑にする修正と不具合を直す修正は別物**だった。
ワークフローに `PYTHONUTF8=1` を足せば緑になるが、環境変数は配布先に付いていかない。

エンドポイント保護のスキャンは遅延にとどまらず、xlsx の書き込み中に I/O タイムアウトで異常終了させた。
再実行では通る。「もう一度やったら通った」で片付けると、顧客環境で起きたときに説明できない。
この待ち時間が、配布方式で exe 化（PyInstaller）を推奨しない理由になった。

### A-5a：取得よりも「壊れたことに気づく」方が難しい

取得そのものは静的も JS 描画も半日で動いた。時間を取ったのは2つ。

1つ目は壊れ方の見分け。セレクタ破壊は例外を出さず、件数が正常なまま中身が空になる。
差分検出は、壊れると「差分なし」として沈黙する。件数だけの監視では4通り中2通りを見逃すと実測で分かり、
件数とフィールドの空率で判定する方式に変えた。**沈黙を正常の合図にしない。**

2つ目は動かす場所。launchd では PATH に uv が無い、デスクトップ配下は保護フォルダで読めない、
iCloud の同期対象になる、仮想環境のラッパーが絶対パスを持っている——で3連続失敗し、
最終的にリポジトリごと移動した。

受注判断の基準には、**法的判断はしない**ことと、**公式 API があれば API を提案する**ことを入れた。
セレクタ破壊の検知を作って運用し続ける手間が、そのまま API を使わない代償になるため。

### A-5b：Slack の制約は、すべて「足したのに直らない」に見える

スラッシュコマンドは3秒以内に応答しないと失敗になる。素朴な実装は 2.80 秒で「今日は動いた」。
遅らせて超えさせると、利用者の画面に「失敗しました。もう一度試して」と遅れて届いた結果の**両方**が出た。
言われたとおり再送すると二重登録になる。しかも Bolt のログは「ack を呼ばなかった」「404」と出し、
原因（遅すぎる）を指さない。受信したらすぐ応答し、結果は後から送る形に直した。

権限は3段階（マニフェストに足す → アプリを再インストールする → 投稿先チャンネルに Bot を招待する）
をすべて終えるまで効かない。途中の段階ではエラーが変わらず、エラーに出る権限名とマニフェストに書く名前も違う。
引き渡し文書には、この3段階と各段階のエラー、トークンが今持つ権限を見て区別する方法を書いた。

Gemini が HTTP 402 を返して分類が止まった。キーは正しく、前払いへの切り替えを求められていた。
**同じキーを使う A-1 も止まっていた可能性が高い。** A-1 のモデル名の提供終了（404）と同じく、
外部サービスの都合で昨日まで動いた仕組みが壊れる型。

一晩動かした Bot は、プロセスは生きたまま Slack との接続だけが壊れ続けていた。
利用者からは API の問題に見えた。プロセスの生死の監視では検知できず、
接続を見張って切れ続けたら自分で終了し、launchd に起動し直させる形にした。
終了する時点では通知できないので、記録をファイルに残し、次に接続したときに運用チャンネルへ送る。

### A-6a：個人情報は「列で絞る」では守れず、「伏せる」は誤った情報を作る

問い合わせ記録を返すツールで、個人を特定できる列を除いて返した。テストでは通った。
実データでは、書き込み側の列ずれでメールアドレスが「状態」や「内容」の列に入っており、**漏れていた。
Claude 自身が指摘して発覚した。** しかも私はツールの説明に「個人を特定できる列は含まれない」と、
保証できない保証を書いていた。

値の中のメールアドレスと同じ行の氏名を伏せる形に直すと、今度は**お名前列に日時が入っていた行**で、
日時を名前とみなして `[氏名]` に置き換え、Claude が「日時欄に氏名が入っている」と事実と違う説明をした。
伏せ字は Claude にとって情報になる。最終的に、列ずれと判定した行は内容を出さない形にした。
本文中に書かれた第三者の氏名は伏せられない、という限界は残っている。

技術面では、SDK が v2 になり旧来の書き方は import すらできず、`ToolError` 以外の例外は原因が Claude に届かない。
公式ドキュメントの「stdio で print すると壊れる」は SDK 2.3.0 では再現しなかったが、
**壊れないので入っても気づけない**ため、本番コードに print が無いことを静的に検査した。
GAS のウェブアプリは HTTP ヘッダを受け取れず、常に 200 を返し、デプロイした時点の版に固定される。

### A-6b：作成者は自分の手順書の誤りを見つけられない

ユーザーが手順書を読んだだけで、私の書き間違いが4件出た（パスの調べ方が無い、ドットファイルが `ls` で見えない、
手順が循環している、「CLAUDE.md を埋める」が背景の無い検証では原理的に完了できない）。
**4件とも実行して失敗したのではなく、読んだ時点で意味が取れなかった。** 私は構造を知っているので見えなかった。
方針書が作成者の検証参加を禁じた理由の実例になった。最初これを「欠陥」と書き、
ユーザーに「単にあなたのミスでしょ」と指摘されて「私の書き間違い」に改めた。

公式ドキュメントと照合しても、**利用者のバージョンでは誤り**になる箇所があった。
ドキュメントは最新版の挙動を書いており、テスト環境（2.1.231）では「共有設定の `bypassPermissions` は効かない」が逆だった。
共有設定に書くと全員の確認が外れる、危険側の誤り。

私が作った確認用のチェックリストにも偽陽性が2つあった（導入する人自身の設定に同じルールがあれば、
キットが読まれていなくても同じ結果になる）。

## 5. 通して見えた構造

### 「動くものを作る」より「他人の環境で動くことを確かめる」方が重い

5ブロックとも、作ること自体は短時間で済み、時間は他人の環境・実データ・実際の作業で消えた。

- A-4：英語ロケールの Windows、エンドポイント保護
- A-5a：launchd の PATH、保護フォルダ、iCloud
- A-5b：常駐させた夜間の接続、外部サービスの課金変更
- A-6a：実データの汚れ（列ずれ）、設定ファイルの手編集
- A-6b：初めての人が読むこと、利用者のバージョン

**テストのデータを綺麗に作るほど、この種の問題は見えなくなる。** A-6a の漏れは、テストのデータでは通っていた。

### 私の誤りの多くは「確かめずに書いた」こと

追加ブロックでは、私（Claude）の誤りが繰り返し見つかった。型はほぼ1つで、**確かめていないことを断定して書いた**。

- `SpreadsheetApp` は読み取り専用で動くと書いた（動かない）
- Claude Desktop では uv が見つからないと予測した（見つかった）
- auto モードでも MCP ツールは許可を求めると案内した（求めない）
- Slack の太字が効かない原因をプレーンテキスト扱いと推測した（全角文字との隣接だった）
- ツールの説明に「個人情報は含まれない」と書いた（含まれていた）
- 照合記録に但し書きを残しながら、結論で無視した（バージョン差）

どれも、実機・実データ・実際に読んだ人によって見つかった。
対処として、引き渡し文書では**確かめたことと確かめていないことを書き分け**（【事実】／未確認）、
未確認のものには理由を添える形にした。

### 「誰が気づき、誰が直すか」は技術では決まらない

A-5a の受注判断基準の最後に「異常時の連絡先を最初に聞く」を入れた。
A-5b の引き渡し文書でも、運用チャンネルを誰が見るか、再インストールを誰が承認できるか、
Bot をどのマシンで動かすか、費用を誰が負担するかを【要記入】として空欄にした。
Phase A の A-3 と同じく、**通知の仕組みは作れても、受け取る人は顧客組織の事情で決まる。**
空欄のまま残る項目が、そのまま顧客への確認事項になる。

### 外部サービスの都合で壊れる

Gemini の 402（前払いへの切り替え）、Phase A の Gemini のモデル提供終了（404）、
SDK のメジャー更新（MCP v2 で旧来の書き方が使えない）、ドキュメントのドメイン移動、
Claude Code のバージョンで挙動が逆になる設定。
**作った時点で正しくても、納品後に外から壊される。** 失敗時に原因（HTTP ステータス・権限）まで
運用担当に届ける経路が、このときの切り分けを可能にする。

## 7. 未達・見送り

## 8. 追加ブロックを終えた時点で言えること

**手元にあるもの**

5つの領域（Excel バッチ・スクレイピング・Slack Bot・MCP サーバー・Claude Code 導入）で、
動くものと、それが**どう黙って壊れるか**の実例がある。とくに「件数は正常なのに中身が空」
「プロセスは生きているのに仕事をしていない」「権限を足したのに効かない」は、どれも自分で踏んで、
検知する仕組みまで作った。

他人の環境で壊れる箇所を、実機なしで先に見つける方法がある（CI で敵対的な環境を強制する、
値を出さずに設定を検査する、プロトコル越しにテストする）。

見積もりの説明材料がある。スクレイピングは「ページ数 × アクセス間隔」が支配的、
JS 描画はブラウザ方式の初回が重い、Slack は3秒の期限があり LLM の応答だけで超える。

引き渡し文書の型がある。【事実】と【要記入】を分け、空欄がそのまま顧客への確認事項になる。

**まだ無いもの**

この期間の実作業時間。見積もりの根拠としては、処理時間の実測はあるが構築時間が無い。

初めての人による検証。A-6b で、作成者には自分の文書の誤りが見えないことが分かったが、
直した手順書を初めての人に通したことはない。他のブロックの引き渡し文書も同じ。

Windows 実機と、業務で使われている Slack ワークスペース（管理者の承認や権限の制限がある環境）での確認。
