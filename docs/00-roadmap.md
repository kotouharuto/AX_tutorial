## 4. A-1：GAS と業務システム接続

### 狙い

「AIが良い出力をする」ことと「業務が実際に回る」ことの間には、
接続という溝があります。そこを自力で埋められる状態にします。

### やること

**① 開発環境**

`clasp` でローカルから GAS を書ける状態にする。
ブラウザのスクリプトエディタで書いている限り Claude Code の恩恵を受けられません。

**② 最小の1本**

スプレッドシートを1行読んで、Gmail を1通送る。
`clasp push` から実行できるところまで。

**③ 実務が回る1本**

推奨題材：
```
Googleフォーム受付 → 内容をAPIで分類 → 担当者へ振り分けメール → シートに記録
```

この形に還元できる業務が非常に多いため、1本作れば分類基準の差し替えで転用できます。

実装の勘所：分類部分は JSON で返させて `JSON.parse()` する。
自然文で返させると表記ゆれで必ず壊れます。
プロンプトで「JSONのみ出力、前置き・コードフェンス禁止」と縛った上で、
それでもコードフェンス除去の処理は入れておく。

**④ 4つの落とし穴を意図的に踏む**

ここが A-1 の本丸です。**先に事故っておくのが目的**なので、
うまく動かすことより壊すことを優先してください。

| 落とし穴 | 内容 | 対処の方向 |
|---|---|---|
| 実行時間制限 | 1実行6分で強制終了。100件をAPIに投げれば簡単に超える | 処理位置を `PropertiesService` に保存し、時間監視で中断・再開する分割実行 |
| トリガー多重起動 | 時間主導と編集トリガーが同時に走り二重処理 | `LockService` で排他制御＋処理済みフラグ列。冪等性を意識した設計 |
| 外部API失敗 | 外部APIは落ちる。タイムアウト・レート制限 | `muteHttpExceptions: true` でステータス分岐、429/503 は指数バックオフ。日次クォータがあるので無限リトライは書かない |
| 権限スコープ | 過剰な権限を要求すると納品先で説明できない | `appsscript.json` で最小権限を明示。`gmail.send` で済むなら `readonly` を要求しない |

**⑤ 配置パターンの理解**

コンテナバインド／スタンドアロン／サービスアカウント経由の違い。
**誰のアカウントで動くか**を間違えると、その人が退職した瞬間に止まります。
他人の組織に納品する前提では避けて通れません。

### 完了条件

- [ ] `clasp push` からデプロイ・実行できる
- [ ] 実務レベルの自動化を1本、通しで動かせた
- [ ] 6分制限を実際に超えさせ、分割実行で回避できた
- [ ] トリガー多重起動を意図的に起こし、排他制御で防げた
- [ ] 外部API失敗時のリトライ・エラー通知を実装できた
- [ ] `oauthScopes` を最小権限で書き、各スコープの必要理由を説明できる
- [ ] 3つの配置パターンの使い分けを自分の言葉で説明できる

### 補足：Microsoft 365 側

Power Automate は現時点では**やらない**。
必要になった時点で対応すれば足ります。ここで手を広げると A-1 が終わりません。

## 5. A-2：RAG と評価設計

### 狙い

「ベテランしか知らない」「どこに何があるか分からない」は、ほぼどの組織にもあります。
ただし **RAG の大半は文書の問題であって、技術の問題ではありません。**
実装だけできる人は、汚い文書を前にして止まります。

### やること

**① 評価セットを先に作る**

順序が重要です。**構築より先に評価セットを作ること。**
作ってから測ると、無意識に自分の実装に有利な質問を選びます。

題材文書は50〜100件。自作の架空文書で構いませんが、**わざと汚くする**。
表記ゆれ、スキャン画像PDF、同内容の新旧2版の混在。
綺麗なデータで測った精度は現場で再現しません。

質問30問の内訳：

| 種別 | 問数 | 狙い |
|---|---|---|
| 単一文書で答えられる | 12 | ベースライン |
| 複数文書を横断する | 8 | チャンク戦略の差が出る |
| 表・数値の参照 | 5 | パース品質の差が出る |
| 答えが存在しない | 5 | ハルシネーション検出 |

最後の「答えが存在しない問い」が最重要です。
RAG が嫌われる最大の原因は**それらしい嘘を返すこと**であり、
「分かりません」と言える設計かどうかが実用の分かれ目になります。

**② 3階層を全部作る**

| 方式 | 特徴 | 適する場面 |
|---|---|---|
| NotebookLM / Claude Projects | 構築ゼロ、文書100件程度まで | 「まずこれで十分」と言えるべき場面 |
| Dify | GUI、権限管理あり、運用を他人に渡せる | 継続運用が必要な場面 |
| 自作（LlamaIndex等 + Drive連携） | チャンク・ハイブリッド検索・リランクを制御 | 精度要求が高い場面 |

同じ文書・同じ30問を全方式に通し、数値で比較する。

**③ 効き幅を数値で把握する**

どのパラメータがどれだけ効くかを実測して持っておく。
おそらく**精度差の大半はチャンク戦略と前処理から来て、
埋め込みモデルの差は想像より小さい**はずですが、それを自分の数字で確認する。

### 完了条件

- [ ] 意図的に汚した文書セット（50〜100件）を用意した
- [ ] 30問の評価セットを作り、「答えが存在しない問い」を含めた
- [ ] 3方式すべてを構築し、同一条件で比較した
- [ ] チャンクサイズ・オーバーラップ・検索方式の効き幅を数値で把握した
- [ ] 「分かりません」を返させる設計を実装し、機能することを確認した
- [ ] 3方式の使い分け基準を自分の言葉で説明できる

### 深追いの警告

この領域は面白いので際限なくチューニングできます。
**完了条件を満たしたら、精度が理想に届いていなくても次へ進むこと。**

## 6. A-3：他人が使い続ける形にする

### 狙い

ここが最大の弱点です。
自分用のツールと、他人が使い続ける仕組みは別物です。
「作れる」と「渡せる」の間の距離を埋めます。

### やること

**① 自動化の使い分けを確立する**

n8n（または Dify のワークフロー）で1本組み、GAS との境界を体感する。
目安：Workspace内で完結し相手の資産にしたいなら GAS、
外部SaaSを跨ぎ運用画面が要るなら n8n。
**実際に両方で同じ処理を組んでみて、自分の言葉で境界を言えるようにする。**

**② 非エンジニアに渡せる形に落とす**

A-1・A-2 で作ったものを題材に、Cowork / Projects / Skills として
「その組織専用の作業環境」に組み直す。

社内で作った設計ファイルは持ち込まず、**白紙から書き起こす。**
構成の目安：業務ルール／用語集／判断基準／手順／禁止事項／出力フォーマット。

**③ 運用を想定して壊す**

引き渡し後に起きることを、意図的に起こして対処する。

- 想定外の入力が来たとき、何が起きるか
- 作った人がいなくなったとき、動き続けるか
- 業務ルールが変わったとき、誰がどこを直すのか
- エラーが起きたとき、誰がどうやって気づくのか

**④ 引き渡しドキュメントを書く**

非エンジニアが読んで運用できる粒度で。
これが書けない仕組みは、渡した時点で壊れる仕組みです。

### 完了条件

- [ ] n8n（等）で1本構築し、GAS との使い分けを説明できる
- [ ] A-1/A-2 の成果物を、非エンジニアが使える形に組み直した
- [ ] 副業用のコンテキスト設計テンプレートを白紙から作成した
- [ ] 想定外入力・担当者不在・ルール変更・エラー検知の4点に対処を実装した
- [ ] 非エンジニア向けの引き渡しドキュメントを書いた
- [ ] 実際に他人（同僚・知人）に触ってもらい、詰まった箇所を記録した
