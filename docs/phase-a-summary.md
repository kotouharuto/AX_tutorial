## 4. 各ブロックの中心的な発見

### A-1：落とし穴の大半が「成功したように見える」

15件のうち大半が、エラーを出さずに失敗する型だった。

- `clasp push` が終了コード0で何もしない（非対話シェル）
- OAuth 承認は通るのに何も起きない（エディタが別の関数を選んでいた）
- **承認画面を読み飛ばした**——スコープに最も時間をかけた本人が
- **承認画面は権限を個別に拒否できる**。部分承認で「許可したのに動かない」が起きる
- **トリガーは移管できない**。所有権を移しても元の作成者のアカウントで動き続ける

**強制終了は catch できない。** 落ちてから片付けることは不可能で、落ちる前に自分で止まるしかない——これが分割実行が必要な理由。

### A-2：評価する側が間違っていた

- **評価セットの正解が1問誤っていた**。被評価側の回答で気づいた
- **自動採点が誤答を正解と判定した**。期待値に誤答例を書いていたため
- **測定方法を変えて解決した**。「採点が難しいのは、測るものを間違えているサイン」だった
  （正答率 → 検索 Recall に変えた途端、判定の曖昧さが消え、API 呼び出しもゼロになった）
- 自分の生成データに**キリル文字・ハングルを3回混入**させた。うち1件は「わざと汚した」とコメントに書いていたが単なるタイプミス

### A-3：GUI ツールの方が渡しにくかった

| 「ルールが変わったとき誰が直すか」 | GAS | n8n |
|---|---|---|
| 担当者を変える | **シートを直す**（非エンジニア可） | **コードを直す**（技術者のみ） |

n8n は参照テーブル（6行）を読むだけで以降の処理が6倍実行され、同じメールが18通飛んだ。
`executeOnce` でも解決せず、宛先をコードに定数として埋めるしかなかった。

- **n8n の OAuth は7日で失効して止まった**（テストモード）。本番運用には**公開されたホームページとプライバシーポリシー URL** が必要
- **Error Workflow はテスト実行では動かない**。本番でしか検証できない
- **「外す」と決めた文書が投入されていた**。旧版を外しただけで矛盾5問が正答に変わった

## 5. 通して見えた構造

### 5-1. 失敗は失敗として現れない

27件のうち約半数が「成功の表示と実際の状態が乖離する」型だった。

```
clasp push        → 終了コード0で何もしない
OAuth 承認        → 通るのに処理が走らない
lsof でポート確認 → 特権ポートを見落として「空き」と判定
Dify の引用表示   → 出典は出るのに回答に反映されない
所有権の移管      → 完了するのにトリガーは動かない
n8n の画面        → 直っているのに保存されていない
```

**だから「エラーが起きたとき誰がどうやって気づくか」が設計の中心になる。**
A-1 で通知経路を設計していたおかげで、モデル名の腐敗（404）を即座に検知できた。

### 5-2. 技術選定は技術以外の理由で決まる

- Gemini 無料枠は**送信内容が学習・人間レビューの対象**（実案件では有料枠が前提）
- Dify は**マルチテナント提供が禁止**、ロゴ削除も不可
- n8n の本番運用には**自分のドメインとプライバシーポリシー**が要る
- Claude Project / NotebookLM は**利用者ごとの出し分けができない**

**「精度が良い方式」ではなく「その組織が使ってよい方式」が選定基準になる。**

### 5-3. 設問の質が成果の質を決める

A-1 の配置パターン、A-2 の方式選択、A-3 のコンテキスト設計——いずれも
「自分の言葉で説明できる」が完了条件だった。

私（Claude）が作った設問は**繰り返し雑だった**。「何があるか」「どこにあるか」だけの行は
トピックであって質問ではなく、2度作り直した。最終的に
「**聞く言葉／確認したいこと／答えの例と対処**」の3点セットにして初めて質問として成立した。

テンプレートの汎用化は、この設問設計に時間を溶かしたため**途中で見送った**。
顧客への質問集（`context-template/00-intake.md`）だけを残している。
