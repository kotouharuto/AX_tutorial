# Phase A 総括

AXコンサル副業に向けた技術習得フェーズの記録。

期間：2026-08-25 〜 09-23（約4週間・実作業 約25時間）
到達：A-1 **7/7** ／ A-2 **6/6** ／ A-3 **5/6**
記録：ハマりポイント **27件**（A-1:15 / A-2:7 / A-3:5）

## 1. 何をやったか

ロードマップの3ブロックを、期間ではなく到達条件で進めた。

**A-1　GAS と業務システム接続**
Googleフォームに問い合わせが届くと、内容を Gemini で4分類し、担当者へメールで振り分け、
スプレッドシートに記録する仕組みを Google Apps Script で構築した。
その上で、実行時間6分制限・トリガー多重起動・外部API失敗・権限スコープの4つを意図的に踏んだ。
配置パターン（コンテナバインド／スタンドアロン）の違いを、同じ処理を両方で作って比較した。

**A-2　RAG と評価設計**
架空企業の社内文書60件を生成し（表記ゆれ・新旧2版の混在・スキャン画像PDF・結合セルの表を
意図的に仕込んだ）、30問の評価セットを構築より先に作った。
同じ文書・同じ設問を NotebookLM / Claude Projects / Dify（セルフホスト）/ 自作RAG の4方式に通し、
数値で比較した。自作はフレームワークを使わず、埋め込みをローカル実行する構成にした。

**A-3　他人が使い続ける形にする**
A-1 と同じ処理を n8n（セルフホスト）で組み直し、GAS との境界を実感として確認した。
A-1・A-2 の成果物を Claude Project として「その組織専用の作業環境」に組み直した。
想定外入力・担当者不在・ルール変更・エラー検知の4点を意図的に起こして対処を実装し、
非エンジニア向けの引き渡しドキュメントを3本書いた。

3ブロックで題材を揃えた（同じ架空企業の問い合わせ業務）ため、A-3 で統合できた。

## 3. 4方式の比較

同じ60文書・同じ30問・同じ前置きで測定した。

| 方式 | 総合 | 単一文書 | 複数横断 | 表・数値 | 記載なし | ハルシネーション率 |
|---|---|---|---|---|---|---|
| Claude Projects | **30.0/30** | 12/12 | 8/8 | 5/5 | 5/5 | 0% |
| NotebookLM | 29.5/30 | 12/12 | 7.5/8 | 5/5 | 5/5 | 0% |
| 自作RAG | 28.0/30 | 11/12 | 7/8 | 5/5 | 5/5 | 0% |
| Dify（既定設定） | 24.5/30 | 11/12 | 5/8 | 3.5/5 | 5/5 | 0% |

**構築ゼロの方式が満点を取った。** 当初の仮説「既製で十分」は数値で支持された。

自作の失点2問は、どちらもスキャン画像PDFにしか答えがない問題だった。
テキスト抽出しかできないため構造的に答えられず、それ以外は全問正答している。

Dify の失点3.5問は、すべて既定のチャンク設定に起因する。
Dify は文書を改行ごとに細かく分割するため、規程の「制定日」と本文が別々の断片になり、
LLM が日付を一度も見ないまま「文書によって記載が異なります」としか答えられなかった。
表も同様に、ヘッダ行と各行が分離して行と列の対応が失われた。
モデルもプロンプトも自作と同一で、違うのはチャンクの切り方だけだった。

ハルシネーション率は4方式とも0%だった。
「文書に記載がない場合は推測せず記載がないと答える」という共通の前置きが、方式を問わず機能した。
自作は答えを知らない問いに対しても、推測せず正直に「記載がありません」と答えた。

## 4. 各ブロックの中心的な発見

### A-1：落とし穴の大半が「成功したように見える」

記録した15件のうち大半が、エラーを出さずに失敗する型だった。

`clasp push` はマニフェストを変更した状態で非対話シェルから実行すると、
「Skipping push.」とだけ表示して終了コード0で終わる。反映されていないのに成功に見える。

OAuth の承認画面は通るのに何も起きない、という状態も起きた。
Apps Script のエディタが「ファイル内の最初に定義された関数」を既定で選ぶため、
補助関数を実行していたのが原因だった。承認画面はマニフェストの宣言に基づいて出るので、
実際に何を呼ぶかとは無関係に正しく表示される。

承認画面そのものについても発見があった。スコープに最も時間をかけた本人が、
検証のために見るはずだった承認画面を読み飛ばした。利用者はもっと読まない。
つまり権限の説明を承認画面に依存できない。
さらに承認画面は権限を個別に拒否できる仕様で、初期状態は未チェックだった。
利用者が一部だけ承認した状態でもアプリは起動するため、
「許可したのに動かない」という、原因がコードの外にある障害が起きうる。

引き継ぎについては、所有権は移せるがトリガーと承認は移せないことが分かった。
ファイルの所有権移管は成功し、新しい所有者はコードも読める。それでも動かない。
トリガーは元の作成者のアカウントで実行され続け、そのアカウントが停止した時点で止まる。
しかもアカウント削除までタイムラグがあるため、引き継ぎから数週間後に、
無関係な変更を疑いながら調査することになる。

実行時間の6分制限については、強制終了が catch できないことが本質だった。
finally も走らないため、落ちてから片付けることは原理的に不可能で、
落ちる前に自分で止まるしかない。これが分割実行が必要な理由そのものだった。

### A-2：評価する側が間違っていた

30問の評価セットを作って方式を測ったところ、評価される側ではなく評価する側の欠陥が出た。

正解を1問間違えていた。表を確認すると自分の書いた期待値が誤っており、
被評価側（Claude Projects）の回答が正しかった。そのまま採点していれば、
正しい回答を不正解と判定していた。

自動採点も誤動作した。期待値に「なぜ間違えやすいか」を親切に書いたところ、
その中に含まれていた誤答例の数値が、実際の誤答とマッチしてしまった。
明確な誤答を部分正解と判定していた。しかもその問題は、
自作構成の構造的な弱点を検出するために置いたものだった。
弱点を検出するはずの問題が、弱点を隠す方向に働いていた。

最終的には測定方法自体を変えて解決した。
チャンク戦略や検索方式の効き幅は本質的に検索性能の問題で、生成部分は全構成で共通なので、
正答率ではなく「正解の根拠文書を検索で拾えたか」で測ることにした。
判定が機械的に定まるようになり、API 呼び出しもゼロになった。
採点が難しいのは、測るものを間違えているサインだった。

また、自分で生成した題材データにキリル文字とハングルを3回混入させた。
うち1件は「わざと表記誤りを含む」とコメントに書いていたが、実際は単なるタイプミスだった。
汚れは意図して入れたものだけを汚れと呼ぶべきで、事故を後から意味づけると
何を測っているのか分からなくなる。

### A-3：GUI ツールの方が渡しにくかった

A-1 と同じ処理を n8n で組んだ結果、「GUI ツールだから非エンジニアでも運用できる」が
成り立たないことが分かった。

最も決定的だったのは、業務ルールをシートで管理できなかったことだ。
n8n は「前の処理が出したデータの件数だけ次の処理を繰り返す」仕組みのため、
担当者マスタ（6行）を読むと以降の処理が6倍実行され、同じメールが6通飛んだ。
順序を変えても、1回だけ実行する設定にしても解決せず、
最終的に宛先をコードに定数として埋めるしかなかった。

結果として「担当者を変えたいとき誰が直すか」への答えが、
GAS では「シートを書き換える（誰でも可）」、n8n では「コードを修正する（技術者のみ）」になった。
A-3 の主題である「他人が使い続ける形」で、GUI ツールが手書きのコードに負けた。

認証についても差が出た。n8n の Google 連携はテストモードのため7日で失効し、
誰も何もしていないのに止まった。止まったことは通知されず、
復旧にはブラウザで Google にサインインし直す必要があるため、
コンテナを触れる人ではなくアカウントの持ち主にしか直せない。
本番モードにすれば無期限になるが、Google の要件として
公開されたホームページとプライバシーポリシーの URL が必要になる。

Claude Project 側では、ナレッジの選別が指示書のチューニングより先に効くことが分かった。
設計時に「旧版の規程2ファイルは外す」と決めていたのに、投入作業で混ざっていた。
指示書には「矛盾があれば両方示す」と書いてあり、それは正しく機能したのだが、
結果として8問が「文書によって記載が異なります」という確認の必要な回答になった。
旧版2ファイルを削除して投入し直したところ、5問が単純な正答に変わった。
矛盾をどう扱うかを指示書で決めるより、矛盾を作らない方が利用者の負担は小さい。

## 5. 通して見えた構造

### 失敗は失敗として現れない

27件のうち約半数が、成功の表示と実際の状態が乖離する型だった。

`clasp push` は終了コード0で何もしない。OAuth の承認は通るのに処理が走らない。
`lsof` でのポート確認は特権ポートを見落として「空き」と判定する。
Dify は引用として正しい文書名を表示するのに、その内容は LLM に渡っていない。
所有権の移管は完了するのにトリガーは動かない。
n8n は画面上で修正が反映されているように見えるのに保存されていない。

だからこそ「エラーが起きたとき誰がどうやって気づくのか」が設計の中心になる。
A-1 で通知経路を実装していたおかげで、Gemini のモデル名が提供終了して404を返すようになったとき、
即座に検知できた。握り潰していれば「なぜか未分類になる」という調査困難な状態になっていた。

### 技術選定は技術以外の理由で決まる

Gemini の無料枠は、送信内容が Google の製品改善・機械学習に使われ、
人間によるレビューの対象にもなる。有料枠では使われない。
動作は完全に同じなので気づく機会がなく、課金を有効化しない限り無料枠のままになる。
実案件では有料枠が前提条件であり、これは価格交渉ではなく技術選定の制約になる。

Dify はオープンソースだがマルチテナント環境の運営が禁止されており、
自分がホストして複数顧客に提供することはできない。フロントエンドのロゴも削除できない。

n8n の本番運用には、自分のドメインと公開されたプライバシーポリシーが必要になる。
GAS では一切不要だった。Google の中で動くか外から使うかの違いがここに出る。

Claude Project と NotebookLM は利用者ごとの出し分けができないため、
部署によって見せる文書を変える要件があると、それだけで選択肢から外れる。

つまり「精度が良い方式」ではなく「その組織が使ってよい方式」が選定基準になる。

### 設問の質が成果の質を決める

A-1 の配置パターン、A-2 の方式選択、A-3 のコンテキスト設計は、
いずれも「自分の言葉で説明できる」ことを完了条件にしていた。

そのための設問を Claude（私）が作ったが、繰り返し雑だった。
「何があるか」「どこにあるか」とだけ書いた行はトピックであって質問になっておらず、
2度作り直すことになった。最終的に
「顧客に聞く言葉／確認したいこと／答えの例と対処」の3点セットにして初めて質問として成立した。

コンテキスト設計テンプレートの汎用化は、この設問設計に時間を溶かしたため途中で見送り、
顧客への質問集だけを残した。ケースバイケースの判断はその場で考えれば済むもので、
テンプレートの価値は考えることの代替ではなく聞き忘れの防止にある、という整理をした。

## 7. 未達・見送り

**他人に触ってもらう検証（A-3 条件6）は未達。**
一人で進めているため協力者がおらず実行できなかった。
引き渡しドキュメントが機能するかは検証できていない。Phase B で実案件の機会があれば確認する。

**コンテキスト設計テンプレートの汎用化は見送り。**
顧客への質問集のみ作成した。架空企業向けの具体例は残してあるので、
次の案件では「前回こう書いた」を見ながらその場で書き換える運用になる。

**サービスアカウント配置と共有ドライブでの所有権移管は調査のみ。**
どちらも Google Workspace の機能で、個人 Gmail アカウントでは検証できなかった。
「所有権は移せるがトリガーは移せない」という結論は公式ドキュメントに基づくもので、実物で確認していない。

**Dify のチャンク調整版は未測定。**
「既定のまま使うと何が起きるか」を測るのが目的だったため、設定を変えた場合の精度は分からない。
調整すれば自作と同等になる可能性は高い。

**OCR を入れた自作RAG は未実装。**
「テキスト抽出しかできない」ことが自作構成の制約であることを実証するのが目的だった。
OCR を入れれば画像PDFの2問は解決する見込み。

## 8. Phase A を終えた時点で言えること

ロードマップの想定どおり、ここで得た実感をもとに次のフェーズを設計する段階に来た。
現時点で事実として言えることを記す。

**手元にあるもの**

「作らない」判断を数値で説明できるようになった。
既製方式が満点を取り、手で書いた自作が2問落とし、GUI ツールが5.5問落とした——
この実測があることで、「NotebookLM で十分だと思います」という感想ではなく、
「同じ30問で測って、作った方が精度が低く、構築に2週間かかります」と言える。

壊れ方の知識が27件ある。特に「動いているように見えて止まっている」型の検知設計は、
自分で通知経路を作り、それが実際に404を捕まえた経験に裏打ちされている。

見積もりの材料がある。4.1秒/件、6分で87件、GAS 2時間 vs n8n 2日。
「何件までなら1実行で回るか」「この構成なら何日か」に即答できる。

**まだ無いもの**

他人に触ってもらった経験がない。引き渡しドキュメントは書けたが、
それを読んだ人が実際に運用できるかは確認していない。

Workspace 環境での検証がない。共有ドライブ、サービスアカウント、
200人規模の権限管理は、個人アカウントでは試せなかった。

自分のドメインとプライバシーポリシーがない。
n8n をはじめ、Google の外にあるツールを納品する前提条件として必要になる。
