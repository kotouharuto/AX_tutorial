## 3. 売り物になる資産

### 3-1. 実測値

顧客への見積もり・説明にそのまま使える数値。

| 数値 | どう測ったか |
|---|---|
| GAS の実行時間 **4.1秒/件、6分で約87件** | 150件を分割せず一括処理して強制終了させた |
| トリガー多重起動で **20件中3件（15%）が二重処理** | 1分間隔のトリガーを2本登録して競合させた |
| RAG のパラメータ効き幅は**最大4%（1問）**、前処理の欠落は**8%（2問）で固定** | 7構成で検索 Recall を測定 |
| 構築時間 **GAS 約2時間 vs n8n 約2日** | 同一処理を両方で実装 |
| Dify は**構築3.5時間に対して評価1時間** | セルフホストで8件の詰まり |

### 3-2. 4方式の比較（同一60文書・同一30問）

| 方式 | 総合 | ハルシネーション率 |
|---|---|---|
| Claude Projects | **30.0/30** | 0% |
| NotebookLM | 29.5/30 | 0% |
| 自作RAG | 28.0/30 | 0% |
| Dify（既定設定） | 24.5/30 | 0% |

**構築ゼロの方式が満点を取った。** 自作の失点2問はどちらも画像PDFにしか答えがない問題で、
それ以外は全問正答。Dify の失点3.5問はすべて既定のチャンク設定に起因する。

この数値があることで、「NotebookLM で十分だと思います」という感想ではなく、
「同じ30問で測って、作った方が精度が低く、構築に2週間かかります」と言える。

### 3-3. ハマりポイント集 27件

踏んだ落とし穴を、原因・対処・効かなかった対処・納品時の含意のセットで記録した。
他人の環境でも同じ問題が起きるため、そのまま納品材料になる。内訳は A-1:15 / A-2:7 / A-3:5。

**約半数が「エラーにならず成功したように見える」型**だった。例：

- `clasp push` が終了コード0で何もしない（非対話シェル）
- OAuth の承認は通るのに処理が走らない
- `lsof` でのポート確認が特権ポートを見落として「空き」と判定する
- Dify は引用として正しい文書名を表示するのに、その内容は LLM に渡っていない
- 所有権の移管は完了するのにトリガーは動かない

### 3-4. 判断基準の文書

- **配置パターンの選択基準**：案件開始時に何を聞き、どの条件でどれを選び、誤るとどうなるか
- **方式選択の基準**：4方式の精度・制約・コストを並べ、「作らない」条件と「作る」条件を言語化
- **顧客への質問集**：外部サービス利用の可否／利用者／文書の状態／運用と引き継ぎ／予算の5分野。
  各項目を「聞く言葉／確認したいこと／答えの例と対処」の形式で記述
- **引き渡しドキュメント雛形3本**：GAS 版・Claude Project 版・n8n 版

## 4. Phase A で見えた、売り方に関わる事実

### 4-1. 「作らない」提案ができる状態になった

既製方式が満点を取ったため、「作らなくていい」と数値で言える。
これは作るより難しい提案で、顧客は予算を用意していることもあるし、
「専門家なのに作れないのでは」と疑われることもある。根拠となる実測を持っていることが差になる。

### 4-2. 技術選定は技術以外の理由で決まる

- **Gemini の無料枠は、送信内容が学習・人間レビューの対象**になる。有料枠では使われない。
  動作は同じなので気づく機会がなく、課金を有効化しない限り無料枠のまま。
  実案件では有料枠が前提条件であり、これは価格交渉ではなく技術選定の制約
- **Dify はマルチテナント提供が禁止**（自分がホストして複数顧客に提供できない）。ロゴ削除も不可
- **n8n の本番運用には、自分のドメインと公開されたプライバシーポリシーが必要**
- **Claude Project / NotebookLM は利用者ごとの出し分けができない**

つまり「精度が良い方式」ではなく「その組織が使ってよい方式」が選定基準になる。

### 4-3. GUI ツールの方が渡しにくかった

「n8n のような GUI ツールなら非エンジニアでも運用できる」は成り立たなかった。

| 「担当者を変えたいとき誰が直すか」 | GAS | n8n |
|---|---|---|
| 答え | **シートを書き換える**（誰でも可） | **コードを修正する**（技術者のみ） |

n8n は参照テーブル（6行）を読むだけで以降の処理が6倍実行され、同じメールが18通飛んだ。
対策を試したが解決せず、宛先をコードに定数として埋めるしかなかった。

さらに n8n の Google 連携はテストモードのため**7日で失効して止まった**。
誰も何もしていないのに止まり、通知もされず、復旧はアカウントの持ち主にしかできない。

**「簡単そう」という印象への反証を、実測で持っている。**

### 4-4. 作業の進み方の傾向（観察）

Phase A を通して、**実装と検証は進み、抽象化・テンプレート化は止まった**。

- 落とし穴を踏んで対処を実装する作業、数値を測って比較する作業は最後まで完了した
- コンテキスト設計テンプレートの汎用化は途中で見送った
  （「ケースバイケースだから、その場で考えるか持ち帰って考えれば済む」という判断）
- n8n の構築では「むずくね？」「無駄に時間がかかる」という反応が出た

引き受ける案件の性質を考える材料になる可能性がある。

## 5. 持っていないもの・確かめていないこと

**これらは Phase B の制約条件になる。**

### 5-1. 環境

- **Google Workspace のアカウントがない**（個人 Gmail のみ）
  → 共有ドライブ、サービスアカウント、ドメイン全体の委任、200人規模の権限管理が検証できていない
  → 「所有権は移せるがトリガーは移せない」という結論は公式ドキュメントに基づくもので、実物で確認していない
- **Windows の実機がない**
  → Excel 処理の納品先は Windows が多いため、実行環境の検証ができない
- **自分のドメインとプライバシーポリシーページがない**
  → n8n をはじめ、Google の外にあるツールを納品する前提条件として必要
- **API の有料枠を契約していない**（無料枠のみで検証）→ 2026-10 に Gemini を前払いにした（9-5）

### 5-2. 経験

- **他人に触ってもらった経験がない**
  引き渡しドキュメントは書けたが、それを読んだ人が実際に運用できるかは未検証。
  一人で進めているため協力者がいなかった（A-3 の完了条件で唯一の未達項目）
- **実案件の経験がない**（架空企業を題材にした検証のみ）

### 5-3. 測っていないこと

- Dify のチャンク設定を調整した場合の精度（既定のまま何点取れるかが目的だったため）
- OCR を入れた自作RAG の精度（画像PDF 2問は解決する見込み）

## 8. 参考：Phase A の運用ルール

Phase B でも同じ原則を使うなら、以下が Phase A で機能した。

- **期間ではなく到達条件で管理する。** 目安期間は締切ではなく、大きく超えたときに深入りを疑う基準
- **完了条件を満たしたら、理想に届かなくても次へ進む**（特に際限なく凝れる領域）
- **落とし穴は意図的に踏む。** うまく動かすより先に壊して、対処を体で覚える
- **記録を義務にする。** 完了条件のチェック、ハマりポイント（原因と対処をセット）、所要時間の実測
- **成功の表示を信用しない。** 終了コード、例外なし、画面表示だけで完了と判断しない

### 9-4. 見えた事実

**「作るより、他人の環境で動くことを確かめる方が重い」が5ブロックすべてで出た。**
作ること自体は短時間で済み、時間は英語ロケールの Windows、セキュリティソフト、macOS の定期実行の制約、
常駐させた夜間の接続、実データの汚れ、初めての人が手順書を読むこと、利用者のバージョン違いで消えた。

**個人情報は「列で絞る」では守れなかった。** テストのデータでは通り、実データの列ずれで漏れた。
伏せる処理を足すと、今度は伏せ字が事実と違う情報になった（日時を名前とみなして伏せた）。
最終的に、形の崩れた行は中身を出さない形にした。本文に書かれた第三者の氏名は伏せられない。

**作成者は自分の手順書の誤りを見つけられない。** 導入キットの手順書は、初めての人が読んだだけで
作成者（Claude）の書き間違いが4件出た。どれも作成者の手元では通っていた。

**外部サービスの都合で、納品後に外から壊される。** Gemini が前払いへの切り替えを求めて止まった（402。
同じキーを使う A-1 も止まっていた可能性が高い）、SDK のメジャー更新で旧来の書き方が使えない、
ツールのバージョンで設定の効き方が逆になる、など。

**Claude の誤りの多くは「確かめずに断定して書いた」ことだった。** 実機・実データ・初めての読者で見つかった。
文書では確かめたことと確かめていないことを書き分ける形にした。

**誰が気づき、誰が直すかは、技術では決まらない。** 通知の仕組みは作れても、受け取る人・承認できる人・
動かすマシン・費用の負担者は顧客組織の事情で決まる。引き渡し文書の【要記入】が、そのまま顧客への確認事項になる。

**Slack の Socket Mode のアプリはマーケットプレイスに出せない。** 顧客のワークスペースごとにアプリとトークンを作る必要がある。
常駐には、常に電源が入りネットワークにつながったマシンが要る。
